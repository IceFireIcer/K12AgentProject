# Domain Docs

工程技能在探索代码库时如何消费本仓库的领域文档。

## 布局：单上下文（single-context）

本仓库为**单上下文**仓库，没有 `CONTEXT-MAP.md`。

## 探索前先读

- **`项目执行文档.md`** —— 唯一权威执行文档：范围决策、接口契约、数据层 DDL、排期、验收标准、风险表。
- **`docs/`** —— 领域语义与依据：
  - `docs/业务陷阱清单.md` —— 各模块领域陷阱与业务验收口径（与编排框架无关，动手前先扫）。
  - `docs/项目简介.md` —— 赛题原文与评分标准，需求边界以此为准。
  - `docs/研判文档PiAgent.md` —— 架构迁移提案（已裁决，**不要照它实现**）。
  - `docs/研判文档Deepseek.md` / `docs/研判文档Qwen3.7.md` —— 设计依据与早期研判（部分结论已被取代）。
- **`docs/adr/`** —— 本仓库**不使用** ADR 目录；架构决策统一记录在 `项目执行文档.md` 第 0 / 第 13 节及历史提交信息中。
- **`CONTEXT.md`** —— 尚未创建。缺失时**静默跳过**，不要提示缺失、也不要主动建议创建；待术语或决策真正收敛时再由 `/domain-modeling` 惰性生成。

## 术语来源与优先级

输出中命名领域概念时（票标题、重构提案、假设、测试名），使用上位文档中的既有措辞，不要漂移到同义词：

1. `项目执行文档.md`（术语与规格的规范来源）
2. `docs/` 各文档
3. 历史提交信息（记录已裁决的取舍，例如「只保留文档、代码见附注标签」）

若需要的概念在上述文档中不存在，这是一个信号：要么在发明项目并不使用的语言（重新考虑），要么存在真实缺口（记下来交给 `/domain-modeling`）。

## 决策冲突

若某项输出与既有裁决相矛盾（例如 `项目执行文档.md` 第 13.3 节的六项架构分叉、第 3.3 节的砍单清单），**显式提出，不要静默推翻**：

> _与 B-1（保留 Python sidecar）相矛盾 —— 但值得重开，因为……_
