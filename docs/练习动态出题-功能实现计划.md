# 练习模块动态生成题目 — 功能实现计划报告

> 版本：v1（2026-10-01）
> 范围：独立闯关练习页（`views/Quiz.vue` + `stores/quiz.ts`）的「做完内置题后动态生成个性化题目」闭环。
> 权威口径：与 `项目执行文档.md` 冲突时以执行文档为准；本计划只做设计，不改任何代码。

---

## 0. 摘要

在**不动冻结契约**的前提下，为练习页补一条「自动追加 + 主动续练」的个性化出题链路：

- 新增主进程**题目生成服务**（即需求中的「题目生成 subagent」，落位 `desktop/src/main/agent/quizgen/`），复用 Pi 模型通道（`runtime.ts` 的 `completerHolder` / `lazyComplete`，与动画 / 编程生成器同一条接线）、复用 Extension 层已有的 `prepareVariants` 校验与 `POST /api/quiz/variants` 登记（**先登记、后下发**，答案不出 Python）。
- 新增 **2 条 invoke 通道**（`quiz:generate-auto` / `quiz:generate-more`），不新增 push 通道、不进 6 事件词表、不新增 Pi Tool（练习页不开对话，与 `stores/quiz.ts` 文件头「刷题不消耗云端对话」的既有裁决一致）。
- 自动追加阶段内置 + 生成题总数上限 **20**；「还想再练练」按钮每次 +10 题、编号从当前总数之后顺延、不受 20 上限约束；按钮渲染在题目列表尾部，追加后天然随列表末端移动，可反复点击。
- 题号是**纯展示序号**（合并列表下标 + 1），不落库、不进契约；题目的稳定标识仍是 `qid`（生成题 `gen-<kp>-<seed>-N` 自带随机段，与题库真题、历史生成题均不撞车）。
- 服务端（Python sidecar）**零改动**：登记（variants）、复用读取（D-088 的 `GET /api/quiz/generated/{id}`）、判分（`POST /api/quiz/grade`）三条端点全部复用。

| # | 需求原文（概括） | 本计划的落点 | 验收口径 |
| --- | --- | --- | --- |
| 1 | 做完全部内置题后，按答题情况在后台启动出题 subagent | 渲染层判据触发 → IPC `quiz:generate-auto` → 主进程 quizgen 服务异步生成 | 内置题全部判分过后**只自动触发一次**；生成期间学生可继续操作（重做、切关、翻题）不被阻塞 |

| 4 | 「还想再练练」按钮：传全部答题情况 + 决策记录，生成 10 题，编号从总数之后继续 | IPC `quiz:generate-more`（载荷含 DecisionTrace）；每次恰好 10 题 | 已有 20 题时新题从第 21 题开始；再点从第 31 题开始 |
| 5 | 按钮在每次追加后移动到新的最后一题之后，可反复点击 | 按钮渲染在题目列表容器**之后**（列表模式）/ 收尾卡动作区（单卡模式），列表变化即移动 | 连续点击 3 次，题号 1→20→30→40，按钮始终在最后一题之后 |

**「做完」的判据（口径裁决，见 §4.1）**：内置题每道**至少判分过一次**（`attempts[qid].result != null`），不要求全部答对。理由：答错可重试是本产品的既有节奏（掌握度首次作答决定），「卡在错题上」的学生恰恰是最需要个性化题的人，多次尝试本身就是出题素材；若采用「全部答对」口径（与单卡模式收尾卡同口径），会把最需要帮助的学生挡在门外。

## 3. 总体设计

### 3.1 「subagent」的形态选择

需求原文是「题目生成 subagent」。本仓库没有 Pi 子会话 / 子 agent 的运行时形态，且练习页**刻意不开对话**（`stores/quiz.ts` 文件头：刷题不该每答一题消耗一次云端调用）。因此落位为：

**主进程常驻的「个性化出题服务」** —— 一个独立模块 `desktop/src/main/agent/quizgen/service.ts`，按请求执行「组装画像 → 调模型 → 校验 → 登记 → 投影返回」的一次流水，不具备对话能力、不注册 Pi Tool、不进 6 事件词表。它对渲染层表现为一次 invoke（Promise 即「后台」：触发后学生继续操作，resolve 时题目出现）。

这样选的边界收益：

1. **LLM 调用归编排层（TS 主进程）** —— 服务走 `lazyComplete`，Python 侧继续零 LLM 客户端（`pyproject.toml` 钉死的那条不变）；
2. **数据 / 答案归 Python** —— 服务不碰 SQLite、不存答案，登记与判分全走 sidecar 既有端点；
3. **契约零改动** —— 不加端点、不改 pydantic 模型，`check:api` / `check:tool-schema` 不受影响（没新增 TypeBox Tool）；
4. **主进程出网两口纪律（D-116）不破** —— 服务只经 `bridge/client.ts` 的 `apiFetch` 打 sidecar，模型调用走 Pi 模型通道，不出现第三处 `fetch(`。

### 3.2 数据流

```
┌─ 渲染层（练习页）────────────────────────────────────────────┐
│ ① 内置题全部判分（触发判据，stores/quiz.ts 扩展）             │
│ ② invoke quiz:generate-auto { kpId, context }                │
│      （context = 内置题 DecisionTrace[]，§4.6）               │
│ ⑦ 返回 QuizPayloadView（无答案）→ 追加进 generated 列表       │
│    → 合并列表续号 → 「还想再练练」按钮随列表末端移动           │
│                                                              │
│ ④ 学生点「还想再练练」                                        │
│ ⑤ invoke quiz:generate-more { kpId, context }                │
│      （context = 全部题目的 DecisionTrace[]）                 │
│ ⑥ 返回 10 题 → 追加 → 回到 ⑦（可反复）                       │
└──────────────────────────────────────────────────────────────┘
          │ ②⑤                                    │ ⑦⑥
          ▼                                       ▲
┌─ 主进程 quizgen 服务（新）───────────────────────────────────┐
│ · 身份/学段注入：studentId() + currentGradeLevel()（不收自渲染层）│
│ · 读现状：GET /api/quiz/bank（题量）+ GET /api/quiz/generated │
│   （已有题干清单 → 去重素材；现有总数 → 算自动阶段配额）       │
│ · buildPersonalizedQuizPrompt(context)（纯函数，可单测）      │
│ · complete() = runtime 的 lazyComplete（无 Key → 可读降级）   │
│ · prepareVariants 校验（复用）→ registerVariants 登记（复用） │
│ · 失败重试 ≤2（复用 DEFAULT_GENERATION_RETRIES 口径）         │
└──────────────────────────────────────────────────────────────┘
          │ 登记（含答案，只进 Python）
          ▼
   POST /api/quiz/variants → learning.db generated_question（本地保存）
   复用读回：GET /api/quiz/generated/{id}（既有链路，需求 3）
   判分：POST /api/quiz/grade（既有链路，qid 不撞车）
```

**先登记、后下发（F4 同款铁律）**：登记失败的那一批**绝不**发给渲染层——后端判不了分的题发出去，学生做完提交必 404。降级路径是「这一批不出」，不是「出无答案的题」。

## 4. 详细设计

### 4.1 触发机制（需求 1）

**判据**（渲染层，`stores/quiz.ts` 新增纯函数，可单测）：

```
shouldAutoGenerate(bank, attempts, autoFiredKp, currentKpId, totalLimit=20) =>
  bank.questions.length > 0
  && bank.questions.every(q => attempts[q.qid]?.result != null)   // 全部判分过（不要求全对，见 §1 口径）
  && autoFiredKp !== currentKpId                                    // 同一关只触发一次
  && (bank.questions.length + generatedCount) < 20                  // 自动阶段配额未满
```

- **触发点**：`submit()` 判分返回后顺手求值（与现在判完刷 `loadProgress(true)` 同一处控制流）；不必开 watcher。
- **防重**：store 里记 `autoFiredKp`（单值即可）；`selectLevel` 切关时清空（与 `attempts` 同一批清理）。学生「重做本关」**不重置**它——做完了就是做完了，重做不再白花一次生成。
- **题库为空的关卡**：`bank.questions.length === 0` 不触发（页面已有「让老师现场出几道」的空态指引）；但若合并列表因**复用历史生成题**非空，全部判分后「还想再练练」按钮仍会出现（按钮判据独立于自动触发，见 §4.5）。
- **在途去重**：沿用 `bankInFlight` 的「请求键」模式（键 = `kpId`），连点 / 判分连击只发一次。
- **沙箱演示态**：与 `quizGrade` 处理器同判据（`demoBlocked()`）——沙箱里不触发生成（它要花真钱调模型）。

### 4.2 出题服务与个性化 Prompt（需求 1、4 的「subagent」）

新文件 `desktop/src/main/agent/quizgen/service.ts` + `prompt.ts`：

**`buildPersonalizedQuizPrompt(input)`**（纯函数，导出供单测），输入：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `gradeLevel` / `kpId` | 主进程注入 | 学段严格贴题（超纲术语由服务端登记时按词表复查，既有防线） |
| `count` | auto = `min(10, 20 - 现有总数)`；more = `10` | 单批 ≤ `MAX_QUIZ_QUESTIONS`（10，契约上限） |
| `summary` | 答对数 / 判分数 / 一次答对数 / 多次尝试数 | 总体难度定档 |
| `traces` | DecisionTrace[]（§4.6） | 逐题素材：错题题干、错选内容、多次尝试轨迹 |
| `existingStems` | `GET /api/quiz/generated` 已有题干（含内置题干） | **去重约束**：新题不得与已有题干同义重复 |

Prompt 输出形态与 `buildVariantPrompt` 完全一致（严格一行 JSON `{"questions":[…]}`，每题含 `qid/type/stem/options/answer/explanation`、开放题带 `rubric`），因此**下游链路（`parseVariantPayload` → `prepareVariants` → `registerVariants`）一行不改**。个性化只发生在 Prompt 内容层：

- 一次答对率高 → 题干变式加深（换情境 / 换问法 / 提升一步推理）；
- 多次尝试 / 答错的题 → 围绕**该题考查的子概念**出同类型巩固题，Prompt 里带上错题题干与学生的错误选项原文；
- 最多 1 道开放题（与既有口径一致，`rubric` 非空即主观题，判分自动走 LLM）。

**服务流程**（伪码级）：

```
generatePersonalized({ kpId, mode: 'auto' | 'more', context }) →
  studentId / gradeLevel ← 主进程（不收自渲染层）
  [auto] 现状 = bank 数 + generated 数；配额 = 20 - 现状；配额 ≤ 0 → 直接返回空成功
  重试 ≤ DEFAULT_GENERATION_RETRIES(2)：
    raw ← lazyComplete(buildPersonalizedQuizPrompt(...))     // 无 Key → 抛可读错误
    prepared ← prepareVariants(raw, { kpId, gradeLevel, maxQuestions: count })   // 复用
    registered ← registerVariants({ studentId, gradeLevel, questions: prepared.questions })  // 复用
    registered ≠ null → return { ok: true, payload: registered }  // 投影后、无答案
  全部失败 → return { ok: false, message: 可读中文 }（**不退回题库**——题库题已做过，退回没有意义；
             这是与 Extension 里 `generate` 的唯一口径差异，要在代码注释里写明）
```

**接线**：`runtime.ts` 模型通道填充处（`completerHolder` 被赋值 / 清空的那段，~1367–1395 行）把 `lazyComplete` 同步交给 quizgen 服务持有——与 `createAnimationGenerator({ complete: lazyComplete })` 完全同构；Key 被热清空时服务随之降级（`completerHolder = null` 的既有行为）。

### 4.3 题号与 20 上限（需求 2）

- **题号 = 合并列表下标 + 1**（`questionRows` 的 `row.index + 1`），纯展示序号，不落库、不进契约。追加生成题只是列表变长，续号天然成立，无任何编号逻辑要写。
- **自动阶段上限 20**：`views/Quiz.vue` 的 `questions` computed 加一段截断——
  ```
  自动阶段（未点过「还想再练练」）：
    生成题最多取 (20 - bankCount) 道（`loadGenerated` 回来的最近优先）
  点击过按钮后：截断解除，列表自然增长（21、31、…）
  ```
  截断放在**渲染层投影**而不是后端：`GET /api/quiz/generated` 的 `limit` 是通用参数，不动契约；「20」是本功能的 UI 策略，不属于数据层。
- **自动阶段批量策略**：配额可能到 17（内置 3 + 17 = 20）。单批 ≤ 10（契约上限），分两批串行（先 10 后 7），批间失败即停并给可读提示（已成功的批次照常下发——部分成功优于全无）。
- **编号示例**（对齐需求原文）：内置 3 题（第 1–3 题）→ 自动追加至 20（第 4–20 题）→ 点按钮 → 第 21–30 题 → 再点 → 第 31–40 题。

### 4.4 本地保存与复用（需求 3）

既有链路原样满足，计划中只需**验证**不需新建：

- 生成题经 `POST /api/quiz/variants` 落 `generated_question`（`student_id` 归属，D-088 v3 迁移；`ON CONFLICT(qid) DO UPDATE`，qid 带随机段不撞车）；
- 换关卡再回来 / 重启应用：`selectLevel` → `loadGenerated(kpId)` 自动带回（`stores/quiz.ts` 既有代码），合并且按 qid 去重（`views/Quiz.vue` 既有 `questions` computed）；
- 复用的题作答照走 `POST /api/quiz/grade`（生成题先于题库查找，`_locate_question` 既有顺序）。

**一个必须写的规则**：复用读回的历史生成题**同样计入 20 上限**（需求原文「内置与 AI 生成题目总数最多 20 题」不分来源）。§4.3 的截断公式 `20 - bankCount` 覆盖了这一点（历史题 + 本轮新题一起截）。

### 4.5 「还想再练练」按钮（需求 4、5）

**出现条件**：合并列表里**所有题**都判分过（`attempts[qid].result != null`，与自动触发同口径但看全量）——既覆盖「自动阶段刚追加完」也覆盖「复用历史题做完」。生成中 / 配额外不隐藏。

**落点（两种排版都要）**：

| 排版 | 位置 | 说明 |
| --- | --- | --- |
| 全部铺开（list） | `<ol class="qlist">` **之后**（`localHint` 那行附近） | 列表变长按钮即「移动」——它渲染在容器尾部，DOM 顺序天然跟随最后一题 |
| 一次一张（single） | 收尾卡 `.qcard__finish-actions` 里，与「回去接着做 / 看本轮小结 / 去下一关」并列 | 走到收尾卡 = 本轮走完，是邀请续练的语义正确时机；新题追加后 `finished` 复位（`goTo` 已有该行为），回到单卡题流 |

⚠️ **两个版式纪律坑（实现时必守）**：
1. 收尾卡里已有 `.k12-cta`（「去下一关」）——「还想再练练」必须用 `el-button`（次要动作形态）。一屏只允许一个主色填充，且 `verify-guard-mutations.mjs` ⑤ 只替换第一处 `.k12-cta`，多一处会让那条变异验证静默失效。
2. 学生视角文案只有「还想再练练」五个字；生成机制（subagent / 登记 / 契约）的说明进 `<TeacherGate>`。`student-view-discipline.test.ts` 会按文件扫文案，新增句子别带技术词。

**状态机**：`idle → loading（防连点，沿用请求键去重）→ done（题目追加，回到 idle）| failed（行内一句可读中文 + 「再试一次」，不摆错误卡——与 `loadGenerated` 静默失败同一条纪律，但按钮路径要让学生知道发生了什么）`。

**上下文组装（需求 4 的「全部答题情况与决策记录」）**：点击时把**当前合并列表全部题目**的 DecisionTrace（§4.6）随 invoke 上行；`count` 固定 10，由服务端定而不是渲染层传（渲染层传了也不信，主进程校验——与 `quizBank` 的 count 处理同一纪律）。

**无 Key 世界的降级**：服务返回 `{ ok: true, degraded: true, note }`（对齐 `SUBJECTIVE_UNAVAILABLE_TEXT` 的「判不了就明说」形态，不是 error 事件）→ 按钮旁显示一句「现在没法出新题（还没有可用的模型），可以先聊一聊或换一关」。自动路径同样返回降级标记，渲染层**静默吞掉**（不摆错误卡）。

### 4.6 决策记录数据结构（DecisionTrace）

**渲染层现状缺口**：`attempts[qid]` 只存最后一次 `result`，提交历史（每次选了什么、判分如何）没有留痕——「一次答对还是多次尝试」「所选选项及决策过程」拿不全。需要**一处扩展**：

```ts
// stores/quiz.ts：QuizAttempt 增加只增不减的提交轨迹（本地态，不落库——落库的流水
// 在后端 learning_history，那是另一份事实，见下）
export interface QuizAttempt {
  qid: string
  answer: string                  // 最近一次作答（草稿态，既有）
  result: QuizResultView | null
  submitting: boolean
  error: string | null
  /** ★ 新增：每次提交的轨迹（提交即追加；判分失败也记，answer 留着、correct 记 null） */
  history: Array<{ answer: string; correct: boolean | null; at: number }>
}
```

上行给 subagent 的 `context`（在 invoke 载荷里组装，**内部 IPC 形态**，不进冻结契约）：

```ts
interface DecisionTrace {
  qid: string
  index: number                    // 题号（展示序）
  type: 'choice' | 'blank' | 'code_blank'
  source: 'bank' | 'generated'
  stemHead: string                 // 题干前 120 字（与 _record_attempt 的截断口径一致）
  tries: Array<{ answer: string; correct: boolean | null }>
  firstTryCorrect: boolean | null  // 首次判分即对
  triesCount: number
}
```

**合规边界**：轨迹内容是**学生的作答**（选项文本 / 填空内容），不是对话正文，随 invoke 上行给主进程组装 Prompt 属于当轮使用，不入库、不落 `learning_history`（后端那条流水继续由判分端点自己写，两条链路不合并）。`stemHead` 截 120 字对齐 `_record_attempt` 的 `question` 列口径。

**v1 局限（计划里明示）**：`history` 是页面内存态，`selectLevel` / `restart` 清空后丢失；跨会话的作答轨迹在后端 `learning_history` 里（`repeat` / `counted` 判据都有），但 v1 **不**为它加读取端点（那是一次契约改动）。按钮触达时如果学生在同一关没切走（绝大多数场景），本轮轨迹是全的；切走再回来的场景退化为「只有题干清单、无轨迹」，Prompt 里相应说明「该生历史作答不可用」。增强项记入 §10。

### 4.7 IPC 通道与载荷

`ipc/channels.ts` 新增（invoke，不进 `PUSH_CHANNELS`）：

```ts
/** 渲染 → 主进程：做完内置题后的自动追加生成（触发判据在渲染层，配额在主进程复核）。 */
quizGenerateAuto: 'quiz:generate-auto',
/** 渲染 → 主进程：「还想再练练」——传全部题目的作答轨迹，生成 10 道续练题。 */
quizGenerateMore: 'quiz:generate-more',

interface QuizGenerateRequest {
  kpId: string
  /** 决策记录（§4.6）；主进程逐条校验（条数 ≤ 200、字段白名单投影），不信任渲染层。 */
  context: DecisionTrace[]
}
// 出参：StudyCallResult<QuizPayloadView>——与 readGeneratedQuestions 同形态
//（QuizPayload 投影，结构上无 answer/explanation），渲染层零新解析。
```

- **身份 / 学段注入**：处理器内 `studentId()` + `options.currentGradeLevel?.()`，请求里**没有**这两个字段（与 `QuizBankRequest` / `QuizGeneratedListRequest` 同一条纪律——渲染层能给的类型里就不出现）。
- **载荷校验**：`context` 逐条白名单投影（`readText` 限长），条数上限 200；认不出整条丢掉（与 `projectQuestion` 同一「宁可少不要脏」口径）。
- **通道总数**：新增 2 条 invoke、0 条 push；`npm run check:docs` 的通道计数文档在实现票里同步更新（别写死数字进代码）。

## 6. 边界情况与降级矩阵

| 场景 | 行为 | 依据 |
| --- | --- | --- |
| 无 API Key | auto 静默不生成；按钮点击后一句可读说明 | 「判不了就说不判」既有纪律 |
| 模型生成失败（重试 2 次后） | auto：停止追加、不提示（下次做完内置题的关卡才会再试）；more：按钮旁「这次没出成，再试一次」 | 部分成功批次照常下发 |
| 登记失败（sidecar 不可用 / 后端拒收） | 该批题**不下发**（先登记后下发的铁律），走上一行降级 | F4 |
| 生成中切关卡 | invoke 结果回来时 `activeKpId` 已变 → **丢弃**（请求序号判据，`fetchBank` 的 `bankRequestSeq` 同一手法） | 「迟到的旧响应不写结果」既有纪律 |
| 生成中学生关掉应用 | 已登记的题在库里（复用链路自动带回），未登记的批次自然作废 | 无需处理 |
| 历史生成题 + 本轮追加 > 20（auto 阶段） | 一起截断到 20（最近登记优先） | §4.4 规则 |
| 学生在 20 题内反复重做（restart） | 不再自动触发（`autoFiredKp` 不因 restart 重置） | §4.1 |
| 沙箱演示态 | 两通道都被 `demoBlocked()` 拦截 | 与 `quizGrade` 同判据 |
| 主观题（带 rubric） | 判分照走 409 → LLM 路径；Prompt 生成侧限量 ≤ 1 道 | 既有链路 |

## 10. 风险与开放问题

1. **跨会话轨迹缺失（v1 已知局限）**：`history` 是页面内存态。增强方向：后端加只读端点（`GET /api/quiz/attempt-summary`）聚合 `learning_history` —— 那是一次**契约改动**（contracts.py → OpenAPI → gen:api → typecheck → test 全链），值得单独开票，不塞进本功能。
2. **20 的口径弹性**：需求钉死了 20 / 10 两个数，实现时建议提为具名常量（`AUTO_PHASE_LIMIT = 20`、`MORE_BATCH = 10`）放一处定义，别散落数字。
3. **生成质量**：去重只能靠「已有题干清单进 Prompt」软约束；登记端没有相似度硬校验。若验收时发现重复率明显，再考虑 stem 哈希近似去重（后端小改），本计划不做。
4. **「做完」口径的确认**：本计划采用「全部判分过（不要求全对）」。若产品口径实为「全部答对」，改 `shouldAutoGenerate` 一行判据 + 一条单测即可，结构不受影响——实现前建议找需求方确认一次。
5. **演示驾驶舱（D-093）**：是否给 quizgen 的轮次加 diagnostics 信封（剥正文的长度 / 哈希 / 结论）——演示要展示「个性化出题」时有用，但会把轮次信封机制扩到新链路。本计划不做，记为可选增强。
