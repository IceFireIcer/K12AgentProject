## 0.6 ★ 核心边界：LLM 可见白名单

这是整个方案里**最重要的一条**，比 v2 的「文本正则过滤」强一个量级。

### 0.6.1 为什么是「白名单投影」而不是「过滤敏感词」

| | v2 的做法 | v3 的做法（采纳） |
|---|---|---|
| 机制 | 发给模型前用正则**过滤文本** | 模型只能看到**结构化标签的一个投影** |
| 漏网 | 换个说法就绕过了（正则的宿命） | **不可能漏** —— 不在白名单的字段没有出口 |
| 可审计 | 靠读代码找正则 | 一个常量，**可写守卫** |
| 原始数据 | 原文仍要经过模型 | ★ **原文根本不出网** |

**v2 的致命处**：`sanitizePii` 是**黑名单思路** —— 只能挡「已知要挡的模式」。
「小明，五年级，我在 XX 小学二班」里的「XX 小学二班」未必命中任何正则，
但**那是学生没同意外传的东西**。白名单是**白名单思路** —— 没被显式允许的，一个字节都出不去。

### 0.6.2 存储：物理隔离两张表（迁移 v5）

~~~sql
-- ① 本地身份层：★ 永不过桥（主进程读，不进任何 prompt）
CREATE TABLE identity_local (
  anon_student_id TEXT PRIMARY KEY,   -- 唯一对外标识（模型可见）
  real_name       TEXT,                 -- 模型不可见
  real_grade      TEXT,                 -- 模型不可见（精确年级）
  school          TEXT,                 -- 模型不可见
  class           TEXT,                 -- 模型不可见
  parent_consent  INTEGER NOT NULL DEFAULT 0,
  memory_switch   INTEGER NOT NULL DEFAULT 1,
  -- ★ 五问流程状态：not_started | in_progress | done | skipped
  --   「只在 not_started 时弹」= 结构上保证不再重问（见 §1.8）
  onboarding_state TEXT NOT NULL DEFAULT 'not_started'
);

-- ② 标签层：**只有白名单字段可能出现在这里**
CREATE TABLE profile_tags (
  anon_student_id TEXT NOT NULL,
  key             TEXT NOT NULL,        -- 必须 ∈ LLM_VISIBLE_TAGS
  value           TEXT,
  confidence      REAL,
  source          TEXT,                 -- declared | observed | inferred
  ts              INTEGER,
  PRIMARY KEY (anon_student_id, key)
);
CREATE INDEX idx_tags_key ON profile_tags(key);
~~~

★ **两张表物理隔离**，不是靠一条 WHERE 过滤：
`identity_local` 没有出口函数（代码里不存在「读它再拼 prompt」这条路径），
`profile_tags` 只有白名单守卫。

### 0.6.3 白名单常量（唯一真相）

~~~ts
export const LLM_VISIBLE_TAGS: ReadonlySet<string> = new Set([
  'anon_student_id',
  'grade_band', 'subject', 'course_module', 'current_topic',
  'knowledge_point', 'mastery',
  'error_type', 'zpd_level',
  'explain_style', 'output_length', 'pace', 'practice_type',
  'interest_topic',
  'emotion', 'intensity', 'trigger', 'confidence',
  'tone', 'encouragement_freq', 'challenge_level',
  'scene', 'task_goal',
  'safety_level', 'boundary_topics'
])
~~~

`parent_consent` 与 `memory_switch` **不在白名单里** —— 它们是**闸**不是**信息**：
主进程读它们决定行为，但它们本身不告诉模型。

### 0.6.4 姓名占位：{{student_name}} 机制（采纳你的设计）

我 v2 里曾**不推荐**这个方案（担心模型不照做、漏替换更糟）。你的设计解决了那个顾虑：

~~~
prompt 里写死：称呼这位学生时使用占位符 {{student_name}}
                        ↓
模型输出：「{{student_name}}，我们先把这道题拆成三步」
                        ↓
渲染层替换：「小明，我们先把这道题拆成三步」
~~~

**模型全程不知道「小明」是谁。** 名字只存在于本机两个地方：
`identity_local.real_name` 与渲染层内存。

**敏感词过滤的新位置**：Q5 的回答进 `identity_local.real_name` **之前**要过一遍 ——
命中「我叫…」「XX 学校」「二班」「138…」等模式就**丢弃并回落「同学」**。
过滤后它**从不进标签表**，所以白名单已经保证了它不会出网；过滤只是防止**本机**留下学生没同意识别的信息。
★ 这道闸现在只剩一个职责（守住本地），不再承担出网保护 —— 出网由白名单全权负责。

⚠️ **我保留的那条风险**（v2 也提过，现在仍成立）：模型可能不照做 —— 改叫「这位同学」或干脆不称呼。
**缓解**：prompt 里给死规则 ——「不知道学生想被怎么称呼时，就**不称呼**，不要用任何其他叫法」。
**并加一条守卫**：渲染层替换后仍出现未替换的 `{{...}}` 残留在正文里 ⇒ 测试红。

### 0.6.5 短期情绪必须有 TTL（配合「禁做长期负面情绪档案」）

你的禁做清单里有**「长期负面情绪档案」** —— 这条我原方案没意识到，但它很对：
把一个孩子「上次考试崩了、情绪低落」长期记着，既伤人也可能被用来**操控**他。

⇒ `emotion / intensity / trigger` 三个标签**必须带过期时间**：

~~~
写入时 ts = now
读取时：now - ts > N 轮（建议 3 轮会话或 24 小时，取先到） → 视为不存在
~~~

这不是「优化」，是**红线实现**。要写成一条守卫（§0.6.6 G-E）。

### 0.6.6 守卫清单（把红线变成测试）

| 守卫 | 断言 |
|---|---|
| G-A | `profile_tags.key` 的任何取值 ∈ `LLM_VISIBLE_TAGS` |
| G-B | `identity_local` 的**任何列**都不在白名单里（两张表永不重叠） |
| G-C | prompt 拼装器**只读** `profile_tags`，代码里不存在读 `identity_local` 的路径 |
| G-D | 渲染层替换后正文**无未替换的** `{{` 残留 |
| G-E | `emotion/intensity/trigger` 过期后**读不到** |
| G-F | `memory_switch=0` 时**不写任何标签** |
| G-G | `parent_consent=0` 时**不外发任何画像** |
| G-H | 14 条禁做项各有对应断言（§0.6.7） |
| G-I | `onboarding_state != 'not_started'` 时**绝不弹引导**（新建会话也不弹） |
| G-J | subagent 调用是 **fire-and-forget**：注入一个永不 resolve 的桩，断言 UI 不阻塞 |

### 0.6.7 ★ 14 条禁做清单（**每条都要能测**，否则等于没写）

| # | 禁做 | 可测的守卫形态 |
|---|---|---|
| 1 | 真实身份进模型 | G-B + G-C |
| 2 | 家庭收入 | 标签表**无此 key**；写入端点无此参数 |
| 3 | 父母职业 | 同上 |
| 4 | 消费画像 | 同上 |
| 5 | 广告 ID | 标签表无此 key |
| 6 | 精确位置 | 标签表无此 key |
| 7 | 跨站追踪 | 存储层**无任何第三方标识字段** |
| 8 | 社交关系 | 标签表无此 key |
| 9 | 公开排名 | 任何端点不返回跨学生聚合 |
| 10 | 敏感属性推断 | `source='inferred'` 的 key **只允许**白名单内那 4 个情绪/风格类 |
| 11 | 长期负面情绪档案 | G-E（TTL） |
| 12 | 心理诊断 | `emotion` 的**取值域**是有限枚举（开心/平静/困惑/沮丧/生气），**不是**临床词汇 |
| 13 | 情绪操控 | 守卫：prompt 里**不得**出现「你要开心一点」「别说难过」这类祈使 |
| 14 | 依赖诱导 | 守卫：prompt 里**不得**出现「只有我懂你」「别去问老师」 |

★ 13、14 两条特别值得写成测试 —— 它们防的不是数据泄露，是**产品价值观滑坡**，
而这种滑坡往往是「模型自己写出来的」，靠 code review 抓不住。

## 1. 对话式五问（新架构）

### 1.1 数据流

~~~
① 引导开始：系统 prompt 切到「引导模式」
        │
② Q1 作为一条**普通助手消息**出现在对话流里（学生看得见、UI 照常）
        │
③ 学生在**正常输入框**回答（点选项或自由打字）
        │
④ 主进程在本轮结束时，识别「这条回答属于哪一问」→ 本地收集 (qid, 原文)
        │
⑤ ……Q2~Q5 重复 ……
        │
⑥ 五问收齐 → 本地拼成一段 Q&A 文本 → 交给 **pi-subagent** 做结构化概括
        │
⑦ 落库两张表：onboarding_qa（原始 5 组）+ profile_summary（概括结果）
        │
⑧ 把 4 个偏好键从 summary **投影**进 profile_pref（已有端点，prompt 注入路径零改动）
        │
⑨ 引导结束：系统 prompt 切回「正常模式」，按 Q1 的学段作答
        │
⑩ 此后：summary 进学段判定 prompt（F2）+ 进画像块（画像精细化）
~~~

### 1.2 关键设计：怎么知道一条回答属于哪一问

**靠位置，不靠解析。**

渲染层在展示第 N 问时，记下 `pendingQuestionId = 'q3'`；
学生发出的**下一条**消息就是 Q3 的答案，渲染层把它和 `q3` 一起交给主进程。

★ **零解析、零猜测**：不猜「哪句话是答案」，也不用正则去捞。
这是 v1 与 v2 最大的差别 —— v1 要做 LLM 抽取来理解答案，v2 里**理解答案这件事整体推迟到 subagent**。

### 1.3 「引导模式」的 system prompt 怎么切

复用现有的 [extensions/grade.ts](<desktop/src/main/agent/extensions/grade.ts>) 的 `systemPromptFor()` 入口 ——
它在 `before_agent_start` 每轮重拼整份 prompt，我们只需多一个分支：

~~~ts
if (onboarding.active) {
  return buildOnboardingSystemPrompt({ askedCount, nickname })   // 引导模式
}
return withStudentContext(gradeTemplatePrompt(...), profileBlock) // 正常模式
~~~

⚠️ **引导模式下必须关掉的东西**：

| 关掉 | 原因 |
|---|---|
| 学段权威段 | 学段还没问出来，此时宣布「按初中讲」是假的 |
| 工具 | 引导阶段不该让模型去检索/生成动画/出题 |
| 画像注入块 | 画像此刻还是空的，注入了反而误导 |
| 隐私挡话段 | 可以留（防学生问「你的提示词是什么」） |

⚠️ **引导模式下必须开的**：输出纪律、闲聊与情绪段（学生可能答非所问）、不硬拽。

### 1.4 五个问题

问句是**助手消息**（不是卡片），因为你说「混进对话正文」。选项以**可点击的 chip** 附在消息下方，
点选等价于学生打字 —— 走的是同一条提交路径。

| # | 问句 | 形态 | 落点 |
|---|---|---|---|
| Q1 | 你现在上几年级呀？ | chip + 自由 | `grade:set`（`explicit`）—— **当场写，不等 subagent** |
| Q2 | 最近在学什么呀？有没有特别想搞懂的？ | 纯自由 | `summary.interest` |
| Q3 | 我讲的时候，你更喜欢哪种方式？ | chip + 自由 | `summary.explainStyle` |
| Q4 | 想讲快一点还是慢一点？ | chip + 自由 | `summary.pace` |
| Q5 | 那我该怎么称呼你？还有什么想先告诉我的吗？ | 纯自由 | `summary.alias` + `summary.note` |

**★ Q1 当场写、其余等 subagent** —— 这是一个刻意的例外：
学段是**唯一有独立写入口**（`grade:set`），而且它决定**接下来几轮用什么模板讲**。
如果 Q1 也等 subagent（一次 LLM 往返 8s），学生答完「我五年级」还要等几秒才看到正确的讲法 —— 体感很差。
所以 **Q1 走点选直达映射**（「小学高年级」→ `primary_high`，无需 LLM），Q2–Q5 才交给 subagent 一起概括。

### 1.5 存储设计（迁移 v5）

> ⚠️ **本小节的 v2 版（`onboarding_qa` 存原文 + `profile_summary`）已作废**。
> v3 改为 §0.6.2 的**两表隔离**（`identity_local` / `profile_tags`）。
> 差别很关键：v2 要把原始 Q&A 交给 subagent 理解，v3 **原文不出网**，理解这件事改由**本地规则**做（见 1.6）。

当前最大版本是 v4（`signal_mark`），新迁移是 **v5**。沿用 [migrations.py:281](<server/app/store/migrations.py:281>) 的幂等模板。

**表 1：`onboarding_qa`（原始问答，审计与重跑依据）**

~~~sql
CREATE TABLE IF NOT EXISTS onboarding_qa (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  ts            INTEGER,
  session_id    TEXT,
  question_id   TEXT,     -- q1..q5
  question_text TEXT,     -- 问句（脚本常量，落库便于事后核对口径变更）
  answer_text   TEXT,     -- ★ 学生原话（**这是本次推翻不变量后新增的**）
  answered_at   INTEGER
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_onboarding_q ON onboarding_qa(question_id);
~~~

`UNIQUE` 保证**一問一答、幂等**（重答是覆盖，不是追加）—— 与 `profile_pref` 的 upsert 语义一致。

**表 2：`profile_summary`（subagent 的结构化输出）**

~~~sql
CREATE TABLE IF NOT EXISTS profile_summary (
  student_id   TEXT PRIMARY KEY,
  ts           INTEGER,
  model_id     TEXT,     -- 哪个模型概括的（可追溯）
  summary_json TEXT,     -- 结构化 JSON，见 1.6 的 schema
  raw_len      INTEGER,  -- 输入长度审计
  status       TEXT      -- ok | degraded | failed
);
~~~

**为什么用新表而不是复用 `profile_pref`**：`profile_pref` 是**四个封闭键**（那是刻意设计，
用来在类型层面堵死「模型写掌握度」）。而 subagent 的输出维度**远多于四个**（学习风格、情绪倾向、学科…）。
塞进去会破坏那条封闭性纪律。**两张表，一条投影边**（8️⃣ 步骤），互不污染。

### 1.6 抽取：**本地问完 → 一次性批量发 subagent → 后台跑**

★ 五问**不在当场解析**。本地只负责**收答案**，收齐后**一次性**打包发给 subagent，
subagent 在**后台**做结构化概括 —— 学生**不必等它**。

~~~
本地（同步，不阻塞 UI）
  Q1 答案 ──► 点选直达映射 ──► grade:set（立即生效，学生下一句就按新学段讲）
  Q1~Q5 ────► 收集进内存 + 标记 onboarding_state=in_progress

本地（fire-and-forget，后台）
  五问收齐 ──► PII 遮蔽 ──► 一次性打包 ──► subagent
                                     │
                              （学生此时可以继续正常用程序）
                                     ▼
                              结构化概括（≤8s，超时降级）
                                     │
                                     ▼
                    写 profile_tags + 投影 4 键进 profile_pref
                                     │
                                     ▼
                              onboarding_state=done
~~~

**「后台跑」的三条硬约束**（否则会变成「界面卡住等 AI」）：

| # | 约束 |
|---|---|
| 1 | **绝不 await** —— 用与 [grade.ts](<desktop/src/main/agent/extensions/grade.ts>) 上交同款串行队列 + `flush()` 语义 |
| 2 | **失败不重试到烦人** —— 只自动重试 1 次，仍失败走降级（§1.7） |
| 3 | **退出前要 flush** —— 否则最后一刻的概括会丢（复用 `runtime.dispose()` 里已有的 `gradeExtension.flush()` 位置） |

**学生视角**：答完第 5 问 → 引导页收起 → **立刻可以正常聊天**，
画像在后台十几秒内悄悄补齐；下次提问时模型已经「认识」他了。

#### 发给 subagent 之前：PII 遮蔽（**白名单边界不因为这一次调用而破例**）

这是 v3 白名单架构下**唯一一处原始文本会碰到模型**的地方，必须堵住：

~~~
原始：      「我叫小明，读五年级，在 XX 小学二班，我喜欢恐龙」
遮蔽后：    「我叫 {{real_name}}，读五年级，在 {{school}} {{class}}，我喜欢恐龙」
                                        ↑ ↑
                        学校/班级抹掉；**五年级保留**（它是提取 grade_band 的原料）
~~~

**为什么五年级不遮**：`grade_band` 是白名单字段、教学必需，
而遮掉它 subagent 就没法从自由回答里判学段。**精确年级进了白名单的`grade_band` 之后就不再是隐私问题**。

**subagent 的输出 schema 硬限定**（超出即丢弃整条结果）：

~~~json
{
  "gradeBand": "primary_high",
  "subjects": ["科学"],
  "currentTopic": "恐龙",
  "explainStyle": "生活例子",
  "outputLength": "short",
  "pace": "慢",
  "practiceType": "先看例子",
  "emotion": "平静",
  "intensity": 2,
  "tone": "亲切",
  "note": "",
  "confidence": 0.75
}
~~~

★ **schema 里没有** `realName` / `realGrade` / `school` / `class` 字段 —— 
不是靠 prompt 说「不要输出」，是**类型层面就没有**（同 `PreferenceKey` 封闭词表的纪律）。



v2 说「把 5 组 Q&A 丢给 subagent 概括」。**v3 推翻这一点** —— 因为白名单投影的前提是**原文不出网**。

**MVP 15 个标签全部可以本地抽取，一个 LLM 调用都不需要**：

| 问题 | 抽取方式 | 产出标签 |
|---|---|---|
| Q1 你上几年级 | 点选直达；自由输入走**年级词表**（「五年级」→「小学高年级」） | `grade_band`（+ 本地 `real_grade`） |
| Q2 在学什么 | 点选学科 + **本地关键词表**（复用 `signals.py` 的词表机制） | `subject, current_topic` |
| Q3 怎么讲 | 点选 + 可选本地映射 | `explain_style, output_length, practice_type` |
| Q4 多快 | 点选 | `pace` |
| Q5 称呼 + 备注 | **称呼**：过敏感词过滤后作 `identity_local.real_name`（**不设标签**） | — |
| 贯穿全程 | 判分/答题已有数据 | `knowledge_point, mastery, error_type` |
| 当轮 | `signals.py` 元认知路（已有！） | `emotion, intensity` |
| 安全 | 已有 [safety/guard.py](<desktop/src/main/agent/safety/guard.ts>) | `safety_level` |

★ **注意最后两行**：`emotion/intensity` 和 `error_type` 的**数据源其实早就有**了，
只是从来没被整理成标签。这让 MVP 的成本比 v2 估的低不少。

**subagent 延后到 v2 票**（票 28）：当出现「自由回答里藏着结构化信息」的真实需求时再上，
那时它的输入也应该是**已脱敏的候选标签**，不是原文。


**做什么**：拿 5 组 Q&A，输出一个结构化 JSON。

**要不要真的开 Pi 会话？** 两个选项：

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | 专用 Pi 子会话（`createAgentSession` + 概括 prompt，用完 dispose） | 你要的形态；能给 subagent 挂工具（如查教材学段范围） | 会话生命周期有坑（要先 dispose 旧会话、目录改道、`systemPromptOverride` 必须给） |
| **B** | 复用已有 `lazyComplete` 通道（判学段/自审/动画生成已在用） | 极轻、无会话开销、已有超时与降级模式 | 纯文本任务，不需要工具时 B 够用 |

**我建议 A，但按 B 的纪律来约束它**（必须有超时、必须可降级、必须不阻塞 UI）。
理由：概括质量直接决定画像质量，值得给一个正经 agent；
而 B 的那三条纪律（超时/降级/不阻塞）无论用哪个都必须有。

**subagent 的输出 schema**（照 `grade.ts` 的 `parseProposal` 写法：宽松读、严格校验、脏值丢弃）：

~~~json
{
  "gradeLevel": "primary_high",
  "gradeConfidence": 0.9,
  "explainStyle": "多用生活里的例子",
  "pace": "慢一点，每步说清",
  "interest": "恐龙和太空",
  "subjects": ["数学", "科学"],
  "alias": "小 W",
  "note": "数学容易慌，讲慢点",
  "learningStyle": "visual",
  "styleConfidence": 0.7,
  "frustrationResponse": "needs_encouragement",
  "frustrationConfidence": 0.4
}
~~~

**后三个字段（`learningStyle` / `frustrationResponse`）是 v2 相对 v1 的真正增量** —— 
v1 只能填 4 个键，v2 一上来就有**学习风格**和**受挫响应倾向**的初值。
它们是 L3 推断层的**起点**（带低置信度，可被后续行为观察修正），是 §4 那些功能能提前跑起来的关键。

### 1.7 降级（每一步都要能单独失败而不崩）

| 环节 | 失败时 |
|---|---|
| Q1 点选写入 | 保持冷启动默认（`junior`），界面标「待判定」，继续问 Q2 |
| 收集某一条 | 记`answered=false`，subagent 收到的是残缺 Q&A（它要能只总结有答案的部分） |
| subagent 超时/解析失败 | `status=degraded`，**自动重试 1 次**后仍失败 → Q2–Q5 退化为「只存白名单里点选得到的字段」，引导照常结束 |
| 进程在概括完成前退出 | `flush()` 未等到 → 状态停在 `in_progress`；下次启动时**不重问**（避免烦人），只把已有答案重跑一次概括 |
| 无 API Key | 同上，永远走 degraded；五问 UI 仍完整可用 |
| 4 键投影 | 逐条独立写，某条失败不阻塞其他 |

★ **引导流程在任何降级下都能走完** —— 这是硬要求，
因为它是新用户的前 30 秒，卡在这里的代价最大。

### 1.8 ★ 入口时机：**只在第一次使用弹**，之后永不再问

你明确要求：五问是**首次冷启动**用的，**新建对话时不再出现**。

#### 状态机（存在 `identity_local.onboarding_state`）

~~~
not_started ──► 弹引导 ──► 答第 1 问 ──► in_progress
                                  │
                      答满 5 问 / 主动跳过
                                  ▼
                          done / skipped
                                  │
                    ★ 从此任何新会话都不再触发
~~~

**触发条件只有一条**：`onboarding_state == 'not_started'`。

⚠️ **明确不作为触发依据的**（v2 曾经用、v4 全部推翻）：

| ❌ 不看 | 原因 |
|---|---|
| 画像是否为空 | 学生之后手动改了学段/偏好，画像本来就会「不空」，但**不该重问** |
| `grade.get` 的 source 是否 explicit | 同上 —— 手动定过学段≠需要重问五问 |
| 是不是新会话 | 五问**只跟学生走**，不跟会话走 |
| 装机时间 / localStorage | 本地 DB 里已经有权威状态，不该再有第二份 |

★ **判据从「画像状态」改成「流程状态」** —— 这是本节唯一的实质变化，
它让「不再问」成为**结构上的必然**，而不是靠一堆条件凑出来的巧合。

⚠️ 顺带一个坑：现在 [App.vue:125-138](<desktop/src/renderer/src/App.vue:125>) 的 `onMounted` 是**无条件**执行的，
且全项目**没有任何 first-run 标记位**（无 localStorage / 无 settings 开关）。
所以这个状态字段必须是**新建的**，且要有守卫：「`onboarding_state` 只在 `not_started` 时弹引导」写成测试。


（与 v1 相同，三条都满足才进引导）

1. `profile:read` 返回 404 **或** `preferences` 为空对象；
2. `grade:get` 的 `source !== 'explicit'`（从没手动定过学段）；
3. `onboarding_qa` 为空（**表里已有记录就不重复问**）—— 这一条现在有了天然判据，
   不再需要 v1 里那个「本地已跳过标记」

### 5.3 两条最有想法的展开

#### ① 学段内难度微调（#10）—— 我认为整个画像体系里最值钱的一条

**问题**：学段只有四档，**粒度太粗**。「小学五年级」和「小学五年级但明显偏难」拿到的是同一套 prompt。

**现状的浪费**：为了表达「他比同年级强一点」，系统要付出一次**完整的学段迁移**
（连续 3 轮同向 + 置信度 0.6 + 冷却 5 轮 + 单次最多 1 级）。而很多时候根本不需要迁移。

**做法**：学段**不动**，画像里加一档**学段内微调**：

~~~
同一年级内部：偏易 ← 正常 → 偏难
~~~

它作用在「**怎么讲**」而不是「讲什么」：术语密度、例子的抽象层、先给结论还是先给推导。

**为什么值钱**：把自适应从**离散跳变**（换整套讲法）变成**连续调节**，
既解决粒度问题，又**完全不触碰**已在跑的学段机制。
而且 v2 之后，`profile_summary` 里已经有`learningStyle` 和置信度，
**微调的输入已经现成了** —— 不需要新数据源。

#### ② 受挫敏感度（#6）—— 让情绪机制第一次「因人而异」

**现状**：`moodSection` 对所有学生说同一句「先把情绪接住，再降一级重讲」
（[rules.ts:155](<desktop/src/main/agent/prompts/rules.ts:155>)）。

**但「太难了」至少有三种意思**：

- **求助型** → 你一鼓励他就走神了，正解是**直接给解法**
- **放弃型** → 你直接给答案他就永远学不会，正解是**先肯定再降一级**
- **试探型** → 只是想确认自己是不是太笨了

**三种用一套策略必然对两种错。**

**v2 的进展**：subagent 已经在给 `frustrationResponse` 的初值了（虽然置信度只有 0.4），
**这让票 28（情绪数据化）从「要做个新机制」降级成「接上一个已有的字段」** —— 门槛降了很多。
后续用行为观察修正它：连续受挫后**继续问**（求助型）还是**停止提问**（放弃型）。
信号其实已经在 `signals.py` 的元认知路里，只是现在只用它下调学段、没看反应。

## 7. 风险与明确不做的事

| 不做 | 原因 |
|---|---|
| **不推翻 learning-log 的不入库** | 作用域缩小到五问；旧守卫 G9-7 继续绿（§4.2） |
| 不全量存对话正文 | 无界、每轮都在长、且没必要（正文在 Pi JSONL 里） |
| 不改 `ChatSendRequest` | 它恰好只有 `text`，守卫 G6c 钉死 |
| 不改既有 pydantic 模型 | onboarding 另开契约；`LearningEventRequest` 不动 |
| 不动 `profile_pref` 的四键封闭性 | 新维度进 `profile_summary`，两者用投影连接 |
| L3 推断写 L1 | 类型层面堵死 |
| 自动推断覆盖学生明说 | D-020 反复吃过的教训；L2 与 L3 分开存、分开显示来源 |
| 画像块里放时间戳 | 会毁掉 system prompt 前缀缓存（D-032） |
| 把 subagent 做成阻塞调用 | 概括 8s 超时；必须 fire-and-forget + 降级（§1.7） |

## 8. 还需要你拍板 2 件事

### ① 14 条禁做清单里，哪几条要在 **MVP 就写守卫**？

我建议 **MVP 全写**（14 条断言成本很低，多是「标签表无此 key」这种一行测试），
理由：红线不写测试 = 下次有人「顺手加个字段」就破了。
你也可以只写前 10 条（数据类），把 13、14（价值观类）留到 v2。

### ② `parent_consent=0` 时的默认行为？

（`parent_consent` 已在 MVP 15 里，但默认值的语义要定）

| 选项 | 行为 |
|---|---|
| A | 引导页**先问家长同意**，不同意则只做无记忆的单次对话 |
| B | 默认同意，家长可在设置页关 |
| C | 默认不同意，必须显式开 |

**我建议 A** —— K12 场景下「默认收集」是风险最高的选择，
而且同意这个动作本身可以设计成引导的第 0 步（家长扫码/勾选），不增加学生负担。
