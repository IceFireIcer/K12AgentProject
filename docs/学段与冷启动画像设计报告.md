## 一、先回答你的第二个问题

### 1.1 结论：会发。前 4 轮的学生原话会完整进入第 5 轮 AI 判定的上下文

代码路径是闭合的，一共三步。

**① 每轮开始，原话进缓冲区** —— `desktop/src/main/agent/extensions/grade.ts:1080`

~~~ts
if (clean.trim()) {
  buffer.push({ turn: turnIndex, text: clampTurnText(clean) })
  if (buffer.length > LAYER2_WINDOW_TURNS) buffer = buffer.slice(-LAYER2_WINDOW_TURNS)
}
~~~

注意这是**无条件**的：不看轮次、不看学段、不看是否已判定。第 1 轮就开始 push 了。

**② 判定时整个缓冲区交出去** —— 同文件 `:903`

~~~ts
return await judge({ turns: [...buffer], currentGrade: appliedGrade })
~~~

**③ 拼 prompt 时只做尾部切片** —— 同文件 `:394`

~~~ts
const recent = turns.slice(-LAYER2_WINDOW_TURNS)   // LAYER2_WINDOW_TURNS = 8
~~~

所以在**同一个会话**里，第 5 轮触发 AI 时，模型看到的是：

~~~
1. 电脑怎么认图片呀？
2. 什么是集合
3. 这题怎么做
4. 帮我看看这段代码
5. 函数有什么用
~~~

即**第 1–5 轮全部原话**，带轮次编号、按时间排序。`LAYER2_WINDOW_TURNS = 8`（`:100`），
所以要到会话第 13 轮，第 1–5 轮才会被挤出窗口。

这一点被测试钉死了 —— `desktop/tests/grade-inference.test.ts:530` 的 G4b 用例
连推 5 轮，断言第 5 轮才带 `proposal`、前 4 轮一律不带。

### 1.2 ⚠️ 但有三个「但是」，设计五问之前必须知道

**但是①：缓冲区是「每会话」的，不是「每学生」的。**

`resetWindow()`（`grade.ts:843`）在**换会话**时被调用，清空 `buffer`；
而累计轮次 `serverCumulativeTurns` **不归零**（那是学生级状态，`:707`）。

| 场景 | 累计轮次 | 会话内轮次 | AI 何时出场 | AI 看到什么 |
|---|---|---|---|---|
| 新学生，单会话 | 1→5 | 第 5 轮 | 第 5 轮 | 第 **1–5** 轮 ✅ |
| 老学生，开新会话 | 已 20 | 第 1 轮 | 不出场（证据不足） | — |
| 同上 | 已 20 | 第 2 轮 | 不出场（证据不足） | — |
| 同上 | 已 20 | **第 3 轮** | 第 3 轮 | 只有第 **1–3** 轮 ⚠️ |
| 同上，聊到第 13 轮 | 已 32 | 第 13 轮 | 本窗口已判过，不再判 | — |

`LAYER2_MIN_TURNS = 3`（`:97`）+ `windowHasProposal` 每会话只判一次（`:344`）
⇒ **AI 判定实际是「每会话最多一次，且要等该会话攒够 3 轮」**。

**但是②：AI 看不到前 4 轮规则引擎算出了什么。**

桌面端**只上交了原文和提议，从不上交信号** —— 测试 G4a（`grade-inference.test.ts:521`）
明确断言 `'signals' in body === false`。服务端拿到原文后**自己**再跑一遍
`signals.py` 提取三路读数。

也就是说：规则引擎和 AI 是**读同一段原文的两个独立读者**，不是「规则先判、交给 AI 接力」。
AI 在第 5 轮是**冷启动重读**第 1–5 轮原文，前 4 轮的规则结论对它**完全不可见**。

反直觉但重要的推论：**「前 4 轮本地判定」的结果，在 AI 接手的那一刻被整体丢弃了。**
如果前 4 轮规则已经稳到某个学段、第 5 轮 AI 判成另一个，学生会看到一次「无感但突兀」的跳变。

**但是③：AI 判定的上下文里只有学生的话，没有老师的回答。**

`buildJudgePrompt(turns, currentGrade)`（`:390`）的入参签名只有两个：
学生原话数组 + 当前学段。没有：

- 老师上一轮说了什么（学生是顺着回答问的，还是自己发散的）
- 学生的画像 / 偏好 / 掌握度 / 错题
- 第一层三路信号的读数与方向

所以现在 AI 判学段时，是一个**只知道「这个学生说了哪几句话」**的判断器。

### 1.3 AI 判定的执行细节（供评估成本）

- **模型**：与聊天**同一个模型**（`runtime.ts:1239`），**没有**独立轻量模型
- **参数**：`maxTokens: 1200`、`temperature: 0`、不给工具（`runtime.ts:1232-1237`）
- **超时**：`JUDGE_TIMEOUT_MS = 8_000`（`runtime.ts:428`）
- **降级**：无 Key / `checkAuth` 没过 / 离线探针 → 返回 `null`，扩展标 `no_llm`，
  服务端标 `degraded`，**第一层照常工作**（`runtime.ts:1212-1215`）
- **在途作废**：LLM 判定期间学生手动改学段 → 整条结论丢弃（epoch 机制，`grade.ts:941-964`）

## 二、现状全链路（核查后的事实）

### 2.1 双层结构

~~~
每轮开始 runtime.ts 调 gradeExtension.observeTurn(学生原话)
   |
   +-> 1 交接 pendingGrade（上一轮判定出的学段 -> 本轮生效）
   +-> 2 原文 push 进 buffer（上限 8 轮）
   +-> 3 串行入队 fire-and-forget 上交
          |
          +-> 累计第 5 轮起？且本会话可用轮次 >=3？且本窗口未判过？
          |     -> 是：跑一次 LLM 判定
          |        -> buildJudgePrompt(最近 8 轮原话)
          |        -> {suggestedGrade, confidence, note}
          |
          +-> POST /api/grade/turns/{studentId}
                {turn, text, sessionId, proposal?, layer2Status}
                    |
                    +-> server/app/grade/signals.py 三路规则信号（不调 LLM）
                           -> grade_signals 表
                              |
                              +-> server/app/grade/rules.py decide()
                                     llm_decides = proposal is not None and cumulative >= 5
                                     decided_by  = 'llm' if llm_decides else 'rules'
                                     四条硬约束 + 原子写库
                                     -> student.grade_level + grade_history
                                          |
                                          +-> 下一轮 before_agent_start 拼 system prompt（学生无感）
~~~

### 2.2 关键常量（双端一致，有跨语言断言钉住）

| 常量 | 值 | 位置 | 作用 |
|---|---|---|---|
| `LLM_DECIDES_FROM_TURN` | **5** | `rules.py:122` / `grade.ts:94` | AI 接手门槛（**累计**轮次，跨会话） |
| `LAYER2_FIRST_TURN` / `LAYER2_RETRY_TURN` | 3 / 5 | `rules.py:105-106` | 旧口径，D-066 后仅描述规则决策期 |
| `LAYER2_MIN_TURNS` | 3 | `grade.ts:97` | AI 判定所需最少可用轮次（**每会话**） |
| `LAYER2_WINDOW_TURNS` | 8 | `grade.ts:100` | 进 AI 上下文的最近轮次上限 |
| `MAX_TURN_CHARS` | 2000 | `grade.ts:103` | 单轮原话截断 |
| `CONFIDENCE_THRESHOLD` | 0.6 | `rules.py:82` | 置信度门槛 |
| `SIGNALS_REQUIRED_FOR_CHANGE` | 3 | `rules.py:85` | 连续同向轮次 |
| `COOLDOWN_TURNS` | 5 | `rules.py:88` | 自动调整后冷却 |
| `MANUAL_COOLDOWN_TURNS` | 10 | `rules.py:95` | 手动指定后冷却 |
| `MAX_STEP_LEVELS` | 1 | `rules.py:98` | 单次最多动一级 |

**「学段长时间不太会改动」是有设计依据的**：置信度 0.6 + 连续 3 轮同向 + 冷却 5 轮 + 单次最多 1 级，
四道闸门叠着；手动指定后冷却翻倍到 10 轮。

### 2.3 冷启动默认值（**这是最大的浪费**）

| 位置 | 值 |
|---|---|
| `server/app/routes/students.py:73` `DEFAULT_COLD_START_GRADE` | `junior`（初中） |
| `desktop/src/main/agent/prompts/grade.ts:31` `DEFAULT_GRADE_LEVEL` | `junior`（须逐字一致，有测试钉住） |
| `server/app/routes/students.py` `DEFAULT_STUDENT_NICKNAME` | `同学` |

新学生进程序，**不管问什么，前 5 轮一律用初中模板作答**。
一个小学三年级的学生，前 5 轮会收到「严谨逻辑推导、术语准确」的初中讲法 —— 这 5 轮基本是废的。

## 三、现有画像 / 个性化 / 情绪机制的真实状态

### 3.1 画像注入块（已存在，但冷启动是空的）

`prompts/student-context.ts` 是唯一拼装器，块标题：

> ## 该学生当前情况（系统自动汇总，不要逐条念给学生听）   （`:65`）

正文由 `extensions/profile.ts:296` 的 `renderProfileText` 渲染，**固定顺序**（为前缀缓存）：

1. 【学习画像 · 内部数据，不要整段念给学生听】学生：{id}（{学段}）
2. - 学生当前在看：{章节}（只是背景，不必刻意围绕它）—— 有章节才出现
3. **掌握度** —— 冷启动时是：「还没有掌握度记录：这是这个学生的第一次对话，
   先用一个具体的小例子建立概念，别急着上难度。」
4. **学习偏好** —— `key=value；key=value`（冷启动时**整行不出现**）
5. **推荐** —— ⚠️ **不是依赖图**。2026-09-22 用户裁决 **D-074** 已把「依赖图后继」
   与「冷启动入口知识点」两段**整个删掉**，现在是两段式（`routes/profile.py:273`）：
   - `review`：**待重练** —— 练过但掌握度 < 0.5，按分数升序（「连续答错 → 下一轮更可能再考它」）
   - `random`：**本学段里随机挑没学过的**（`rng` 用「学生 id + 当天日期」做种子，
     所以同一天稳定、跨天轮换）
   `graph` / `cold_start` 仍留在 `RecommendationSource` 词表里，但**不再被产出**
6. **错题摘要** —— 知识点名 + 错次（无错题不出现）

**块必须逐字节稳定（D-032）**：不放时间、偏好按 `PREFERENCE_ORDER` 固定顺序、掌握度平局按 kpId 排。
这对五问设计是**约束也是机会**：五问是一次性写入，写完块变一次 —— 那一次缓存失效是「应该付的」。

### 3.2 偏好词表（**封闭，只有 4 个键**）

`server/app/contracts.py:108`：

~~~python
PreferenceKey = Literal["interest", "explain_style", "pace", "note"]
~~~

- 表结构**只有两列**（`store/migrations.py:248`）：
  `key TEXT PRIMARY KEY` / `value TEXT` —— 没有 id、没有时间戳、没有学段列
- `profile_pref.key` 是主键 ⇒ 总条数天然 ≤ 4，**不需要清理逻辑**
- 写入口是幂等 upsert（`store/learning.py:609`：`ON CONFLICT(key) DO UPDATE`）
  ⇒ 同一个键提交两次，库里状态完全相同（这是选 PUT 而非 POST 的理由）
- 封闭词表的用意是**在类型层面**堵死「模型写掌握度/学段」（D-020 的教训）
- 单值上限 `PREFERENCE_VALUE_MAX_CHARS = 40`（`contracts.py:116`），因为它会进**每一轮**的 system prompt
- 渲染顺序钉死：`PREFERENCE_ORDER = ['interest', 'explain_style', 'pace', 'note']`（`profile.ts:227`）

### 3.3 ⚠️ 偏好写入**没有渲染进程入口**

现有的**唯一**偏好写入口是模型的 `remember_preference` Tool
（`profile.ts:705` → `preferencesPath` → `PUT /api/profile/{id}/preferences`）。

渲染进程侧的 IPC 通道只有 `profile:read` 和 `profile:recommendation`（`channels.ts:312-314`），
**没有 preference 写通道**。

⇒ 五问要写偏好，**必须新增一条 IPC invoke 通道**。这是本次设计唯一必须动通道契约的地方。

### 3.4 ⚠️ 「情绪化回答机制」目前是**静态 prompt**，不是数据驱动的

`prompts/rules.ts:150` 的 `moodSection(name)` 是四份模板**共用**的一节，内容固定：

- 跑题 / 闲聊：可以接一两句，再顺势聊回学习
- 受挫（「太难了」「我不想学了」）：**先把情绪接住**，再降一级重讲
- 情绪低落：不追问细节，建议找老师或家长
- 「你是谁」：用智团团的语气直接回答
- 语气纪律：不恐吓、不贬低、不绝对化

**这一节对每个学生一字不差**。系统**不知道**这个学生：

- 怕被嘲笑还是不怕
- 受挫时需要先被肯定，还是直接给解法
- 用什么名字称呼他最自然（模型侧自称固定「智团团」，**学生叫什么名字根本没进 prompt**）

这正是「情绪化回答机制」的最大缺口 —— 它有策略，**没有画像**。

### 3.5 ⚠️ 发现的一个现存缺陷：推荐的来源标签缺 `random`

这是探查时顺带抓到的，**它会直接影响票 26**（把画像摘要注入 AI 判定 prompt），所以必须记一笔。

`RECOMMENDATION_SOURCE_LABELS`（`extensions/profile.ts:190`）只有四个键：

~~~ts
{
  review:     '优先重练（这个知识点还没练熟）',
  graph:      '依赖图后继（前置已掌握）',      // ← D-074 后不再产出
  cold_start: '学习路线起点（新学生）',        // ← D-074 后不再产出
  empty:      '暂无（知识库或学习记录不足）'
}
~~~

**没有** `random` —— 而它恰恰是 D-074 之后的**主来源**。
于是 `renderRecommendationLines` 的兜底（`profile.ts:403`）会把它渲染成：

> - 推荐下一步（**依赖图推荐**）：…

**服务端明明是随机挑的，注入给模型的却是「依赖图推荐」** —— 模型会据此以为
「这是有学习路线顺序的下一个知识点」，从而把学生往一条并不存在的路径上带。

**修法**（很小，建议并入票 26）：给标签表补一条
`random: '还没学过的，可以随便挑一个开始'`，
顺带把两个已不产出的 `graph` / `cold_start` 删掉（留着它们，
下一个读代码的人还会以为依赖图在决定推荐）。

### 3.6 已有的开场白机制（与五问的位置关系）

`GET /api/profile/{id}/opening`（`routes/profile.py:632`）已经有一套开场白：

- `_OPENING_VARIANTS` 有 4 个变体（`profile.py:417`），
  统一以「你好，我是智团团。」开头（`:462`）
- 只点**第一个**知识点（`:436`，因为动作按钮只指向一个 kp_id）
- `rng` 用**会话 id** 做种子 ⇒ 同一条会话每次开场白一致（D-072）
- 知识库不可用时 `source='empty'`、`text=''` ⇒ **一句招呼都没有**

★ 顺带印证了 3.4 那条结论：变体里的 `{name}` 填的是**「智团团」**（模型自称），
**学生的名字从来没有进过 prompt**。

**与五问的关系**：五问应该在开场白**之前**完成 —— 开场白是「第一次会话的第一句话」，
如果那时画像还空着，它推荐的那句「我们从 X 开始吧」就是纯随机 + 空画像。
五问跑完之后开场白才有依据。
### 3.7 身份与账号系统（现状）

- 渲染层 `stores/student.ts` 只持有**单个**当前学生，默认昵称「同学」
- 身份单点在**主进程**：`resolveActiveStudentId()`（`main/ipc/handlers.ts:356`）=
  环境变量 `K12_STUDENT_ID`（须过白名单 `/^[A-Za-z0-9_-]{1,64}$/`）→ 否则回落 `student_001`；
  渲染进程**递不了也改不了**（`channels.ts:300-307` 把这条写死了）
- **没有**学生切换器、**没有**账号 / 登录体系（`login` / `account` 全树 0 命中；`auth` 的命中全是 API Key）
  三档视角**明确不是权限系统**（`Settings.vue:18-19`：「这不是权限系统…开关是可绕过的」）
- ★ 切学生目前**只能改环境变量并重启**（`handlers.ts:349-352`：「『选学生』的 UI 属票 20/21」）
  ⇒ **五问这一票不需要动身份解析**，切账号那一票才动
- `PAGES`（`stores/ui.ts:123-181`）共 9 页：问问智团团 / 动画讲解 / 编程环境 / 闯关挑战 /
  学习记录 / 设置 / 参考资料库 / 知识图谱 / 运行透视
- **没有任何 onboarding / 欢迎页 / 引导流程**
- `StudentCreateRequest`（`contracts.py:506`）只接受 `nickname` + `gradeLevel`，
  **无更新端点** ⇒ 昵称建号后改不了

## 四、「五问」设计

### 4.1 设计原则（先把红线划死）

1. **不复用聊天通道**。学段 / 偏好 / 昵称**一律不进 `ChatSendRequest`**（它恰好只有 `text`，
   守卫 G6c 钉死）。走独立的 `grade:set` 与新增的 `profile:preference` 通道。
2. **不新增第二套真相**。五问的答案**必须落进已有存储**：`grade:set` →
   `POST /api/grade/override`；偏好 → `PUT /api/profile/{id}/preferences`。
   不新建「问卷表」再让它和 `profile_pref` 双向同步。
3. **答案不一次性拼成一个 prompt**。五问是 5 次独立写入，**逐条落库**。
   写失败只影响那一条，不回滚已写的（幂等 upsert 语义天然支持重试）。
4. **每一问都能跳过**。跳过 = 不写；全跳过 = 现状不变。
5. **是学生面内容**。措辞要过 `student-view-discipline` 守卫 + `npm run ux:student`。

### 4.2 五个问题

#### Q1 · 你现在上几年级？

| 项 | 值 |
|---|---|
| 选项 | 小学低年级 / 小学高年级 / 初中 / 高中 / 先按默认来 |
| 落点 | `grade:set` → `POST /api/grade/override` |
| 副作用 | `grade_history(source="explicit")`、**立即生效**、冷却 10 轮、清空 `current_chapter` |
| 进 prompt | ✅ 学段模板（`prompts/grade.ts` 查表）+ 画像块第 1 行 |

**为什么第一个问这个**：它单独解决了「前 5 轮讲法可能全错」这个最大浪费。
学生自报年级是**最强的单条学段证据** —— 现有 LLM 判定口径第 3 条就明确写了
「学生自己说出的年级算证据」（D-073）。

⚠️ 写 `explicit` 会进 10 轮冷却，期间规则引擎不自动调。这是**对的**：
学生自己说的比信号更权威，也省掉「刚答完就跳走」的尴尬。

#### Q2 · 你更喜欢我怎么讲？（讲解方式）

| 项 | 值 |
|---|---|
| 选项 | 一步一步讲清楚 / 先讲道理再举例 / 多用生活里的例子 / 直接给结论和步骤 / 想看着做题边讲边练 |
| 落点 | `profile_pref.key = 'explain_style'` |
| 进 prompt | ✅ 画像块「学习偏好」行 |

选项**故意对齐**模型侧 `remember_preference` 的描述词（`profile.ts:105`），
保证两条写路径同口径。

#### Q3 · 你想讲多快？（节奏）

| 项 | 值 |
|---|---|
| 选项 | 慢一点，每步都说清楚 / 正常 / 快一点，直接讲重点 / 我想多练几遍 |
| 落点 | `profile_pref.key = 'pace'` |
| 进 prompt | ✅ |

在选项里预留「慢一点」，与 `moodSection` 的受挫策略形成呼应：
学生说「太难了」时，画像里已经写着「想慢一点」，模型接住情绪后有据可依地降速，
而不是临场发挥。

#### Q4 · 你最近对什么最感兴趣？

| 项 | 值 |
|---|---|
| 形式 | 选项（动物 / 太空 / 游戏 / 动手做东西 / 讲故事…）+「自己写一句」（≤40 字） |
| 落点 | `profile_pref.key = 'interest'` |
| 进 prompt | ✅ |

**边界**：这一问**不**自动写 `current_chapter`。章节写入口只有 `chapter:set`
（学生显式选择，且必须命中当前学段真实章标题，否则 422）。
「兴趣」是软提示，「章节」是教材定位，**混为一谈会让 Prompt 里出现一本不存在的教材**。

#### Q5 · 还有什么想让我先知道的？

| 项 | 值 |
|---|---|
| 形式 | 自由输入，≤40 字 |
| 引导语 | 「比如：怎么称呼你 / 你哪里容易卡住 / 你不喜欢什么样的讲法」 |
| 落点 | `profile_pref.key = 'note'` |
| 进 prompt | ✅ |

**这一问是给「情绪化机制」留的口子**。举例回答：

- 「叫我小 W」「别叫我小朋友」→ 自称与称呼
- 「我数学特别容易慌」→ 受挫时的接法（画像给了模型这个先验）
- 「我不喜欢一次讲太多」→ 与 Q3 互为印证

⚠️ 值长度上限 40 字是**硬约束**（`PREFERENCE_VALUE_MAX_CHARS`），前端必须同步限制，否则 422。

### 4.3 五个问题的落点汇总

| # | 问题 | 写入通道 | 服务端端点 | 存储 | 进 prompt |
|---|---|---|---|---|---|
| Q1 | 几年级 | `grade:set`（**已存在**） | `POST /api/grade/override` | `student.grade_level` + `grade_history` | ✅ |
| Q2 | 怎么讲 | `profile:preference`（**需新增**） | `PUT /api/profile/{id}/preferences` | `profile_pref.explain_style` | ✅ |
| Q3 | 多快 | 同上 | 同上 | `profile_pref.pace` | ✅ |
| Q4 | 兴趣 | 同上 | 同上 | `profile_pref.interest` | ✅ |
| Q5 | 备注 | 同上 | 同上 | `profile_pref.note` | ✅ |

**一个值得强调的性质**：五问**一个字段都不用新增**。
4 个偏好键全部落在已有的 `PreferenceKey` 封闭词表内（`contracts.py:108`），
学段走已有通道。这意味着**不需要改 pydantic 契约、不需要 `gen:api`、
不需要改 `StudentProfile` 形状** —— 唯一的新增是**一条 IPC 通道**。

### 4.4 五问之后系统会变成什么样

以「小学五年级 + 多用生活里的例子 + 慢一点 + 喜欢太空 + 叫我小 W」为例，
第 1 轮的 system prompt 就已经是：

~~~
[小学高年级模板]（童话 -> 通俗、比喻、短句）
...
## 该学生当前情况（系统自动汇总，不要逐条念给学生听）
【学习画像 · 内部数据，不要整段念给学生听】学生：student_001（小学高年级）
- 掌握度：还没有掌握度记录：这是这个学生的第一次对话，先用一个具体的小例子建立概念，别急着上难度。
- 学习偏好：explain_style=多用生活里的例子；interest=喜欢太空；note=叫我小W；pace=慢一点，每步说清
- 推荐下一步（依赖图推荐）：分数与导数（sr-functions-sr） 掌握度 0.00   ← 这个标签有问题，见 3.6
## 学段（你手动指定的，以此段为准）
...
~~~

对比现状：同一时刻画像块里**只有**一行
「还没有掌握度记录：这是这个学生的第一次对话…」。

**这就是「前 5 轮裸奔」和「第 1 轮就准确」的差别。**

## 五、连带建议（不在五问范围内，但与它强相关）

### 5.1 让 AI 判定看到画像（低成本、高收益）

你问的「前 4 轮判定结果要不要给 AI」—— 我的建议**不是**把规则结论塞进去（那是第二套真相），
而是**把画像摘要塞进去**，因为：

- 画像块 `renderStudentContextBlock` **本来就是逐字节稳定的纯函数**，直接复用零成本
- 它对规则引擎同样有意义：Q1 写的是 `explicit`，10 轮冷却内 AI 本来就不该改
- ⚠️ 塞进 `buildJudgePrompt` 时放在**最后**（AI 判定的 prompt 本就每轮不同，没有缓存压力）

改造点很小：`Layer2Judge` 入参（`grade.ts:220-223`）从 `{turns, currentGrade}`
扩成 `{turns, currentGrade, persona?}`，`runtime.ts:1272` 的 `useJudge` 里补一次读取
（每轮 `fetchStudentContext` 已经有数据，可复用）。

### 5.2 buffer 跨会话（谨慎，建议先不动）

「AI 判定上下文跨会话累积」听起来对，但有两个反作用：
① `windowHasProposal` 的窗口语义会变复杂；
② 跨会话的提问可能跨主题，混在一起反而干扰判读。

**建议**：先做 5.1，不动 buffer。真要跨会话，应单独一票。

### 5.3 昵称不能改（已知缺口）

`StudentCreateRequest` 只在建号时收 `nickname`，**没有更新端点**。
将来「切学生账号」落地时，昵称修改要一并考虑 —— 但那属于账号系统那一票。

### 25 号票的关键实现约束（写给执行者）

- **无 vue-router**：新增页面必须登记进 `stores/ui.ts` 的 `PAGES`（D-040）
- **通道总数只认 `npm run check:docs`**，不要在别处写死数字
- 新 IPC 通道是 **invoke**，**不进 `PUSH_CHANNELS`**
- 渲染进程**永远不直连 sidecar**，偏好写入走 `bridge/client.ts`（`apiFetch`）
- 前端**必须**限制 Q4 / Q5 输入 ≤40 字（`PREFERENCE_VALUE_MAX_CHARS`），否则 422
- ⚠️ 偏好值**禁止换行**：`PreferenceUpdateRequest._clean_value`（`contracts.py:563`）
  **拒绝**（不是压成单行）`\n \r \v \f`。前端单行输入框天然满足，但**别做「多行」控件**
- 五问是**学生面**内容，措辞要过 `student-view-discipline.test.ts` + `npm run ux:student`
- ⚠️ **触发时机的 404 细节（已逐条核实，别想当然）**：
  - 服务端 `GET /api/profile/{id}` 对**从未建档**的学生返回 **404**
    （`routes/profile.py:529`，理由是「空画像会让学生以为『我没学过任何东西』」）；
  - 渲染侧的 `profile:read` 通道**没有**兜底，直接透传（`handlers-data.ts:242`）⇒ **它会 404**；
  - 但 `student:get` 通道**有**兜底：404 时改调 `/recommendation` 建行再读一次
    （`handlers-data.ts:227-236`），而它在首屏 `loadInitialData()` 里就会跑。
  ⇒ **实际时序**：`student:get` 先把行建出来，之后 `profile:read` 拿到的是
  **200 + `preferences: {}`**，不是 404。所以判据的主形态是「偏好为空」，404 只是兜底分支。
  正确判据（三条都满足才弹）：
  1. `profile:read` 返回 404 **或**返回的 `preferences` 为空对象；
  2. `grade:get` 的 `source !== 'explicit'`（从没手动定过学段）；
  3. 本次装机还没有「已跳过五问」的本地标记 —— 建议新建 per-student 的**本地**标记，
     **不要**塞进 `profile_pref`（那是模型的写入口，塞 UI 状态会污染那条纪律）

- ⚠️⚠️ **将来做账号系统时的一个已知地雷**（P3-4，已实测过）：建学生**绝不能**用 `POST /api/students`。
  那个端点的 id 是服务端扫描目录分配的「下一个空号」，于是「列一遍 → 没有就建」是个**读-改-写竞态**：
  启动时两个并发调用各建一个，现场表现是**同一秒出现 `students/student_001` 与 `students/student_002`**，
  学生数据分裂在两个目录里。正确做法是`按已知 id 走会自动建行的端点`（`/recommendation` 等），
  幂等、并发安全（`handlers-data.ts:199-210` 的注释把这段坑写得很完整，动手前先读）。
- 收尾顺序：**先写 Q1（学段立即生效）再写偏好**，反过来会出现「按初中讲了两秒才切成小学」
