## P-001 裸 `python` / `py` 指向已删除的路径（`0x80070003`）

- **现象**：本机直接敲 `python` 或 `py` 报 `0x80070003`（系统找不到指定路径）；但 `uv run` 一切正常。
- **根因**：注册表里残留着**已删除的** `D:\Code\PythonEvm` 的安装项，`python`/`py` 启动器按注册表解析解释器路径，解析到一个不存在的目录。**真实解释器**是 `D:\Code\PythonEvm312\python.exe`（3.12.7）。这不是 PATH 顺序问题，改 PATH 无效。
- **解决**：全程用 **uv 锁定 Python 3.12**，所有命令与文档只写 `uv run`；**不要去改注册表**。
- **防呆**：任何脚本 / 文档 / npm script 都不提供裸 `python` 命令；`uv.lock` 与 `.python-version` 必须提交（锁定依赖与解释器）。
- **报告用法**：风险表 #2 的「已诊断 → 已解决」全过程。可讲的点是**排错方向**：报错码看起来像权限问题（0x80070003 常与安装权限相关），实际是注册表残留指向死路径——先确认「解释器到底在哪」再动手修环境。

## P-002 依赖版本升级会直接装不上（peer 冲突）

- **现象**：升 `vite` 到 8 或把 TypeScript 升到 7，`npm install` 直接失败。
- **根因**：peer 依赖区间卡死——`electron-vite@5` 的 peer **只接受 `vite ^5|^6|^7`**；`openapi-typescript` 的 peer 是 `typescript ^5.x`。这不是 bug，是上游的兼容声明，升上去就是明确的「不支持」。
- **解决**：锁死当前组合：`electron ^44.4.1 + electron-vite ^5 + vite ^7.3 + vue ^3.5.42 + pinia ^4 + TS ^5.9 + typebox`（**已实测可零冲突解析，398 包**）。
- **防呆**：**升级任一版本前先跑一次 `npm install --dry-run`**；`AGENTS.md` §4 已把「不要升 vite 8 / 不要升 TS 7」写成硬约束。
- **★ 重建期实测补强（票 01，2026-09-16）**：`npm install --dry-run` **不能直接当冲突检查用**——
  npm 11 在 dry-run 模式下**仍会执行 `postinstall`**，而此时依赖尚未落盘，`electron-builder` 还不存在，
  命令会以 `'electron-builder' 不是内部或外部命令` 退出。**这是 npm 的行为，不是依赖冲突，极易误判。**
  纯净的冲突检查写法：`npm install --dry-run --ignore-scripts`（实测 398 包、0 冲突、exit 0）。
- **报告用法**：设计合理性——「版本矩阵是实测出来的，不是抄的」；并在报告里给出**反例清单**（vite 8 / TS 7），说明锁定版本是工程决策而非保守。

## P-003 PyInstaller 打包后中文变 GBK（spawn 传 env 无效）

- **现象**：源码运行态一切正常；**打包产物**里 `sys.flags.utf8_mode=0`、`sys.stdout.encoding='gbk'`，界面/日志中文乱码。
- **根因**：**PyInstaller 的 bootloader 设置了 `Py_IgnoreEnvironmentFlag`**，Python 启动时忽略全部环境变量——于是源码态有效的 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8` / `PYTHONUNBUFFERED=1` 在打包态**全部失效**，Windows 上 stdio 回落到 ANSI 代码页（GBK）。**同一个 env 在两种运行态行为不同**，这就是「开发好好的、打包就乱码」的错觉来源。
- **解决**：**必须在 Python 层 reconfigure** —— `server/app/console.py` 的 `install_utf8_stdio()`，在 `main.py` **最早期**调用；源码运行态仍可继续传 env；所有文件读写显式 `encoding="utf-8"`。
- **防呆**：打包冒烟脚本断言打包产物的 stdio 编码为 utf-8；文档里把「只靠 env 解决打包态乱码」标成死路。
- **报告用法**：**报告第 7 章的主力条目**。可直接引用结论：「不要试图只靠 env 解决打包态乱码——那条路是死的，会白花半天」。这是典型的「平台工具链与直觉相反」的难题，验收方爱听。

## P-004 PyInstaller 必须 `--onedir` + `--collect-all`（打包成功 ≠ 运行可用）

- **现象**：打包过程无报错，**运行期**才炸——找不到 sqlite_vec 的 `.dll`、找不到 fastembed 的模型文件、`resources/` 下的题库与模板缺失。
- **根因**：PyInstaller 只静态分析 Python 的 import 图，看不到两类资源：① 通过 `load_extension` **运行期动态加载**的 C 扩展 `.dll`（sqlite-vec 不经过 import，是打开连接后才加载）；② 通过**文件路径读取**的数据文件（ONNX 模型、敏感词库、题库、动画模板）。此外 `--onefile` 每次启动都要解压到临时目录，**冷启动可达 10s+**，演示体感极差。
- **解决**：`--onedir`（**不用 onefile**）+ `--collect-all sqlite_vec --collect-all fastembed` + `--add-data "resources;resources"`；统一走 `scripts/build_server.py`，不要手敲 pyinstaller 命令。
- **防呆**：**每加一个原生/数据依赖就重打一次包验证**，别攒到最后（风险表 #1 / 业务陷阱清单第 8 节第 1 条）。
- **报告用法**：报告第 7 章「难题与解决方案」；论证「打包不是一次性的动作，而是每加一个依赖就要重验的持续动作」。

## P-005 PyInstaller spec 里 `collect_all` 的返回值必须前置收集

- **现象**：spec 文件里写 `a.datas += collect_all(...)` 时报 `ValueError: not enough values to unpack`。
- **根因**：`collect_all()` 返回的是 **2 元组**（datas, binaries）；而 `Analysis(...)` 执行完之后 `a.datas` 已经是**3 元组**结构。在事后 `+=` 时，Python 用 2 元组的解包规则去处理 3 元组，直接解包失败。**顺序错了，语义也就错了**。
- **解决**：必须在 `Analysis(...)` **之前**调用 `collect_all()` 并作为参数传入（接受 2 元组）。
- **防呆**：spec 里保持「先 collect、后 Analysis」的固定写法，加注释写明为什么不能事后追加。
- **报告用法**：报告第 7 章的短条目——「构建脚本的元编程陷阱」；配合 P-003 一起讲「打包链路上的坑都不在业务代码里」。

## P-006 sidecar 握手的 stdout 通道被污染 + Node 侧分片

- **现象**：Electron 拿不到 sidecar 的端口号，启动卡住或握手 JSON 解析失败。
- **根因**：两个独立原因叠加。① **stdout 被日志污染**——Python 侧任何一行 `print` / 库自带的 console handler 打到 stdout，就会混进握手通道；② **Node 的 `data` 事件会分片**——管道不保证按行投递，握手 JSON 完全可能被切成半行到达，`JSON.parse` 半行必然抛错。
- **解决**：**stdout 只许输出这一行 JSON**（`{"event":"ready","port":N,"pid":P}`），**日志全部走 stderr**；Node 侧收到数据后**缓冲到 `\n` 再 parse**，**非 JSON 行只记日志、绝不当错误**（否则任何一条第三方库的噪音都会把启动流程打成失败）。
- **防呆**：sidecar 启动自检——stdout 的第一行必须是合法 JSON；日志库初始化时显式指定 stream=stderr。
- **报告用法**：设计合理性——「进程边界上的协议要按流处理，不能按消息处理」；也是「`stdout` 是协议通道，不是日志通道」这条工程常识的具体案例。

## P-007 sidecar 进程泄漏、端口占用与重打包 `WinError 5`

- **现象**：① 关闭应用后仍有残留进程占着端口，二次启动失败；② 重新打包时 PyInstaller 清理 `dist/` 报 `WinError 5`（拒绝访问）。
- **根因**：① Windows **不会级联杀子进程**，主进程退出后 Python sidecar 变成孤儿；② 上一次验证留下的 sidecar 进程**仍持有产物里的 `.pyd` / `.dll`**，文件句柄没释放，PyInstaller 删不掉。
- **解决**：App `before-quit` 时用 `taskkill /PID <pid> /T /F` **杀进程树**；崩溃时非正常退出则自动重启一次；**打包前先 taskkill 自愈**。
  两条实测补充细节（都会造成难查的行为）：③ **`restart()` 不能复用 `stop()`** —— `stop()` 会把 `shuttingDown` 置为 true，之后崩溃就不再自动重启；④ **`onExit()` 会先把 `this.child` 置为 null**，必须在置空前先取 pid，否则杀不掉。
- **防呆**：打包脚本开头先做一次自愈式 taskkill；验收标准含「关闭后无孤儿进程」。
- **★ 重建期实测补强（票 01，2026-09-16，带真实数字）**：
  ① 手动 `kill` 掉 `uv run python -m app.main` 后，**端口 8756 仍处于 LISTENING**——
  `uv` 是父进程、python 是孙进程，`kill` 只终止了父进程，**孙进程活成孤儿**。这直接证明 `/T` 不是可选优化。
  ② 紧接着启动 Electron，其 sidecar 绑定 8756 失败并 **exit code=3**，界面显示「启动失败：sidecar 进程意外退出」。
  ③ **PID 取错对象是真问题**：当时 UI 显示的「进程 PID」是 **4508**（`uv` 包装器），
  而真正监听端口的 python 是 **44156**（孙进程）。**dev 态绝不能拿 `child.pid` 去杀**——
  这就是「必须用握手自报的 python pid」这条设计的实测依据。
  ④ 附带确认：**失败路径是对的**——没有白屏，给出可读中文错误，符合执行文档 §7.4 第 3 条。
- **报告用法**：报告第 7 章「难题与解决方案」——生命周期管理里的**状态机细节**；④ 那条尤其适合讲「异步回调里的字段被提前置空」这类隐蔽 bug；
  ③ 那条适合讲「看似微小的进程模型差异（wrapper 进程）如何让清理逻辑静默失效」。

## P-008 CORS 中间件顺序造成的「假故障」（★ 新架构下整类消失）

- **现象**：浏览器侧报 `TypeError: Failed to fetch`，看起来像网络问题；但服务端日志显示请求其实到了、返回的是 401。
- **根因**：**Starlette 的中间件是洋葱结构，最后 `add_middleware` 的在最外层**。CORS 若不是最后加，就在鉴权中间件**内层**；鉴权提前 `return` 的 401 响应**不经过 CORS 层**，缺少 `Access-Control-Allow-Origin`，浏览器因跨源校验失败而把 401 **伪装成 `TypeError: Failed to fetch`** —— 真实原因（401 鉴权失败）被完全掩盖，排查方向被带偏到网络层。
- **解决**（当时与现在都适用的修法）：**CORS 必须最后 `add_middleware`**；v3 保留一段最小显式来源的 CORS 作纵深防御（**禁止 `*`**，执行文档 §6.3），这条顺序纪律在部署时仍然生效。
- **★ 新架构下这类故障已不存在**：本项目把「渲染进程 ↔ 主进程」的传输定为 IPC（从零实现即 IPC，D-007），且**渲染进程不再直连 sidecar**（D-008，主进程是唯一的 HTTP 客户端）——浏览器里**根本不再发生对 sidecar 的跨源请求**，这一类故障连同它的排查成本一起被设计掉了。
- **防呆**：架构守卫一律**正向断言**（执行文档 §6.4）——断言「聊天事件流必须经 preload 白名单 IPC 通道送达」；同时保留唯一一条**负向禁止**：渲染进程不得直连 sidecar 的 HTTP 端点（这条才是本 CORS 教训在 v3 的真正落点）。
- **报告用法**：**这是「一个设计改动消掉一整类 bug」的最佳报告故事**——不是把 bug 修好了，而是让 bug 无处产生。放在报告第 7 章，同时支撑设计合理性 25%。

## P-009 日志脱敏过滤器抹掉占位符，把日志系统自己打崩

- **现象**：脱敏功能上线后，日志里出现 `TypeError: not all arguments converted during string formatting`，而且抛错位置在**业务日志调用点**，看起来像业务代码 bug。
- **根因**：`logging` 的 `record.msg` 是**格式串**，参数单独存在 `record.args` 里。过滤器无脑把 `record.msg` 擦成 `***` 之后，`record.args` 还留着；`record.getMessage()` 执行 `msg % args` 时占位符数量对不上，直接抛 TypeError。**脱敏器把日志系统本身弄崩了**。
- **解决**：脱敏过滤器**必须保留 `%s` / `%(name)s` 占位符**，只替换参数里的敏感值。
- **防呆**：过滤器加单测（带参数的日志记录仍能正常格式化）；v2 追加第二道防线——用 Pi 的 `before_provider_request` / `before_provider_headers` **在 provider 边界统一脱敏审计**（比在各处散点脱敏可靠）。
- **报告用法**：合规（「LLM 与嵌入模型不得明文写入日志」这条约束）的实现细节；可讲「脱敏最容易伤到自己」，以及为什么把脱敏落在**一个收口点**（provider 边界）而不是散点。

## P-010 sqlite-vec 的加载序列（顺序固定，且必须收尾）

- **现象**：扩展没加载成功 → 查询直接报错；或忘记关回，进程带着可加载任意扩展的能力继续跑。
- **根因**：SQLite 默认**禁止加载扩展**，必须显式打开；而 `sqlite_vec.load(conn)` 依赖这个开关已经打开。顺序错了就加载不上，收尾忘了就留下安全隐患。
- **解决**：固定三步——`conn.enable_load_extension(True)` → `sqlite_vec.load(conn)` → **立刻** `conn.enable_load_extension(False)`。加载失败必须能回退 FTS5 / numpy 暴力余弦（数千 chunk 暴力余弦毫秒级，可接受，见 D-013）。PyInstaller 打包须 `--collect-all sqlite_vec`，否则运行期找不到 `.dll`（见 P-004）。
- **防呆**：加载封装成单一函数（唯一的调用点），加载失败走降级分支而不是抛到上层。
- **报告用法**：创新性 + 用户体验（降级链可现场演示）；配合 D-013 讲「四级降级链为什么必须留在 Python 侧」。

## P-011 FTS5 中文分词必须 `tokenize='trigram'`

- **现象**：中文关键词检索**一条都命中不了**，但英文/数字能命中。
- **根因**：FTS5 的默认分词器（`unicode61`）按空格与标点切词、**不认识中文**——中文没有词间空格，整句会被当成一个（或极少数）token，任何查询词都匹配不上。这不是「效果差」，是**完全不可用**。
- **解决**：建表时显式指定 `tokenize='trigram'`（三字滑窗），中文即可用。
- **防呆**：FTS5 必须作为降级链的第 3 级**实际跑通并现场演示**（把模型目录改名 → 自动降级 FTS5 仍能检索），不能只写不验。
- **报告用法**：报告第 7 章的短条目；讲「为什么降级链的兜底层必须选一个**永不失败**的实现（FTS5 内置于 SQLite）」。

## P-012 `chunk_vec` 与 `chunk` 行号错位（检索结果张冠李戴）

- **现象**：检索**不报错**，但返回的文本和查询意图毫无关系——像是「别人的答案」。
- **根因**：`chunk_vec` 是 `vec0` 虚表，它的 rowid 由自身写入顺序决定；如果写入时没有显式对齐 `chunk.rowid`（两张表的 rowid 各自生成），KNN 返回的 rowid 拿去 `chunk` 表查出来的就是**另一条文本**。只要有一张表插过、删过、或写入顺序不同，就会错位——**而且是静默的**。
- **解决**：写入时**显式使用 `chunk.rowid`**；建索引脚本必须**幂等（先清表再写）**，否则调试时数据翻倍。
- **防呆**：建完索引做一次 rowid 对齐断言：`chunk` 行数 == 两表 rowid 能 join 上的行数。
- **报告用法**：报告第 7 章——「静默错误比报错更难查」；也是「向量表与内容表必须共享同一个主键锚点」这条设计的由来。

## P-013 embedding BLOB 的端序必须显式小端（`dtype='<f4'`）

- **现象**：向量维度对、行数对、查询不报错，但相似度**毫无意义**，检索结果随机。
- **根因**：向量以 BLOB 存库时，字节的排列顺序由**写入端**的 dtype 决定，而读取端（sqlite-vec / numpy）按某个固定约定解释。若写入端依赖「本机序」默认值，一旦写入端与读取端平台不同（大端机上 `=` 即 `>f4`），同一段字节会被按另一种端序还原成完全不同的浮点数——**维度没错、行数没错，所以没有任何报错**。
- **解决**：存 `Float32Array` 字节时**显式写 `dtype='<f4'`**，两端约定唯一。
- **防呆**：写库与读库走同一个序列化/反序列化函数（只此一处），并加一个「写入后读回，值相等」的往返断言。
- **报告用法**：报告第 7 章——「跨语言数据交换里，协议不止是字段名，还包括字节序」；可与 P-012 合并讲「沉默的向量层错误」。

## P-014 依赖图递归 CTE：深度上限、方向语义、悬空引用

- **现象**：① 递归 CTE 查询**挂死/耗尽**；② 推荐出的下一步是「更基础的内容」而不是后继；③ 部分节点**静默不参与**推荐与检索扩展。
- **根因**：① 递归 CTE **没有天然的终止条件**，元数据误标出的环（A→B→A）会让它无限展开，SQLite 没有通用递归深度保护；② `from` / `to` 的语义没有统一约定，写反了方向就整体反向；③ `to_kp_id` 在 `kp` 表里不存在（悬空）时若被**静默跳过**，依赖链就悄悄断了——推荐路径缺一环，没有任何日志。
- **解决**：① **`depth` 上限必须加**（`WHERE p.depth < 10`），并在导入阶段用 **DFS 检测环**（有环要报出**具体路径**）；② `from→to` 语义**全项目一致**（**`from` 是前置、`to` 是后继**）并写进注释；③ 悬空 `to_kp_id` **报错而非静默跳过**；④ 检索扩展只作补充上下文且**要有数量上限**（别把 top-k 挤满）。
- **防呆**：导入脚本做外键存在性校验 + 环检测有输出；依赖扩展数量上限写成常量。
- **报告用法**：教育适配性 20%——依赖图**双用途**（推荐路径规划 + 检索上下文扩展）是创新点，这条讲的是「双用途共用一张图时必须先把图本身的完整性守住」。

## P-015 掌握度 `mastery_delta` 必须限幅

- **现象**：学生答对一道题，掌握度直接从 0 跳到 1；之后推荐难度与闯关解锁立刻失真。
- **根因**：`mastery` 是 0–1 的累计值，而单次答题的增量如果不设上限，**一次观测就能决定终态**——这既不符合教育测量常识，也会让「连对 3 题」这类规则失效。
- **解决**：`mastery_delta` **限幅**（如 ±0.2）。
- **防呆**：限幅逻辑写在写库的唯一路径上（不是各调用点自己夹），并加单测断言越界输入被裁剪。
- **报告用法**：教育适配性 20%——「个性化闭环里，单次反馈不能决定长期状态」；这句话在汇报时比参数值本身更有说服力。

## P-016 LLM provider 的 BaseURL 形式差异（`/v1` 有无都能通，改一下就翻车）

- **现象**：默认值能跑通；用户按自己的习惯改了一下 BaseURL（加或删 `/v1`），保存后**连不上了**，且现场看不出原因。
- **根因**：Pi 内置 DeepSeek provider 的 baseUrl 是 `https://api.deepseek.com`（**无 `/v1`**），而前端默认值历史上写的是 `https://api.deepseek.com/v1`。**两者都能连通**（OpenAI 兼容路径的行为差异），于是「谁对」在代码里没有唯一答案；一旦用户改动、而系统只做保存不做验证，问题就会延后到真正请求时才暴露。
- **解决**：默认填 `https://api.deepseek.com/v1`（OpenAI 兼容习惯）并在校验器里明确约定；**保存时必须做一次真实连通性探测**（`GET /models` 或发一条 1-token 请求），把失败原因回显到设置页（新增 `POST /api/settings/probe`）。供应商名称 / BaseURL / APIKey / ModelID 四项自填是**需求硬性要求**，必须保留。
- **防呆**：设置页保存路径**必须经过 probe**，不允许「只存不验」。
- **报告用法**：用户体验 15% + 演示现场防翻车；讲「默认值正确 ≠ 用户改完仍正确」，以及为什么把连通性探测放进保存动作。

## P-017 动画资源的鉴权方式与 iframe 能力冲突（`X-Auth-Token` 用不上）

- **现象**：给 `/resources/animation/*` 加上 `X-Auth-Token` 鉴权后，iframe 里的动画**加载不出来**。
- **根因**：**`<iframe src>` 是浏览器原生导航，无法携带自定义 header**（自定义 header 只适用于可控的 fetch/XHR）。鉴权方案与沙箱能力直接冲突——而如果因此改成无鉴权公开路由，本机任意进程都能读学生数据，违背数据隔离要求。
- **解决**：改用**一次性 nonce**（主进程生成，绑定 `student_id` + `kp_id` + 有效期，拼进 URL query），Python 校验 nonce 后返回 HTML，并设 `Cache-Control: no-store`；路由按学生分目录 `/resources/animation/{student_id}/{kp_id}`。**不允许把该路由做成无鉴权的公开路由。**
- **防呆**：验收明确写「不允许无鉴权公开路由」；nonce 有效期与绑定字段写进契约。
- **报告用法**：设计合理性 25% + 合规——「安全边界不能因为沙箱的限制而放弃，要换一种等价的凭据形式」。

## P-018 动画模板内联 CDN / postMessage 不校验来源 / 进度回调高频

- **现象**：① 演示现场**断网即白屏**（动画卡片一片空白）；② 同时开两张动画卡片时**串台**（A 卡片的播放指令打到了 B 上）；③ 动画播放中界面卡顿。
- **根因**：① `sandbox="allow-scripts"` 的 iframe **没有网络访问能力**（正是沙箱的目的），任何外部 CDN 引用都必然 404；② `postMessage` 是**广播式**的，多个 iframe 实例都会收到消息，不校验来源就无法区分「这条消息是谁的」；③ 高频 `postMessage` 会阻塞渲染。
- **解决**：动画库**必须内联进 HTML 字符串**（本地读取后注入，不用 `<script src>`）；所有消息**带 `payload_id` 校验来源**；进度回调**节流到 ~10Hz**；重试次数**硬上限 3**（否则死循环烧 API 额度）；页面 5s 内无 `ready` 判定超时。
- **防呆**：模板入库前做一次「无外链」检查；`payload_id` 校验写进 RPC 封装的唯一出入口。
- **报告用法**：多模态交互质量 25%（动画能现场演示不翻车）+ 报告第 7 章「难题与解决方案」（沙箱带来的能力约束）。

## P-019 Pyodide：体积大/加载慢、必须可中断、Monaco 需要 worker 配置

- **现象**：① 应用启动慢；② 断网演示时编程环境不可用；③ 学生写出无限循环，**整个界面卡死**；④ 生产构建报错。
- **根因**：① Pyodide 运行时体积大，随应用启动一起加载是纯浪费；② **任何 CDN 引用都会在断网演示时翻车**（本项目全程离线可用是卖点）；③ 主线程执行学生代码即阻塞渲染，**必须有中断手段**（Pyodide 需用 `setInterruptBuffer` 配合 Worker 才能实现）；④ Monaco 依赖独立的 web worker，vite 不配置 worker 打包规则时开发态能跑、**生产构建才报错**。
- **解决**：Pyodide **本地自托管 + 懒加载**（进编程卡片才加载），**必须在独立 Worker 里**跑并加**超时中断**；Monaco 配好 vite worker；预置 `numpy`。
- **防呆**：CI/构建脚本里跑一次生产构建（不要只在 dev 态验证）；Worker 中断路径做一次实测（写 `while True` 验证可中断）。
- **报告用法**：多模态交互质量 25% + 设计合理性（沙箱三重隔离，D-010）；「学生代码绝不接触 sidecar」是安全隔离设计，报告要讲。

## P-020 `node --test` 直接跑 .ts 时不能用 TS parameter property

- **现象**：`node --test` 跑 TypeScript 测试文件报 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`。
- **根因**：Node 的「类型擦除」模式**只做类型删除，不生成任何代码**；而 `constructor(private readonly x)` 这种 parameter property 要求编译器**同时生成字段声明与赋值语句**——超出擦除能力，只能报错。
- **解决**：写成**显式字段 + 构造函数赋值**（两行，功能完全等价）。
- **防呆**：把这条写进编码约定；测试文件用纯擦除友好的语法子集。
- **报告用法**：报告第 7 章的短条目——「工具链的支持边界要摸清，不能按印象写」。

## P-021 UI 验收不要靠截图（截图会截到别的窗口）

- **现象**：验收截图里出现的是**别的应用窗口**；不同 DPI 下同一界面截出来不一样。
- **根因**：本机截图受**前台窗口与 DPI 缩放**影响——截的是屏幕而不是「你要的那个窗口」，且窗口未前置时截到的内容完全无关。用它做验收等于没验收。
- **解决**：用 **CDP 读真实 DOM 做断言**（元素文本、状态、可见性），验收结论以 DOM 为准；`K12_DEBUG_PORT` **默认关闭**，勿让分发包带调试入口。
- **防呆**：验收脚本走 CDP；报告用的**展示性截图**必须确认窗口正确前置后**当场核对**。
- **报告用法**：报告第 8 章「测试与验收」——「可自动化的验收不靠眼睛」；顺带说明为什么调试入口默认关闭（安全）。

## P-022 弱网 / API 不可用必须有优雅降级

- **现象**：DeepSeek 不可用或额度耗尽时，对话直接断掉，界面没有可读反馈。
- **根因**：把「云端 API 总是可用」当成默认前提。这是**外部依赖**，不稳定与限流都是常态，且演示现场的网络条件不由自己控制。
- **解决**：UI 必须给出**优雅降级提示**（`error.degraded`），而不是崩溃或静默无响应；供应商可自填切换（见 P-016）；检索侧有四级降级链（D-013）保证断网仍能出内容。
- **防呆**：演示前必做**断网演练**（确认降级提示生效）。
- **报告用法**：用户体验 15% + 报告第 7 章；汇报预设「网络断了怎么办」的标准答案。

## P-023 `.gitignore` 的模式锚定坑（90MB 模型险些入库）

- **现象**：`server/resources/models/` 下的 90MB 模型差点被提交进 git 仓库。
- **根因**：**含中间斜杠的 gitignore pattern 会被锚定到仓库根**。写 `resources/models/` 只会匹配仓库根下的同名路径，**匹配不到 `server/resources/models/`**；必须写成 `**/resources/models/`。
- **解决**：改用 `**/resources/models/`。（此坑**已实际踩到**，不是理论风险。）
- **防呆**：**推送前必做**——确认无 `*.sqlite`（含未成年人学习记录隐私）、`**/resources/models/`、`.venv/`、`*.onnx` 被暂存；不要提交 `config.json` / `.env`（含 API Key）、`logs/`、`server/_data*/`。
- **报告用法**：合规 + 仓库纪律；「凭直觉写的忽略规则可能是无效的，且失效时不会有任何提示」。

## P-024 ★ Pi 的 `esbuild` 原生依赖导致 Electron 打包失败（v2 头号风险）

- **现象**：打包后的应用**跑不起来**，报 `Cannot find package 'esbuild'`；Pi `0.85.0` 在 Electron 里因 `esbuild` **直接崩溃**。Pi 官方 issue **#9286** 正是「在 Electron 里嵌入 SDK」时踩到这个点。
- **根因**：**Pi 包没有 `./sdk` 子路径，只能从包根导入**；而包根会 evaluate CLI 的 `main.js`，从而拖入 `@earendil-works/chord` → **`esbuild`（约 10MB 的原生二进制）**。原生二进制**不能待在 asar 归档里**（进程无法从 asar 内直接加载/执行它），asarUnpack 未覆盖到它就必然加载失败。**导入图的副作用在开发态看不出来，只有打包后才暴露**。
- **解决**：**锁 `^0.85.1`**（0.85.0 的崩溃已修）；`asarUnpack` 白名单 + 按架构分发 + 签名；**D3 第一天就做 `npm run build:unpack` 冒烟**，并把「打包产物里 Pi 能否加载、`esbuild` 是否被正确解包」写进验收标准（v2 新增最高风险项）。**Plan B = 改用 Pi RPC 模式**（`pi --mode rpc` 作子进程，不 import SDK），必须在 D3 当天决定，不能拖到 D14。
- **防呆**：`build:unpack` 冒烟作为 D3 的关卡动作；风险表 #15 的决策截止日就是 D3。
- **报告用法**：**v2 必记素材第 1 类「Pi 迁移的真实代价与解决过程」**，汇报预设第 1 问的必备补充——**主动讲代价比被问出来更可信**。

## P-025 Pi 的 `session_end` 事件不存在（写它会静默失效）

- **现象**：`pi.on("session_end", ...)` 写了但**完全不生效**——没有报错、没有回调、没有日志。
- **根因**：该事件名**在 Pi 全包 grep 0 命中**，是凭印象臆造的 API。事件名写错不报错，只是永远不触发。
- **解决**：会话终态用 **`session_shutdown`**；一轮结束用 **`agent_end` / `agent_settled`**。学习记录 Extension 挂在 `tool_execution_end` / `agent_end` 上。
- **防呆**：Pi 共 **34 个原生事件**，写 hook 前先在包内 grep 一遍事件名。
- **报告用法**：报告第 7 章的短条目——「第三方 SDK 的隐式契约：写错名字不会报错，只会静默失效」；也解释了为什么主流程要留可观测的轨迹（D-014）。

## P-026 `tool_execution_end` 是只读通知，不能改结果、不能回写状态

- **现象**：想在 `tool_execution_end` 里改 Tool 的返回结果、或回写重试计数，**改不动**。
- **根因**：该事件是**通知**语义（通知外部「这个 Tool 执行完了」），不是中间件钩子，事件里没有回写结果的通道。
- **解决**：**动画的重试逻辑必须写在 Tool 的 `execute()` 内部**，不能指望事件回写；重试计数用 Extension 内的 `Map<toolCallId, n>`（同一轮内有效），**不要再放 State**（原 LangGraph 的 `retry_count` 放 State 的做法作废）。
- **防呆**：Extension 模板里把「重试与降级」明确放在 `execute()` 内；`Map` 的清理时机（轮次结束）写清楚。
- **报告用法**：设计合理性——「在哪里能改状态、在哪里只能观察」是扩展机制的边界知识；对应 D-003 的容错链路落点。

## P-027 `before_agent_start` 能替换 systemPrompt，且多扩展是链式叠加

- **现象**：以为 hook 只能读；多个扩展都改 systemPrompt 时**互相覆盖**。
- **根因**：不了解 hook 的返回值语义——**`before_agent_start` 可以返回 `{ systemPrompt }` 替换本轮的 system prompt**，且多个扩展是**链式叠加**的（后注册的扩展能看到前者的结果）。
- **解决**：把**学段注入**落在这里（每轮按当前学段替换语气与深度，**不需要重建会话**）。同族语义要一起记牢：`input` 可返回 `{action: "continue" | "transform" | "handled"}`；`tool_call` 可返回 `{block, reason, terminate}` **并原地改 `event.input`** —— **这是 Tool 级安全阀的位置**。
- **防呆**：四学段 prompt 模板集中放 `desktop/src/main/agent/prompts/`；多个扩展改动 systemPrompt 时的叠加顺序要在代码注释里说明。
- **报告用法**：教育适配性 20%（学段语气逐轮微调）+ 设计合理性（「LLM 自由选能力、约束在代码层」的分层）。

## P-028 Pi 的 SDK 入口名不能臆造（写错就是编译/运行错误）

- **现象**：按印象写 `createAgent` / `PiAgent` / `registerExtension`，都不存在。
- **根因**：Pi 的 SDK 入口与扩展形态有固定契约，凭「一般 SDK 的样子」猜必然猜偏。
- **解决**：真实存在的是 **`createAgentSession` / `AgentSession` / `AgentSessionRuntime` / `ModelRuntime` / `SessionManager` / `DefaultResourceLoader` / `defineTool`**；**不存在 `createAgent` / `PiAgent`**。Extension 的形态是**导出默认工厂** `(pi: ExtensionAPI) => { pi.on(...); pi.registerTool(...) }`，**不存在 `registerExtension`，也不是插件清单**；加载器是 **jiti**（免编译直跑 TS）。
- **防呆**：动手前先 grep 包内导出；把「存在 / 不存在」两组名字并排写进 Extension 模板注释。
- **报告用法**：报告第 7 章——与 P-025 / P-026 一起构成「上手第三方 Agent SDK 的真实成本」，P-024 讲打包代价、这三条讲**接口语义代价**。

## P-029 默认 system prompt 会泄漏宿主安装路径（issue #6308）

- **现象**：模型收到的 system prompt 里**带着宿主应用的安装路径**。
- **根因**：Pi 官方 issue **#6308**——SDK 嵌入时，默认 system prompt 会把宿主应用的安装路径带出去。这是 SDK 的默认行为，不设就默认发生。
- **解决**：**必须设 `systemPromptOverride`**（经 `DefaultResourceLoader`），用本项目自己的四学段 prompt 模板覆盖。否则既违反「禁止暴露内部实现」的 prompt 规则，也是**信息泄漏**。
- **防呆**：验收清单 v2 新增一条——「System Prompt 不含本机安装路径」。
- **报告用法**：合规 + 用户体验；可讲「SDK 的默认行为在嵌入式场景下未必可接受，必须显式覆盖」。

## P-030 Pi 会话默认落 `~/.pi/agent/`，不改道就跨学生混放

- **现象**：一个学生的对话与另一个学生**混在同一目录**——对 K12 未成年人数据是**合规硬伤**。
- **根因**：Pi 默认把会话写到 **`~/.pi/agent/sessions/--<cwd>--/`**，也就是「宿主用户的全局 Pi 配置目录」，与应用自己的数据目录无关；不放 `agentDir` 就不会按学生分目录，**同一台机器上所有学生共用同一个路径**。
- **解决**：**显式改道** —— `DefaultResourceLoader({ agentDir })` 或 `settings.sessionDir` 指向 `students/<id>/pi-agent/`；`ModelRuntime.create({ authPath, modelsPath })` 同样指向本应用自己的目录，**不得读写用户的 `~/.pi/agent`**。
- **防呆**：**必须加自动化断言**——检测 `students/<id>/` 之外是否出现本应用的 `.jsonl`（D4 产出）；验收清单对应「会话文件落在 `students/<id>/pi-agent/`，未污染 `~/.pi/agent/`」。
- **报告用法**：合规（数据隔离）+ 设计合理性；对应风险表 #18，也是 D-012「三处存储分离」的落地细节。

## P-031 Pi 是纯 TypeScript、无 Python 绑定；RPC 模式不能用 `readline`

- **现象**：① 想在 Python 侧直接接 Pi，发现没有绑定；② RPC 模式下用 Python 的 `readline` 读返回，**一条 JSON 被切成好几段**，逐行 parse 全部失败。
- **根因**：① Pi 是**纯 TypeScript，无 Python 绑定**；唯一的 Python 集成路径是 RPC 模式。② `readline()` / `str.splitlines()` 按 **Unicode 行边界**切分（包含 U+2028 LINE SEPARATOR、U+2029、U+0085 等），而 **JSON 载荷内部（中文文本、转义序列）完全可能包含这些字符**——「按 LF 分隔」与「按 Unicode 行分隔」是两种语义，混用即出错。
- **解决**：RPC 模式用 `subprocess.Popen(["pi","--mode","rpc"])` + **手动按 LF 切分并缓冲**（与 P-006 处理 sidecar 握手是同一套纪律）。**本项目首选仍是在 Electron 主进程内 import SDK**，RPC 只是 Plan B（D-004）。
- **防呆**：任何跨进程 JSONL 协议都只允许「自己缓冲 + 按 `\n` 切」，禁止用语言内置的按行迭代器。
- **报告用法**：报告第 7 章——「协议边界的切分规则必须自己定义，不能借用语言默认的行语义」；这条与 P-006 合起来是一条完整的经验。

## P-033 Pi 与 UI 同在主进程：Tool 必须自己兜异常，`dispose()` 必须在 `before-quit`

- **现象**：① 某个 Tool 抛异常，**UI 和 Agent 一起崩**；② 退出应用后 JSONL 会话文件**写到一半**（半写/损坏）。
- **根因**：**Pi 的 Extension 与 Agent 同在主进程，且拥有完整系统权限**——主进程崩溃会同时带走 UI 与 Agent，一个 Tool 的未捕获异常就是「全盘皆崩」。退出路径上若没有显式收尾，会话文件的写入不会优雅结束。
- **解决**：**每个 Tool 的 `execute()` 必须自己兜异常**（返回可读错误而非抛出）；**`session.dispose()` 必须在 `before-quit` 调用**。
- **防呆**：Extension 模板统一带 try/catch 外壳；`before-quit` 的清理清单（杀 sidecar 进程树 + `session.dispose()`）写进同一处。
- **报告用法**：设计合理性——「进程内嵌 Agent 的代价：异常传播范围被放大」，与 P-024 一起构成「Pi 迁移代价」的完整叙述。

## P-034 Pi 的 `engines.node >= 22.19` 与 Electron 内置 Node 不是一回事（已解除）

- **现象**：Pi `0.85.1` 声明 `engines.node >= 22.19.0`，一度以为 Electron 不满足，准备把 Pi 降到 `0.74.2`。
- **根因**：**`engines` 是按「系统 Node」的口径写的**，而 **Electron 自带自己的 Node 运行时**，两者不是同一个东西、不能直接对照。**Electron 44.4.1 内置 Node 24.21.0**（Chrome 152，本机实测命令 `ELECTRON_RUN_AS_NODE=1 electron -v`），远高于 22.19。
- **解决**：**不需要为 `engines` 降 Pi，也不要主动降 Electron**；D3 只需确认实际安装的 Electron ≥ 44。只有当有人**主动把 Electron 降到 ≤33**（内置 Node 20.x）时才需要退路 `0.74.2`（`legacy-node20`，要求 Node >= 20.6）。
- **防呆**：D3 清单第 1 步固定跑 `npm view @earendil-works/pi-coding-agent version engines` + `npm ls electron`，**别在这一步纠结**。
- **报告用法**：风险表 #16 从「致命」到「已解除」的全过程。可讲的点：**声明式的版本约束与实际运行环境不是一回事**——先用实测把不确定项变成确定项，再决定要不要动手改技术栈。

## P-035 `subprocess(text=True)` 在 UTF-8 模式下**静默**吞掉 GBK 输出

- **现象**：验证脚本里调 `netstat -ano` 解析「哪个进程占着端口」，**命令返回码 0、看起来一切正常，但解析结果永远是空**——`pid_owning_port()` 恒返回 `None`，断言一直失败却看不出哪里错。
- **根因**：两个约定撞在一起——
  ① Windows 自带工具（`netstat` / `taskkill`）按**系统代码页**输出（本机 GBK），表头是中文；
  ② 进程处于 UTF-8 模式（`PYTHONUTF8=1`，本项目全程设着），于是 `text=True` 会拿 **UTF-8 去解 GBK 字节**。
  `subprocess` 的解码发生在**读取线程**里，线程抛 `UnicodeDecodeError` 后**直接死掉**，
  而 `communicate()` 拿到的是一个空缓冲区 —— **不报错、不抛异常、返回空字符串**。
  这是典型的「静默失败」：最坏的一种 bug，因为它伪装成「命令跑成功了，只是没有结果」。
- **解决**：**不要用 `text=True`**。显式收字节再自己解：
  `subprocess.run(cmd, capture_output=True)` → `.stdout.decode("utf-8", errors="replace")`。
  用 `errors="replace"` 而不是硬编码 GBK：非 ASCII 字节变成替换符，而我们真正要解析的
  **ASCII 字段（端口、pid、LISTENING）位置不受影响**，且不依赖本机代码页。
- **防呆**：项目里所有对系统工具的调用都收敛到 `smoke_api._run_capturing_bytes()` 一个函数，
  并在函数 docstring 里写明原因。**新增对 `netstat` / `taskkill` / `wmic` 的调用一律走它。**
- **报告用法**：报告第 7 章「难题与解决方案」——**静默失败比显式报错危险得多**。
  这条尤其适合讲「为什么断言要写得足够具体」：正是那条「握手 pid 必须等于占端口的 pid」
  的断言，把一个看起来通过了的环节暴露了出来。如果当时写的是「能取到 pid 就算过」，这个 bug 会一路带到最后。

## P-036 跨进程边界时，「你 spawn 出来的 pid」往往不是「真正干活的 pid」

- **现象**：要杀掉 sidecar 时，拿 `Popen` / `child.pid` 去杀 —— **杀掉了，但端口没释放**，
  下一次启动直接绑定失败。
- **根因**：中间隔着**包装器进程**。本机实测到两层：
  ① 开发态 Electron spawn 的是 `uv run python -m app.main`：`Popen` 拿到的是 **`uv` 的 pid**，
  真正监听端口的是它的 **python 孙进程**（实测 `Popen` 报 46964，握手自报 44740）；
  ② 连 venv 的 `python.exe` 本身也是个 **redirector**：`Popen` 报 37432，进程内 `os.getpid()` 是 39792。
  杀掉包装器不会级联到子进程，孤儿就继续占着端口。
- **解决**：**只以被管理进程「自报」的身份为准** —— 即握手里的 `pid`。
  Electron 侧两条都杀（自报 pid 优先，`child.pid` 兜底），且必须 `taskkill /PID <pid> /T /F`
  （`/T` 才是杀进程树）。
- **防呆**：`smoke_api.py` / `build_server.py` 的断言**不是**「握手 pid == Popen 的 pid」（那本身就是错的假设），
  而是「**握手 pid == 真正监听该端口的进程**」（用 `netstat` 反查）。这个断言在本机抓到了上面的全部现象。
- **报告用法**：报告第 7 章 + 架构章节。这是「**跨进程边界的身份问题**」的一个干净案例：
  在单进程思维里 pid 是唯一的，一旦引入包装器/重定向器就不再成立。
  也正好解释了为什么 sidecar 协议要把 `pid` 放进握手 —— 那不是冗余字段。

## P-037 学段全自动之后，两个「原本无伤大雅」的假设变成了硬约束（**边界审查，非现场故障**）

> **背景**：2026-09-16 学段设计翻转为**完全自动推断、自动生效**（见 D-020；D-009「显式选择 + 建议条」已废止）。
> 翻转时对推断链路做了一遍边界审查（移除人工出口 ⇒ 规则的每条边界都成了终审），挑出下面两处。
> **如实说明：这两条是审查结论，不是线上/现场踩到的故障** —— 记在这里是因为它们**只在"无人工出口"这一前提下才成立**，
> 换个设计（比如 D-009 的建议条）就会被人工纠正顺手掩盖过去。

- **两处假设**：① 「冷启动时写一条 `grade_history`」很容易被当成"一次学段变更"，从而让冷却期在**前 5 轮**一直挡住调整；
  ② 「方向一致性要连续 3 个同向证据」的计数单位很容易被写成**信号条数** —— 而四类信号在一轮里可能同时触发（词汇 + 深度 + 元认知），
  于是**一次提问就凑够"3 个信号"**。
- **根因**：
  ① 冷启动默认值（小学高年级）**必须留一条轨迹**（否则报告里看不出学生从哪起步），但它**不是一次变更**；
  只要 `from_level` 落成任何非 NULL 的值，冷却期计算就会把它读成"刚改过"；
  ② 「一轮」与「一条信号」不是一回事：轮次才是学生的自然单位，信号只是它的证据。
- **解决**：① 基线写 `from_level = NULL`，冷却期只认「`from_level IS NOT NULL AND from_level <> to_level`」的最近一行；
  ② **先按轮聚合成一个「轮次读数」再计数** —— 信号写入时在 `raw` 里带**轮次锚点**（`t<n>|`），判定前按轮归并、方向取和、强度取平均。
- **防呆**：两条都落单测（`server/tests/test_grade.py`）：① 冷启动后第 1–5 轮不得被判为冷却期；
  ② 同一轮塞 4 条同向信号 → 仍不改学段（`streak = 1`）。阈值全部是 `server/app/grade/rules.py` 里的**具名常量**，
  桌面端 `extensions/grade.ts` 用同组数值并由测试**反向读 `.py`** 做一致性断言，防止两边各改一半。
- **报告用法**：报告第 6 章（学段自适应）+ 第 7 章（难题与解决）。这是「**取消人工出口会让哪些隐含假设变成硬约束**」的实例：
  有人工兜底时，规则的边界错误还能被用户手动纠正；一旦全自动，**规则的每一处边界都是终审**。与 D-020 的「主动讲代价」叙事配套使用。

## P-038 扩展「注册成功」但钩子从未触发 —— 被自家控制流挡住的静默失败

- **现象**：学段推断扩展在启动日志里明确显示
  `[agent] 主 Agent 扩展：已注册 6 个扩展（quiz, profile, grade, …）`，
  但学段永远停在默认值：数据库 `grade_signals` **0 行**、日志里**一行 `[grade]` 都没有**。
  最刺眼的是**没有任何报错** —— 看起来一切正常，功能就是不生效。
- **根因**：不是 Pi 的事件 bug，也不是扩展写错了，而是**我们自己的 `runtime.ts` 把两条路都堵死了**：
  1. **无 API Key 时 `input` 事件永远不触发**。Pi 的 `session.prompt()` 第一句就
     `emitInput()`（`dist/core/agent-session.js:842`），而 runtime 的「无 Key」分支
     **在调用 `prompt()` 之前就 `return` 了** —— 学段观察代码根本不可达。
     同项目的 learning-log 之所以正常，是因为它挂在 `agent_end` / `tool_execution_end` 上，
     那条路在两种世界里都会走到。**同一个「扩展没生效」，一个是 API 用法问题、一个是控制流问题。**
  2. **`before_agent_start` 排在凭据校验之后**。`prompt()` 先跑 `hasConfiguredAuth`
     （`:880-889`），没 Key 直接抛，永远走不到 `emitBeforeAgentStart()`（`:915`）。
     于是 prompt 覆盖也不可能生效 —— 实际发出的 prompt 一直是 runtime 的兜底模板。
- **解决**：**不再依赖「事件一定会来」这个假设**。把学段扩展改为三个显式入口
  （`observeTurn` / `systemPromptFor` / `appliedGrade`），由 runtime 主动驱动，且**在早返回之前**调用；
  两个 prompt 出口（`systemPromptOverride` 与 `before_agent_start`）合并到同一个函数，
  于是「覆盖是否生效」在发出的 prompt 里**可 grep**，而不是静默 no-op。
- **防呆**：① 覆盖块带一个**独特标题**（`## 学段（系统自动推断，以此段为准）`），
  使「生效与否」可用一条 grep 判定；② 断言拼装幂等（重复调用不叠第二段）；
  ③ 顺手修掉一处**假绿断言** —— 验收脚本原来拿中文字面量与机器值（`junior`）比较，
  恒真，等于没测。
- **报告用法**：报告第 7 章「难题与解决方案」，也是**汇报最值得讲的一条**：
  「注册成功 ≠ 生效」。这类 bug 的可怕之处是没有报错，只能靠**端到端观察可测的副作用**
  （数据库行数、可 grep 的标记）才能发现 —— 纯单测永远抓不到，因为单测里我们是直接调函数的，
  恰恰绕过了出问题的那段控制流。

## P-039 供应商调用失败时**根本不发 `message_update`**（只盯它会把失败当成功收尾）

- **现象**：把 BaseURL 指到一个连不上的地址，界面在供应商**一个字都没返回**的情况下显示「已作答」，
  正文是空的。事件流里 `done` 先到、`error` 后到 —— UI 已经把「这一轮结束了」记下，随后的 `error` 变得像多余事件。
- **根因**：**失败的供应商调用不会产生任何文本增量**，因此没有 `message_update`。
  用离线探针实测 Pi 0.85.1 的真实序列是：
  `message_start` / `message_end` → **`agent_end`（`willRetry=true`）** → `auto_retry_start` **×3** →
  最后一次 `agent_end`（无 `willRetry`）→ `auto_retry_end(retryFailed)` → `agent_settled`。
  问题出在「把 `agent_end` 无条件映射成 `done`」——**`agent_end` 在重试过程中也会发**，
  它在那一轮里不代表「回答完了」。
- **解决**：① `willRetry === true` 的 `agent_end` **不发终态**；
  ② 一轮真正的终态**只有一个**——`agent_end` 与 `agent_settled` 用「已发过终态」标志互斥，先到者赢；
  ③ `error` 只给**真·终局失败**（`auto_retry_end(success=false)`）。
- **防呆**：事件映射写成**显式状态机**（收到哪个事件、当前是否重试中、终态发过没有），并对上面那条
  真实序列写一条**序列断言**（喂事件序列 → 断言产出的 6 事件序列），而不是只测单个事件。
- **报告用法**：报告第 7 章。这条的价值在**「API 语义 ≠ 直觉语义」**：`agent_end` 这个名字读起来
  就像「答完了」，实测才发现它在重试里也发。配套可讲的一条推论是
  **「一轮只该有一个终态」**——多发一个终态，UI 就会把失败显示成成功。

## P-040 `setInterruptBuffer` 必须由**另一个线程**写 SIGINT，且 `SharedArrayBuffer` 在 Electron 里默认关闭

- **现象**：给死循环加「5 秒超时中断」，结果**测试直接挂死**（`node` 退出码 **124** = 被超时 kill），
  界面也卡死；加了中断代码却**一点作用都没有**。
- **根因**：两层，缺一个都不行。
  ① **同线程的定时器永远不会触发**：Pyodide 的 `runPython` 是**同步阻塞**调用，会占满该线程的事件循环，
  在同一个线程里用 `setTimeout` 往中断 buffer 写 `SIGINT`，那个定时器**根本没机会跑**。
  ② **`SharedArrayBuffer` 默认不可用**：实测 Electron 的渲染进程（`file://` 与 `data:`）与 Worker 里
  `typeof SharedArrayBuffer === 'undefined'`，而它是 `setInterruptBuffer` 的前提。
  合起来就是「以为加了超时、其实一点保护都没有」。
- **解决**：① 采用**主线程 ↔ Worker 双线程**结构，定时器归**主线程**，到点往 `SharedArrayBuffer`
  写 `SIGINT`（值 2），Worker 里的 Python 轮询到即抛 `KeyboardInterrupt`；
  ② 主进程加一行 `app.commandLine.appendSwitch('enable-features', 'SharedArrayBuffer')`。
- **防呆**：**启动时自检** SAB 是否可得，拿不到就**如实降级**为「只有墙钟超时、无法中断」并报给界面
  ——**绝不假装有保护**；并留一条真实死循环实测：`while True: pass` → 「已中断（运行 **5002 ms**）」，
  且中断期间 **rAF 仍在走（实测 1269 帧）**——主线程被占住的话这个数会接近 0。
- **报告用法**：多模态交互质量 25% + 报告第 7 章。**「1269 帧」是这条的记录方式**：
  拿一个与结论**反向**的指标（帧还在动）去证明主线程没被占，比只贴一句「已中断」硬得多。

## P-041 `payload_id` 注入顺序反了：症状（卡片说「加载失败」）与根因（消息全被丢弃）完全相反

- **现象**：动画卡片提示「加载失败 / 超时」，**但动画明明在屏幕上正常播放**。
  画面是对的、通道是断的 —— 第一反应会去查播放逻辑或网络，方向全错。
- **根因**：`payload_id` 的注入被排在**沙箱运行时之后**，而运行时在**求值时**就要读到它；
  读不到就**自造一个随机 id**。于是宿主发出的每条指令带的 id 与沙箱自认为的 id 不匹配，
  **所有消息都被当成「串台消息」丢弃**（这正是 `payload_id` 校验的设计目的）。动画自己播起来了，
  是因为模板脚本本来就会自动开始；而宿主→沙箱的播放/暂停/进度**全丢**，最终判超时。
- **解决**：把 `payload_id` 的注入提到**运行时之前**（`window.__K12_PAYLOAD_ID__ = …`；
  服务端托管时另拼进 URL query），并在代码里写明「顺序反了它会自造一个随机 id」。
- **防呆**：服务端在产物里断言 `payload_id` 校验标记存在（`PAYLOAD_ID_MARKER`），没有就判不合格；
  另有一条回归用例专门盯 `{body}` 占位符漏拼（模板脚本会跑在**空 DOM** 上）。
- **报告用法**：报告第 7 章，**汇报最值得讲的一条**。这类 bug 的特征是
  **「症状的指向与根因相反」**：错误提示说「加载失败」，实际数据是「加载成功但被丢弃」；
  动画在播反而**强化了错误假设**（"既然在播，那问题肯定在别处"）。教训是**先看通道计数**
  （被丢弃的消息数是个可观测指标），而不是先怀疑被观测到的现象。

## P-042 `Number(null) === 0`：模型「没给分」被静默当成「0 分」并真的扣掌握度

- **现象**：模型对主观题返回 `{"score": null}`（没给分），学生被判**0.0 分**、
  **掌握度被真的扣掉**、闯关进度后退。而且**没有任何报错**——链路一路绿灯。
- **根因**：JS 的 `Number(null) === 0`（`Number("") === 0` 同理）。判分代码拿到 score 后直接
  `Number(rawScore)`，**「缺失」被静默折叠成「零分」**。「模型没表态」与「模型判定为零分」
  在类型上都是 `number`，于是这个语义丢失**无法在后续任何一层被察觉**。
- **解决**：**先排除 `null` / `""` 再转数值**——认不准就返回 `null`（明确表示「本题没有结论」），
  由调用方决定怎么处理，而不是猜一个 0.0 出来。
- **防呆**：顺手把主观题分数**限定在固定档位**（`0.0 / 0.2 / 0.5 / 0.8 / 1.0`），
  并断言「`score` 必须落在这些档位上」；越界或非数值一律当「无结论」，不吸附到最近档。
- **报告用法**：报告第 7 章。这是**「静默的类型强制转换吃掉业务语义」**的教科书案例：
  一个 `Number()` 就把「未作答/无结论」和「零分」合并了。可延伸的讲法是
  **「业务上不同的状态，在代码里必须是不同的值」**——用 `null` 而不是 `0` 表示「不知道」。

## P-043 无脑擦 `record.msg` 会让日志系统自己抛 `TypeError`（**实测复核 P-009**）

- **现象**：脱敏过滤器上线后，日志里出现
  `TypeError: not all arguments converted during string formatting`，
  抛错位置在**业务日志的调用点**，看起来像业务代码写错了。
- **根因**：`logging` 的 `record.msg` 是**格式串**，参数单独放在 `record.args`。
  把 `record.msg` 整个擦成 `"***"` 之后 `record.args` 还留着，`record.getMessage()` 做 `msg % args`
  时占位符数量对不上，**脱敏器把日志系统本身弄崩了**。
  （本条与 P-009 是同一陷阱：P-009 是**预判**，这里是**实测数值复核**。）
- **解决**：脱敏必须**逐段跳过 `%`-占位符**（`%s` / `%(name)s` / `%d` / `%%`），
  只替换参数里的敏感值；`%d` 的参数还**必须保持是数字**（转成字符串同样会抛 TypeError）。
- **防呆**：正反两面对照的单测。**正面**：`"检索失败 %s：key=%s 用时 %d ms"` + `("循环", FAKE_KEY, 12)`
  脱敏后 `getMessage()` 得到 **`'检索失败 循环：key=*** 用时 12 ms'`**（占位符全留、`%d` 参数仍是数字）；
  `%(name)s` 的命名形态同样存活。**反面**：直接 `record.msg = "***"` 确实抛 `TypeError`。
  另断言过滤器**永远返回 `True`**、安装**幂等**（重复安装不叠第二层）。
- **报告用法**：合规（「凭据不明文入日志」）的实现细节 + 报告第 7 章。
  可讲点是**「安全代码自己成了故障源」**：脱敏是防御措施，实现不当反而让整个服务不可用；
  以及「预判的坑要留到**实测复核**才算数」——P-009 写了危险，P-043 才给出真实数值。

## P-044 打包「成功」不等于打进去的是新代码

- **现象**：`npm run build:win` 一路成功、产物能启动、冒烟也过，于是判定「打包通过」。
  实际产物里的 sidecar 是**几小时前的陈旧二进制**，只注册了 **1 条路由 `/health`**、
  只带进 **1 个资源文件**。应用能起来，但**所有业务接口都不存在**。
- **根因**：`electron-builder` 的 `extraResources` 只是把 `server/dist/...` **当时磁盘上有什么就搬什么**。
  而 sidecar 的产物是**按需重建**的（`scripts/build_server.py`），
  代码改了但没重跑打包脚本时，`dist/` 里躺着的是上一版。
  **「构建成功」只说明搬运没出错，不说明搬的是新的。**
- **解决**：`build:win` / `build:unpack` 之前必须重跑 sidecar 打包；
  更重要的是**把「新旧」变成可断言的事实** —— 在产物自检里断言**接口数量**与**资源文件数**，
  而不只是「进程能起来、`/health` 返回 200」。修后实测：路由 **1 → 21**、资源 **1 → 39**。
- **防呆**：自检改成**行为级**——清空数据目录后真调一次 `/api/rag/search`，
  断言 `hits > 0` 且 `degraded == "vector"`。这条断言在同一轮里同时抓住了两个缺陷
  （陈旧二进制、随包知识库缺失），而「文件存在」这类断言当时全都绿着。
- **报告用法**：报告第 7 章。这是**验证设计**的典型案例：断言写得越接近用户可感知的行为，
  越能抓住真问题；写「文件存在 / 进程起来了」这类代理指标，绿灯只证明流程跑完，不证明结果正确。

## P-045 只读发布的 SQLite 不能是 WAL 模式（写保护目录下会打不开）

- **现象**：把知识库做成随包只读资产后，本地开发一切正常；装到真实安装路径
  （写保护目录）后**打不开数据库**，报 `unable to open database file`。
- **根因**：`journal_mode=wal` 的库即使以只读方式打开，SQLite 也需要创建
  `-shm` / `-wal` 两个旁路文件。**写保护目录里建不了**，于是打开失败。
  注意这与权限位无关——`mode=ro` 也救不了它。
- **解决**：发布前 **VACUUM 并切回 `journal_mode=delete`**（回滚日志模式），
  并**拒绝**产物里残留 `-shm` / `-wal`。
- **防呆**：产物自检里明确断言「随包库能以只读方式打开」+「写入被拒」两条同时成立。
  实测：回滚模式只读打开 OK、写入被拒；WAL 模式直接打开失败。
- **报告用法**：报告第 7 章。**「开发机跑得通」和「用户机器跑得通」是两个命题**——
  差异往往不在代码，而在运行环境的**可写性**。这是把本地数据库当只读资产分发时的必修课。

## P-046 绕过 UI 直调底层接口造出的「假 bug」——验证必须走用户真实入口

  「我们怎么确认一个 bug 是真 bug」——绕过 UI 直调底层接口，测出来的是
  「这个接口单独用会怎样」，而不是「用户会遇到什么」。

## P-047 「耗时两小时的子代理」——并行任务的看护成本

- **现象**：一个负责修「渲染 bug」的子代理跑了**两小时**没有返回，最后被用户手动叫停。

## P-050 启动竞态：只读的学段徽章**早于 sidecar** 把会话建出来，设置从此本次运行内永不生效

- **现象**：修好 P-049 之后，冷启动仍然不读设置（日志里是
  「取『生效中的 LLM 配置』失败：sidecar 尚未就绪」），只有手动保存一次才生效。
- **根因**：**渲染进程一挂载就读学段**（那是只读徽章），而读学段走的是
  `ensureChatRuntime()` —— 它比 sidecar 就绪**更早**发生。于是会话被用内置默认值建出来并缓存，
  此后 `ensureChatRuntime()` 直接返回这个实例，本次运行内**再也不会**重新读设置。
  这是**顺序假设**错误：写这条链时默认「第一个拉起会话的动作发生在用户发消息时」，
  而实际上有个更早的、看起来无关的调用方（只读徽章）。
- **解决**：① 记住「本次会话是降级装配的」（`runtimeConfigDegraded`）；
  ② 每轮对话前调 `ensureRuntimeConfigApplied()`：若降级过且现在拿得到设置，就热应用一次
  （幂等、便宜、不抛）。**会话不必重建**，对话历史保留。
- **防呆**：`desktop/tests/settings-to-pi.test.ts` 的 C4 断言
  「必须有『补配置』这条路径」且 `runChatTurn` 里确实调了它。
  ⚠️ 这条坑**只能靠真机冷启动验证**：单测与「先手动保存一次」的验收路径都会掩盖它 ——
  所以真机验证时必须**关掉应用重开、且中途不碰设置页**。
- **报告用法**：「先赋值的路径会固化后续行为」—— 当「拿配置」与「用配置」被拆到不同时机，
  就必须显式处理「当时拿不到、后来拿到了」这个中间态。
  顺带一提：这个 bug 只有在**真正冷启动**时才暴露，
  单元测试与「先手动保存一次」的验收路径都会掩盖它。
- **服务哪条评分**：设计合理性 25% / 用户体验 15%。

## P-051 热切换只改了「谁在发请求」，没改「允不允许发」——门禁读的是过期快照

- **现象**：热切换成功（日志确认 provider/model 都换了、`setRuntimeApiKey` 也调了），

  热切换时就地更新并重算 `checkAuth`；所有读点（每轮门禁、补全器填充、judge 可达性）改读这一份。
  另外把补全器抽成 `fillCompleter()`，热切换后重填 ——
  否则「配好了 Key 也只有对话能用」，自审/判学段/动画生成仍停在降级态。
- **防呆**：`desktop/tests/grade-judge-wiring.test.ts` 的 J4b 断言
  「热切换后必须重新填补全器 + 重算 authReady」；
  J4 断言 judge 的可达性判据与补全器共用同一套口径（不再各读各的）。
- **报告用法**：**状态的可变点必须收敛到一处**。
  同一个事实（有没有 Key）被三个地方各自缓存成常量时，任何一次运行时变更都会留下
  一半新、一半旧的中间态；而这种不一致的表现形式是「文案与事实打架」，极难从日志看出来。
- **服务哪条评分**：设计合理性 25%。

## P-052 「两份实现，两边单测都绿」——用一条比对测试把它逼成一份

- **现象**：同一个纯函数（候选模型合并）在主进程与渲染进程各写了一份：逻辑等价、
  写法略有差异（`!trimmed` vs `trimmed === ''`）。
  两侧各自的单测都过 —— 因为它们**各自**断言的是自己对不对。
- **根因**：写的时候是「两处都要用 → 各写一份省事」，而**没有任何断言盯着两者是否相等**。
  这类分叉的后果是「界面显示的候选」与「主进程实际返回的候选」不一致，
  且因为两边都测过，排查时会先怀疑别的地方。
- **解决**：本意只是加一条「两边结果必须一致」的断言，**结果它当场就红了**
  （同一组输入两份实现的写法不同，逐字比较不过）。于是干脆把实现上移到
  `@shared/provider-catalog`，两个消费点都 import 同一份 —— 从「断言它们一致」升级成「不可能不一致」。
- **防呆**：`desktop/tests/settings-to-pi.test.ts` 的 D4 三条断言：
  ① 行为规格表（规则本身）；② **任何消费方都不得再写一份 `function mergeModelCandidates`**；
  ③ 两条 import 路径拿到的是**同一个函数**（不是包装过的副本）。
- **报告用法**：这是「**用测试把重复实现逼成单一实现**」的一个正面例子 ——
  先写断言发现分叉，再把结构改对。可讲的点：比对测试的价值不只是「发现不一致」，
  更是**逼出更简单的结构**（一条断言换掉两份要同步维护的代码）。
- **服务哪条评分**：设计合理性 25%。

## P-053 「测试与实现各自恰好都对」——三种假绿形态，以及为什么必须先跑负向对照

- **现象**：本轮审查（2026-09-17）在**全绿**的 1025 项测试里找出五条「假绿」，
  它们不是失败，而是**永远不会失败**。修完实现后，新写的断言一开始也踩了同一个坑。
- **根因**（三种形态，可命名复用）：
  1. **恒真断言**：`record(mockLog.includes(...) === false || true, …)`；
     或对「刚创建、从未 emit 过」的对象断言其计数为 0 —— 条件与结论无关。
  2. **自我引用的完整性检查**：`EXPECTED_TOOLS` 与 `TOOLS` 是同一份硬编码列表，
     「工具清单也要完整」这条检查只是在跟自己比。
  3. **判据被实现「恰好也满足」**：这是本轮最隐蔽的一条 ——
     新写的「登记生效」回归用例用了 `sk-` 形态的假 Key 做断言，
     而 `guard` 的**形态规则**本来就会无条件擦掉 `sk-…`，
     于是把 `register_secret()` 全部删掉，用例**依然通过**。
- **解决**：
  ① 恒真式改成真判据（`lines.length > 0`），「顺带断言」拆成独立一条；
  ② 完整性检查改为从**真实注册表派生**（`AGENT_TOOL_NAMES` / `TOOL_TO_KIND`），并反向断言清单里没有已不存在的 Tool；
  ③ 形态 3 的解法是**换一个只有被测机制才能覆盖的输入** ——
     改用自建网关形态 `gw-…`（不在任何形态规则里，只有登记了才会被擦）。
     **并且每次都要做负向对照**：把被测的那行实现删掉，确认用例真的变红。
- **防呆**：
  - 每条新回归用例都**必须**先验证「修复前为红」；本轮 40+ 条新用例全部走过这一步。
  - 同类改造还有：三处 substring 守卫改为 **`stripComments` 后再匹配**（否则「注释掉调用 + 写一行 TODO」即可满足守卫），
    断言窗口从定长 `slice(N)` 改为「取到下一个顶层声明」。
  - `scripts/check-tool-schema.mjs` 用**负向注入**自证不是空转（改坏一个 Tool 参数类型 → 必须退出 1）。
- **报告用法**：**「测试全绿」不是结论，「测试会红吗」才是。**
  可讲的最有力的一句：我们在全绿的 1025 项里找出五条永不失败的断言 ——
  这说明测试数量与覆盖质量是两件事，而建立这个判断的方法只是「把实现改坏，看它红不红」。
- **服务哪条评分**：设计合理性 25%。

## P-054 「表建好了、读接口有了、就是没人写」——全绿的功能断头路

> **如实说明**：这条是**静态审查发现**（把链路逐段 grep 出来的），不是现场故障 —— 正因为如此，它更能说明问题。

- **现象**：`profile_pref` 表在迁移里建好（`server/app/store/migrations.py:246`，`key TEXT PRIMARY KEY, value TEXT`）、
  `GET /api/profile/{id}` 会把它读成 `preferences` 返回（`server/app/routes/profile.py:470` / `:486` / `:495`）、
  TS 侧也有现成的渲染逻辑（`renderProfileText` 会把偏好渲染进画像文本，
  `desktop/src/main/agent/extensions/profile.ts:142` / `:171`）——
  **但全仓搜不到任何生产写入路径**：唯一一条 `INSERT INTO profile_pref` 在
  `server/tests/test_profile_routes.py:309`，是测试。
  也就是说需求要求的「兴趣偏好」这一项，**看起来三层都实现了，实际永远是空的**。
- **根因**：**写路径依赖一个不存在的调用方** —— 表与读接口都是「先按数据模型建好」，
  而写入口被设想成「模型主动来写」，可那个 Tool 从来没被建出来；
  读端先建好之后，**没有人回头看「那谁往里写」**。
  两侧各自的测试都能过（读端用例只需一条自造数据的 `INSERT`），缺口恰好落在两边都看不见的缝里。
- **解决**：补 `remember_preference` Tool（模型主动写）+ `PUT /api/profile/{id}/preferences` 端点（D-031），
  并把偏好 key 限制成固定词表 4 个（`interest` / `explain_style` / `pace` / `note`）——
  写入路径一旦存在，就必须同时回答「写什么、能写多少、谁来清」这三个问题。
- **防呆**：**判断一个功能是否真的落地，不能只看「有没有表 / 有没有接口」**，
  要顺着「**谁写 → 存哪 → 谁读 → 读来干什么**」走完整条链；四条里缺一条，功能就是空的。
  可以做成机械检查：对每张表 / 每个端点反向断言「至少存在一处生产写入」。
  同理，读接口的单测**自造数据的 `INSERT` 会掩盖写路径的缺失** —— 这类用例要么走真实写入口，要么显式标注「造数」。
- **报告用法**：**这是「静态看代码很难发现」的典型**：有表、有接口、有渲染、有测试，四项齐全，
  唯独没有那条「把数据放进去」的路径。可讲的点是**功能的完整性是链路的完整性，不是各层存在性的总和**；
  以及为什么「新增一张表」的票必须同时交付一个写入路径（哪怕只是内部调用）。
- **服务哪条评分**：设计合理性 25% / 教育适配性 20%（偏好本来要喂给个性化推荐）。

## P-055 「数据算好了但没人用」——算出来 ≠ 用上了（「可以有」与「每轮都在用」是两件事）

- **现象**：掌握度、推荐、偏好这些数据每轮都在真实写入和计算，围绕它们的用例有 40 条以上
  （`test_personalization.py` 19 条 + `test_profile_routes.py` 17 条，判分侧 `test_quiz_loop.py` 另 17 条用例涉及 `mastery`），
  但**画像从来没有进过 system prompt**：`renderProfileText()` 只在 `get_student_profile` 这个 Tool 的
  `execute()` 里被调用（`desktop/src/main/agent/extensions/profile.ts:292`）——
  也就是说模型想用画像，只能**自己决定**去调那个工具；
  而四学段 prompt 里关于画像只有一句「不要为了画像去追问学生个人信息」
  （`desktop/src/main/agent/prompts/rules.ts:76`）—— **只说了不许做什么，没说该做什么**。
- **根因**：能力被实现成「一个可以调用的 Tool」之后，就默认「模型会去调」。
  但**「可以有」和「每轮都在用」是两件事**：前者靠工具描述（模型用不用是概率事件），
  后者要靠 **prompt 注入**（每轮都摆在模型眼前）。把「使用」寄托在模型的自发行为上，
  等于把确定性需求交给不确定的执行者 —— 而它平时**不会报错，只是永远不生效**。
- **解决**：把画像**每轮注入** system prompt（D-031 的 A 项），
  与学段覆盖共用既有那条唯一的 prompt 出口（不要拉第二条拼装路径），并保持拼装幂等。
- **防呆**：**「实现了」的验收标准要分档** —— ① 代码存在 ② 能被调用 ③ 在真实运行里会被用到；
  本项目此前有一批专门的「接线了没有」测试只守到 ②（P-038 / P-049 / P-052 都是这条线上的），
  这次的坑说明还需要**第四档：「每轮都在生效吗」** —— 对关键上下文，断言它出现在
  **真正发出去的那份 prompt** 里，而不是断言「有个函数能生成它」。
- **报告用法**：可讲的对比很锋利：**加一句 prompt 注入与加一个 Tool，成本差一个数量级，
  但对「是否真的影响模型行为」的效果也差一个数量级**。
  本条与 P-054 是一对 —— 一条讲「数据进不来 / 出不去」，一条讲「数据在里面但没人看」；
  合起来正好是「功能链路的四问」与「验收的分档」两套自查清单。
- **服务哪条评分**：教育适配性 20%（个性化学习路径）+ 设计合理性 25%（上下文管理的显式设计）。

## P-056 「每轮都变」的上下文 = 每轮都丢一次前缀缓存（一个不会报错的性能与成本缺陷）

- **现象**：注入 system prompt 的画像块里带了最后一行「最近活跃：`YYYY-MM-DD HH:mm`」。
  `learning_log` 每轮都会 `upsert_student` 刷新 `student.last_active_at`，而这行精确到**分钟** ——
  所以只要学生两次提问间隔超过一分钟（正常对话几乎必然发生），
  下一轮拼出来的 system prompt 就**整体变了一个字节**。
  它不崩、不报错、日志里什么都看不到，测试也全绿（那个时间戳是「正确渲染」的）。
- **根因**：system prompt 是**前缀缓存的最前面一段**，而缓存按「从头开始的最长相同前缀」命中 ——
  块里任何一个每轮都变的字节，都会让整段前缀**连同它后面的全部对话历史**一起丢掉命中。
  代价不是「多付一笔」，而是**拿不到折扣**：DeepSeek 的缓存**写不收费**、读只要输入价的 2%
  （Pi 内置目录实测 `deepseek-v4-flash`：`input 0.14` vs `cacheRead 0.0028`，$ / M token）。
  真正被学生感知到的是**首字延迟**（厂商要重新预填充整个前缀），成本只是顺带的。
- **关键判断（按量级算过，不是感觉）**：本次实测整份 system prompt 约 1.6–1.8k token
  （四学段模板 1,736–2,165 字符 + 画像块最多 619 字符）。
  在「每轮都 miss」与「全命中」之间，一次十轮对话的差额在**分**的量级；
  而输出价是缓存读价的 **100 倍** —— 也就是说**回答长度与工具往返次数**对成本的影响
  比缓存命中率大一个数量级以上。所以结论是「别让无意义的字节变动」，**不是**「砍个性化去省缓存」。
- **解决**（D-032）：块里**不放时间**（`lastActiveAt` 仍留在契约里给界面用，只是不进给模型的那一段）；
  偏好按固定顺序 `PREFERENCE_ORDER` 渲染（`SELECT key, value` 不带 `ORDER BY`，
  行序取决于 SQLite 存储布局 —— **重写同一个键就会挪位置**，同样让块变样）；
  掌握度平局按 `kpId` 兜底排序（不依赖调用方给的数组顺序）。
- **防呆**：G21 组 6 条守卫，其中**反向对照**是重点 ——
  「同样的画像 → 逐字节相同」很容易被「把块冻成常量」这种假优化骗过，
  所以必须有另一半断言：**画像真的变了，块必须跟着变**（掌握度 / 偏好 / 推荐三类各一条）。
  另加一条源码级断言：`renderProfileText` 里不得出现 `Date` / `lastActiveAt` 等时间符号。
- **报告用法**：这是一个**很好的「看不见的缺陷」案例** —— 它没有失败模式，
  只有「贵一点、慢一点」，而且在做优化之前根本没人会去量它。
  讲的时候可以配上实测数字：模板与块的字符数、以及「输出价 = 缓存读价 × 100」这个量级对比，
  说明**知道该优化什么、也知道该放弃什么**比单纯「做了缓存优化」更有说服力。
  与 D-032 互为正文（决策理由在那边，这里是复现与量化的过程记录）。
- **服务哪条评分**：用户体验 15%（首字延迟）+ 设计合理性 25%（上下文与成本管理的显式取舍）。

## P-057 「数据全在，接口也全在」—— 但**排序依据**是错的（章节顺序踩了两次）

- **现象**：实现「按学段列出章节」时，第一版用 `GROUP BY chapter_title ORDER BY MIN(rowid)`，
  理由写得很像回事：「rowid 是入库顺序，而入库顺序就是教材顺序」。
  实测小学低年级返回 **`第1章, 第6章, 第1章, 第3章, 第5章, 第2章`** —— 目录顺序全乱。
- **根因**：`kp` 表的 rowid 是**文件名字典序**（`pl-ai-around-me` → `pl-ai-draws` → `pl-ai-learns`
  → `pl-ai-manners` → …），与教材章节顺序**没有任何关系**。
  第一版之所以敢写「入库顺序就是教材顺序」，是因为**没有真的看一眼数据**——
  这个假设在 `chapter_title` 恰好按文件名排序时才会成立，而它显然不成立。
- **解决**：排序改为**解析章节名里的数字**（`第N章`），解析不出的排到末尾并按名称兜底。
  顺序这条性质用最强的形式断言：章号必须**严格递增且从 1 连续**。
- **★ 触发这个 bug 的测试**：我写这条断言时的原意是「防字典序把『第10章』排到『第2章』前」，
  结果它**顺带抓住了入库顺序这个形态**。如果把断言写成「第2章在第10章前面」这种
  只针对字典序的弱形式，这个 bug 会直接溜过去（当前教材根本没有两位数章节）。
- **可推广的教训**：**「顺序」这种需求，断言要写成「最强的顺序性质」（递增 + 连续），
  而不是「我预想的那种错误形态」**。后者只在你想到了那个错法时才有效。
- **报告用法**：可以讲一个很具体的对比 —— 同一个 `ORDER BY`，写在注释里的理由是错的，
  而**只有真的把 API 打一遍看返回值**才发现。呼应 P-055「算出来 ≠ 用上了」：
  这里是「字段有值 ≠ 值是对的」。

## P-058 零引用的读原语 = 零测试覆盖的死代码（负向对照抓出来的）

- **现象**：给「错题本」加数据层读原语时，我顺手加了四个：`history_rows`（读全部记录）、
  `mistakes`、`daily_activity`、`activity_days`。写完后做**负向对照**（P-053 的纪律：
  每条守卫都要注入一次回归、确认它真的变红），其中一条是：
  「把 `is_correct` 的 `None`（没有对错概念）与 `False`（答错）混为一谈」——
  这是 `_history_from_row` 里最容易写错的一行（`bool(None) == False`）。
- **结果：全部 34 条测试仍然全绿。**
- **根因**：不是守卫写得不好，而是**那段代码根本没有调用方**：
  `mistakes()` 在 SQL 里就 `WHERE is_correct = 0`，`daily_activity()` 按天聚合 ——
  两个真实消费者都不经过 `_history_from_row`。于是那三行代码是**零引用**的：
  没有调用方 ⇒ 没有测试 ⇒ 注入任何回归都不会被发现。
- **解决**：删掉 `history_rows` / `HistoryRecord` / `_history_from_row`，
  并在原处留一条注释说明**为什么不加**（要加就等真的有调用方时再加）。
  本仓库有同类先例（`pi-paths.ts` 里删过一个零引用的 `isWritableDir()`）。
- **★ 这条与 P-053 是一对**：P-053 说「不会变红的守卫等于没有守卫」；
  这一条说「**没有守卫的代码等于没有代码**」—— 而它的发现方式正是前一条的纪律
  （负向对照）。如果不做那次注入，我会一直以为那三行是「有测试覆盖的」。
- **报告用法**：这是「我们不只是写测试，还会验证测试本身有效」的直接证据。
  可以讲成一句话：**绿色的测试数与通过的负向对照数，是两个不同的指标**。

## P-059 「注入进每轮 Prompt 的内容」比「界面显示的内容」危险得多

- **现象**：把错题摘要注入 system prompt 时，最自然的写法是把 `MistakeItem` 整个渲染进去
  （它有 `stem` 题干、`lastWrongAt` 时间、`lastQid` 题号，信息量看着最全）。
- **根因（两层）**：
  ① **`lastWrongAt` 是时间戳**：它是「上一次答错的时间」，学生每答错一次就变一次 ——
     而 system prompt 是**前缀缓存的最前面一段**，块里任何一个字节变化都会让整段前缀
     连同其后**全部对话历史**一起掉出缓存（P-056 的机制）。界面上的时间戳只是显示，
     注入里的时间戳是**每轮重新预填充**；
  ② **`stem` 是 120 字题干**：块在每一轮的首位，题干会稳定挤掉真正相关的教材上下文 ——
     而模型手里本来就有**当前这一轮**题目的上下文，历史题干对「下一步怎么讲」价值很低。
- **解决**：注入层只取 `{kpId, kpName, wrongCount}`，并显式写进类型注释
  （`MistakesResponse` 的注释点名「不取 stem、不取 lastWrongAt，以及为什么」）。
  新增 G22 组守卫：断言块里**没有日期/时刻/长数字串**、没有题干，且错题平局按 kpId 兜底。
- **负向对照**：把 `new Date().toLocaleString()` 注回错题那一行 → **G21-6（源码级）与 G22-2（行为级）
  同时变红**。两个不同层次的守卫各自独立发现了它 —— 这正是「源码级 + 行为级」双保险的价值。
- **可推广的教训**：**同一份数据，显示口径与注入口径应该分开设计**，
  而不是「界面显示什么就注入什么」。注入物的成本结构完全不同（它在每轮请求的首位）。
- **报告用法**：这是 D-032「逐字节稳定」那条纪律的一次实战应用 ——
  它不只是「别加时间戳」这么一条禁令，而是**新增任何注入内容时都要走一遍的设计检查**。

## P-060 「手动设置」写进库的轮次号是 0，于是冷却期假装只剩 3 轮

- **现象**：学生手动切换学段后，`GET /api/grade/state` 报 `cooldownRemainingTurns = 10`，
  但**下一轮**再查就掉到 3 —— 而设计是「10 轮内不再自动调整」。如果只按「切完之后查一次」写断言，
  这条**永远绿**；真正的问题要等到「第 4 轮之后自动判定又动手了」才暴露，而那时代码已经交付了。
- **根因**：冷却剩余 = `窗口 - (当前轮次 - 锚点轮次)`。写入手动那条轨迹行时，
  `turn` 用的是「这个请求里带来的轮次号」—— 而手动切换是一个**独立的 HTTP 调用**，
  它根本不属于任何一轮对话，接口层能拿到的默认值就是 `0`。
  于是 `elapsed = 当前轮(如 3) - 0 = 3`，`remaining = 10 - 3 = 7`……看起来「在递减」，
  实际上是**凭空消费掉了 3 轮冷却**。它不会报错，只会让「10 轮保护」静默缩水。
- **解决**：写入前先取「当前轮次水位」`turn_watermark()` = `max(信号表里的最大轮次号, 锚点行轮次号, 0)`，
  用它当锚点轮次。于是「第 3 轮时学生手动切换」写进去的是 `turn=3`，
  `elapsed` 从 0 起算，冷却真的是 10 轮。
  实测证据：CDP 点完学段后查库，`grade_history` 那一行是 `turn=8`（不是 0），
  与 `grade_signals` 里的最大轮次一致。
- **负向对照**：把 override 的 `turn` 临时写死 `0` → **两条断言同时变红**
  （「冷却 10 轮」（4–12 轮全部 `reason=cooldown`）与「重复选同一学段也算锚点」），
  还原后全绿。这证明那组断言真的在测冷却，而不是在测「刚写进去那一瞬间的返回值」。
- **可推广的教训**：**「从一个不参与该流程的入口写数据」时，最容易漏掉的就是时间/序号锚点**。
  手动切换、后台补数据、运维修数都属于这一类 —— 它们没有「第几轮」这个概念，
  而下游的算法偏偏依赖它。**给锚点取当前水位，不要取请求里的默认值**。
- **报告用法**：配合「冷却窗口按来源推导（不加列）」一起讲 ——
  这是一个「不加状态也能改行为」的例子，代价是**锚点必须取对**。

## P-061 「在途的判定结论」会把学生刚做的选择悄悄顶掉

- **现象**：学生点了一个学段，界面当场变了；过一两秒**又自己跳回去**。偶发，难复现。
- **根因**：学段自动判定是**异步且 fire-and-forget** 的 —— 主进程上交证据 → 服务端算 → 回程。
  学生的点击与一次在途判定可能**同时**发生。那个判定是**按旧学段算出来的**，
  它回来时执行 `pendingGrade = nextGrade`，于是学生刚选的值被一个「出发时还不知道他改了」的结论覆盖。
  这与 P-3x 的「跨学生丢弃在途证据」是**同一个形状的问题**：异步回程时，**出发时的前提可能已经不成立了**。
- **解决**：加一个**代际号** `epoch`。`adoptOverride()`（采纳学生的手动选择）时 `epoch += 1`；
  上交任务在 `await` **之前**快照 `epochAtSubmit`，`await` **之后**比对，不一致就**丢弃那个结论**
  （并记一条 warn 日志，绝不静默）。
  ★ 关键细节：这次丢弃**不计入 `submitted`**（那个计数表示「结论真的进了决策链路」），也不计入 `failed`
  （HTTP 本身是成功的）—— 计数口径要写进注释，否则以后有人看到 `submitted` 少一次会当成丢包 bug。
- **负向对照**：把那次检查改成 `if (false && ...)` → 两条断言红（「不被覆盖」与「计数语义」），
  而**反向对照**（不调 `adoptOverride` 时那条结论**必须**被采纳）**保持绿** ——
  证明这组断言测的是「作废机制」，不是「把结论全部丢掉」。
- **可推广的教训**：**任何 `await` 之后的写操作，都要问一句「我出发时读的那些状态现在还成立吗」**。
  学生切换、切换会话、切换学生、清空数据都属于会改变前提的动作。
  代际号是这个问题的通用解，比「加锁」轻、比「不管」安全。
- **报告用法**：与 D-037 一起讲「两条写路径如何共存而不打架」——
  这是那套设计里唯一真正需要新机制的地方，其余全部复用现有机制（冷却、轨迹、契约）。

## P-062 架构文档的「状态行」会腐烂：它写着「没有」的接口，其实早就在跑

- **现象**：做「教材章节选择」的文档同步时核对源码，发现
  `architecture/pending/02-教材章节选择.md` 头部写「**状态：部分实施**」、
  §2.3 的缺口表更直白：「列出章节的 API：**没有**（现有 21 个路由里无 `/api/knowledge/*`，已实测）」。
  但那个端点 `GET /api/knowledge/chapters/{grade_level}` 就在 `server/app/routes/knowledge.py` 里注册着，
  `server/tests/test_study_routes.py` 有一组断言跑它，`decisions.md` 的 D-033 也把它列为
  四个只读聚合端点之一 —— **同一件事在三份文档里有两个相反的口径**。
  （同一次核对还发现：本文档 §4.4 把 `renderProfileText` 的位置指到
  `prompts/student-context.ts`，而它实际在 `extensions/profile.ts`；
  `AGENTS.md` §10 写着「decisions.md（D-001…D-017）/ pitfalls.md（P-001…P-034）」，
  而当时文件里已经写到 D-037 / P-061。）
- **根因**：文档是**写它的那一刻**的快照，而代码在之后继续长。「部分实施 / 未实施」这类状态
  **没有任何自动信号** —— 代码落地时不会有人回头改它，所以它只会**朝一个方向腐烂**，
  而且腐烂不报错、不碍事，只有你真的去点那个接口才会发现。
  危害不止是「信息旧了」：一句「**没有**」会诱导后来者去**重新实现已经存在的东西** ——
  这与 `AGENTS.md` §0 那句「禁止恢复已删除实现」是同一类风险的两面。
  更隐蔽的一层：这类文档里写死的**计数与编号区间**（路由条数、编号范围、行号）
  天然是短命的，而它们读起来又最像「经过核实的结论」。
- **解决**：本次把状态行改成「已实施」，并在头部列出**三处与原始设计不符的现状**
  （`renderProfileText` 的真实位置、存储用 `student.current_chapter` 列、
  文档未覆盖的新规则「学段变更即清空章节」）；§2.3 的缺口表改成「**当时 / 现在**」两列 ——
  **保留当时的判断不美化**（这是 `docs/report-material/README.md` 的既有纪律），只并排补一列现状。
- **防呆**：① 状态行必须自带「**以仓库代码为准**」并给出可核对的坐标（文件 + 符号名，
  **不要只给行号** —— 行号是最先失效的那部分）；② 文档里**不写死会增长的计数**
  （本次把 `AGENTS.md` §10 的编号区间删掉，改成「看两个文件末尾的编号」）；
  ③ 缺口服的表要能一眼看出「哪一列是历史、哪一列是现在」。
- **报告用法**：这是「**约束要建在结构里，而不是建在提醒里**」这条论点在**文档**上的对应物 ——
  手维护的状态标注没有机制保证它不腐烂，所以只能把它降级成「指向代码的路标」而不是「结论」。
  汇报时与第 0 节「不要恢复已删除实现」配套讲：**过期文档会让人把力气花在重做上**。

## P-063 「加一列」的迁移在并发开库时会把 HTTP 500 交给学生 —— 而根因不是「等得不够久」

- **现象**：为「教材章节选择」加了 `LEARNING_MIGRATIONS` v2（`ALTER TABLE student ADD COLUMN
  current_chapter`）之后，**第一次跑起真实应用**就在后端日志里看到：

  ```
  app/store/migrations.py", line 299, in _apply_chapter_v2
      conn.execute("ALTER TABLE student ADD COLUMN current_chapter TEXT")
  sqlite3.OperationalError: database is locked
  ```

  紧接着主进程那一行是 `[grade] 读取当前学段失败：HTTP 500（Internal Server Error）` ——
  这条 500 是**直接端到学生脸上**的（学段指示器读不出来）。
  更要命的是它对**新学生库**是概率性的：一台干净机器上，界面一挂载就同时发出几条读请求，
  谁先开库谁迁移，其余的就可能炸。

- **根因**（两件事叠加，缺一不可）：

  ① **一人一库的打开方式是「每次请求现开现关」**（`routes/students.py` 的 `open_learning_store`
     的 docstring 明写「没有全局连接池是有意的」），所以「并发开库」不是边缘情形，
     而是**界面每次挂载都会发生**。
  ② **WAL 下迁移是「先读后写」，而读那一步就把连接钉在旧快照上**：
     `ensure_migrated` 先 `SELECT` 记账表、迁移函数再 `PRAGMA table_info` 判列，然后才 `ALTER`。
     等它要升级成写事务时，赢家已经提交过，SQLite 只能返回 `SQLITE_BUSY_SNAPSHOT` 并抛
     `database is locked`。★ **这种失败不吃 `busy_timeout`** —— 连接上早就设了
     `PRAGMA busy_timeout = 5000`，等 5 秒还是同样的错。
     所以「加大超时 / 重试一下」这条路是死的；实测 36 次并发开库有 **11 次**直接失败。

- **解决**：在迁移器里**先拿写锁、再读账本** —— `ensure_migrated` 在确认「确有未应用条目」后
  执行 `BEGIN IMMEDIATE`（它**会**正常等锁），拿到锁再重读 `schema_version`
  （等锁期间别人的提交这时才看得见），然后才跑迁移、最后统一提交。
  两条连接从此被**确定性**地串行化：后到的那个进来看见账本已是 v2，直接跳过，不碰 ALTER。
  同时保留一条**事后查账本**的兜底分支（判据是账本，不是错误文本）：万一仍有连接撞上
  「另一个连接刚跑完」，只要那一版已在账上就按已应用处理，而不是把 `database is locked` 抛出去。
  ⚠️ 两个关键细节：① 只在**确有未应用条目**时才抢写锁 —— 绝大多数调用（每次开库）都是
  「已是最新」，这条热路径不该被加上额外开销；② 异常路径要 `rollback()` 收掉自己开的写事务，
  否则写锁会一直握在手里，下一个请求卡到 busy_timeout 才失败。
  （单独加的回归测试：`server/tests/test_store.py::TestMigrations::test_concurrent_first_migration_does_not_blow_up`，
  3 轮 × 3 并发连接，断言全部到 v2 且账本只记一行。）

- **反向对照**（证明这条守卫有牙）：把 `BEGIN IMMEDIATE` 那段从源码里删掉、在内存里替换回修复前的
  `ensure_migrated`，用同一条并发场景跑 —— 9 次开库里失败 2 次。所以那条测试不是「恰好通过」，
  它抓的正是这个缺陷。

- **报告用法**：① 这是「**测试全绿 ≠ 应用能跑**」的又一条硬证据 —— 这一条**单测抓不到**，
  因为单测里开库是串行的；它是「真的把应用跑起来并用真实入口点一遍」才暴露的
  （与「验收驱动方式」D-027 同源）。② 讲**混合后端**时它是很好的注脚：Python 侧的
  并发正确性（WAL / 事务边界 / 迁移串行化）与 TS 侧完全是两个世界的问题，
  契约再冻结也挡不住这类缺陷 —— 这正是「数据域的全部并发语义都留在 Python 一处」的价值。
  ③ 讲工程习惯时可用它说明「**同一句 `database is locked` 有截然不同的处置**」：
  这次如果照直觉去加 `busy_timeout` 或重试，会白花半天而问题照旧。

## P-064 「重建成功但检索到的还是老教材」—— kb 解析顺序把它静默遮蔽了

- **现象**：教材知识库页点「重建索引」→ 回执是成功（`ok:true`、带统计、带了用时），
  但检索结果**没有任何变化**，新导入的教材永远查不到。
- **根因**：`kb.sqlite` 的解析顺序是
  `K12_KB_PATH`（环境变量）→ **随包只读库** → 用户库 → 缺席。
  「随包库优先」这条**本身是对的**（升级后不该被用户目录里的旧库遮蔽，
  `tests/test_kb_bundling.py::test_bundled_wins_over_per_user` 就钉着它），
  但重建写的是**用户库**那一份 —— 于是打包态下用户库**永远排在随包库后面**，
  写进去的内容当场被遮住。**两边各自都对，合起来是错的**。
- **解决**：加一个**标记文件** `<data-dir>/shared/kb.rebuilt`（`user_rebuild_marker_path`）。
  标记存在时解析顺序把用户库提到最前；不存在时维持原样。
  - 为什么用文件存在性而不是配置项：删掉它就退回随包库，**不需要额外的清理入口**；
    而分步接线的中间态（有标记、库是坏的）也能一眼看出来。
  - 标记**只在 `build()` 成功之后才写**：先写标记再失败的话，之后检索会指向一份根本没建起来的库。
  - 标记写不进去 = 重建结果**不会生效** → 这种情况回执必须报**失败**，不能报成功（否则又回到这个坑）。
- **报告用法**：
  ① 这是「**两个各自正确的设计放在一起产生了错误行为**」的绝佳例子 —— 比「某人写错了」有说服力得多；
  ② 讲工程习惯时用它说明「**回执说成功 ≠ 用户看到效果**」：
     如果只测「重建接口返回 200」，这个 bug 会活到演示现场；
  ③ 修复手法（用文件存在性而不是配置项来表达「用户做过这个动作」）也可以顺带讲。

## P-065 统计接口谎报「向量不可用」——`vec0` 虚表数不出来

- **现象**：知识库页显示「向量引擎：不可用」，但检索明明走的是 `degraded: vector`（向量路径）。
  用 sqlite 命令行直接数 `chunk_vec` 也是 0 行，看起来像索引真的没建。
- **根因**：`chunk_vec` 是 `vec0` **虚表**。**不先加载 `sqlite-vec` 扩展**时，
  连 `SELECT COUNT(*) FROM chunk_vec` 都会抛 `no such module: vec0`；
  而 `kb_repo.stats()` 对每个表**单独 try/except 并吞掉错误**（那是有意的：单表读不出来不该把整页打空），
  于是错误被吞成 `0` —— 界面上就是「185 条向量被报成 0 条」。
- **解决**：`_vec_ready()` 在这个连接上试着加载扩展，成功则**重数一遍**覆盖那个 0；
  加载失败不抛（那就是真的降级，界面该显示「只能靠关键词检索」）。
  实测修正后：`chunk_vec 185`（= 子块数）、`vecReady: true`。
- **报告用法**：
  ① 与 P-064 同属「**接口对了、语义错了**」这一类：`COUNT(*)` 语法完全正确，
     错的是「这个表需要先做一件事才能被查询」这个隐含前提；
  ② 讲「宽吞异常」的代价：「读到 0 行」是一个**合法返回**，所以吞掉错误之后
     故障表现成「数据不见了」，而不是「出错了」—— 后者至少能被发现。

## P-066 主进程给 Python 传 `--data-dir` 时的类型坑：`str` 不是 `Path`

- **现象**：`POST /api/knowledge/import`（带重建）当场 500，traceback 是
  `TypeError: unsupported operand type(s) for /: 'str' and 'str'`；
  而**不带重建**的 `/rebuild` 走得好好的。
- **根因**：`request.app.state.config.data_dir` 是 **`str`**（`RuntimeConfig` 那个 dataclass 就是这么存的），
  而代码里写的是 `data_dir: Path = getattr(config, "data_dir", None) or resolve_data_dir(None)`
  —— **类型标注不是类型转换**，运行时它还是 `str`。
  那些 `Path(base)` 在自己内部先转换的辅助函数（`per_user_kb_path` / `user_rebuild_marker_path`）
  因此照常工作，只有真做 `data_dir / 'shared'` 的那一处炸了。
  「一半能跑」正是它能活到运行期的原因。
- **解决**：在**每个入口**（不是每一处用法）做一次 `Path(...)` 转换，并留一个统一的
  `request_data_dir(request)` 辅助函数；同时把 `test_knowledge_admin.py` 的夹具**特意用 `str` 传 data_dir**
  （照生产的方式传），这样这个坑再出现会被测试当场抓住。
- **报告用法**：
  ① 讲「**类型标注骗人**」这条时非常直观：`x: Path = <str>` 在 mypy 下可能过、
     在运行时必然炸，而 Python 的类型标注**本来就只是标注**；
  ② 顺带是「**测试夹具要照生产的样子传参**」的论据 ——
     如果夹具习惯性传 `Path`，这条 bug 在单测里根本复现不出来。

## P-067 `unplugin-*` 的 `dts` / `dirs` 路径**相对渲染进程 root**，写错不报错只静默失效

- **现象**：给 `electron.vite.config.ts` 的 renderer 段加了 `AutoImport` 与 `Components`
  （移植进来的界面靠这两条链路：`ref()` 不写 import、`<el-button>` 不注册）。
  构建与 typecheck **全绿**，界面也照常跑。但 `src/renderer/src/types/components.d.ts` 里
  **一个自定义组件都没注册**，而且过了两天才发现。
- **根因**（两个叠加的错误）：
  1. `dts` 与 `dirs` 都是**相对渲染进程的 vite root（`src/renderer`）** 解析的，
     不是相对 desktop 根。所以：
     - 写 `dts: 'src/renderer/src/types/…'` → 实际落到 `src/renderer/src/renderer/src/types/…`
       （一个凭空多出来的嵌套目录）；
     - 写 `dirs: ['src/renderer/src/components']` → 那个目录不存在。
  2. **目录不存在时 unplugin 既不报错也不警告**，只是「扫到 0 个组件」。
     更糟的是：`dts` 指到嵌套路径后，**原来那份正确位置的声明文件不会被更新**——
     它停留在旧版本、且**不在 `tsconfig.web.json` 的 include 里**，
     于是 typecheck 完全不参与，问题被彻底藏住。
- **解决**：
  - `dts: 'src/types/components.d.ts'`、`dirs: ['src/components', 'src/cards']`（都按渲染 root 写）；
  - 删掉嵌套目录与那份陈旧副本，重新构建后核对生成物：
    **25 个自定义组件 + 17 个 Element Plus 组件**都在。
  - 判定路径口径的**实证方法**（比读文档可靠）：改完跑一次 `npx electron-vite build`，
    然后 `find . -name 'components.d.ts'` 看它**实际落在哪**——
    落点会直接告诉你 root 是哪一个。
- **报告用法**：
  ① 这是「**构建全绿 ≠ 配置生效**」的典型：所有检查都过了，因为出问题的那条链路
     恰好不被任何检查覆盖（声明文件不在 include 里）；
  ② 讲「生成物的**存放位置本身就是契约**」这一点很合适 ——
     生成物放错地方时，它既不会被使用、也不会被报错，等于**静默失效**；
  ③ 也说明「移植别人的构建配置」不能只看插件名，**路径基准**必须逐一实证。

## P-068 换样式表时丢掉工具类：`class="sr-only"` 变成「可见文字」

- **现象**：顶栏多出一条「智团团 —— 陪你学 AI 的通识课小老师」，输入框上方多出一条
  「输入你的问题」。两处都不是新写的代码 —— 它们本来是**无障碍隐藏文本**
  （`<p class="sr-only">` / `<label class="sr-only">`），在改造前是看不见的。
- **根因**：移植新界面时 `assets/base.css` 被**整体替换**，而 `.sr-only` 这个工具类
  只定义在旧的那一份里。类的**使用者**照旧写着 `class="sr-only"`，但那份 CSS 已经没了 ——
  **类名不存在时浏览器不报错**，只是那条规则不生效：`position: static` 的 `<p>` 于是正常显示。
- **解决**：把这个全局工具类补回 `assets/base.css`（`clip-path: inset(50%)` + 1px，
  不是 `display:none` —— 后者会让辅助技术**也**读不到，那就失去了它存在的意义），
  并删掉 `SessionsTab.vue` 里那份局部复制（两份定义迟早分叉，而 CSS 分叉是静默的）。
- **报告用法**：
  ① 与 P-067 同源：**替换一整份样式资产时，被它服务的那些「约定名」会集体失效**，
     而失效方式是「不报错、只是长得不一样」。移植设计系统时值得专项 grep 一遍
     `class="(sr-only|k12-|btn|chip)"` 这类**约定类名**，逐个确认新样式表里有定义。
  ② 也说明「无障碍代码最容易在这种时候被吃掉」：它本来就是不可见的，
     坏了不会有人立刻发现 —— 只有那次「怎么多了一行字」的偶然才会暴露。

## P-069 无边框窗口下，拖拽区里的交互元素必须显式 `no-drag`

- **现象**（预判并规避，未实际发生）：`frame: false` 之后把整个顶栏设成
  `-webkit-app-region: drag`，若里面的按钮没有 `no-drag`，点击会被窗口拖拽吃掉 ——
  表现成「按钮点不动」，且**没有任何报错**。
- **根因**：`drag` 是**区域属性**（Windows 上由系统接管该区域的鼠标事件），
  它不区分「这块是背景」还是「这块上面有个按钮」；要区分就必须逐个元素声明
  `-webkit-app-region: no-drag` 把它排除出去。
- **解决**：拖拽区只给 `AppShell` 的 `.shell__head`（顶栏那一行）；
  其内每一个可交互元素各自声明 `no-drag`：三步循环按钮（`App.vue`）、
  模型 chip（`AppTopbar.vue`）、学段指示器的触发键与选项面板（`GradeIndicator.vue`）、
  以及 `WindowControls` 整块。每一处都留了注释说明「少了这一条就点不动」。
- **报告用处**：这是「**平台特性会静默吞事件**」的好例子 ——
  和 P-068 一样属于「不报错但不对」。演示前值得专门点一遍顶栏上的每个控件。

## P-070 `nav: false` 的页面在没有 router 的项目里等于「点不到」

- **现象**：`knowledge`（教材知识库）与 `dependency`（依赖图谱）两页代码完整、
  后端接口也接好了，但**界面上没有任何入口** —— 全仓 grep 只有 `App.vue` 的渲染分支，
  没有一处导航到它们。而「教材知识库」里恰好有**导入教材 / 重建索引**两个真功能。
- **根因**：这两页的设计来源（原型）是 **router 驱动**的，`nav: false` 的语义是
  「不进侧栏，但可以直接改哈希进去」。本项目按 D-040 **不装 router**，
  于是 `nav: false` 的那个「另一条入口」根本不存在 —— 语义被搬过来了，实现没有。
- **解决**：改成进侧栏（「学习数据」组），并在 `PageMeta.nav` 的注释里写死这条纪律：
  **`nav: false` 的页面必须有别的入口，否则等于点不到**。
- **报告用法**：
  ① 「**从一个框架搬到另一个框架时，语义会带着、实现不会**」——
     这类 bug 不会在编译、测试、构建里露头，只有「人真的去点一遍」才发现；
  ② 也说明「做了却没有入口的功能等于没做」：导入/重建是这份交付里少数的**写操作**，
     藏在点不到的页面里，等于演示时讲不出来。

## P-071 抬字号会**连锁**触发三类布局坏掉，而且都不报错

- **现象**：把字号阶梯整体从 14px 基准抬到 16px 之后，出现三类问题：
  ① 右栏降级链的**第一档比其它三档高一倍**，且它的状态标签「本轮未检索」飘在两行之间；
  ② 输入条上的模型 chip 文字被**裁掉一半**；
  ③ 浮窗上的图标按钮显得**点不准**（但它本来就只有 24px）。
- **根因**（三类各不相同，都不是字号的错）：
  ① **窄栏里的 `align-items: center` 单行**：档位名一长就折行，而 `center` 会让
     圆点 / 档位名 / 状态标签**各自垂直居中** —— 于是状态标签落在两行之间，
     读起来像「这一档的状态到底是哪个」要猜。字号小的时候名字不折行，问题不存在。
  ② **固定高度装文字**：`.cp__model` 是 `height: 22px` + 13px 字 + 上下内边距，
     22px 是按旧字号（12px）定的 —— 字号一抬，盒子装不下，字被**裁掉**。
  ③ **图标按钮的可点区**：24px 在 12px 界面里算正常，字号抬到 13px 后
     它相对更小 —— 而它是**要按的东西**，不是标签。
- **解决**：
  ① 顶对齐（`flex-start`）+ 圆点用 `margin-top` 自己下移对齐首行 + 状态标签 `align-self: flex-start`；
     **同时把档位名压到最短**（「向量检索 · fastembed 本地」→「向量检索 · 本地模型」）——
     技术名词在这里没有信息价值，学生关心的是「本地 / 云端」这个区别；
  ② 去掉固定高度，改由 `padding` 撑开（字号再变也不会裁字）；
  ③ 抬到 28px，并写下判据：**图标按钮的可点区由「手指能不能按到」定，不由视觉定**。
- **报告用法**：
  ① 这是「**改一个全局变量会连锁影响三处不相干的布局**」的实例 ——
     字号不是孤立的样式值，它是所有文字容器的**隐含尺寸输入**；
  ② 三类问题的共同点是**都不报错**：CSS 没有「装不下」的异常，
     只有「看起来不对」。所以抬字号之后必须**逐页真的看一遍**，
     不能只看 typecheck 与测试（它们全绿，而这三种坏法一个都不覆盖）；
  ③ 也可以讲「为什么抬字号要连容器尺寸一起改」：
     只改字号等于让所有容器突然变紧，那不是「字变大了」，是「排版崩了」。

## P-072 ★★ 打包出来的安装包**携带着一个过期的 sidecar** —— 源码修好的 bug 在包里还活着

- **现象**：冷启动打包版（`dist/win-unpacked`），右栏稳定显示
  「读取失败（HTTP 500）：Internal Server Error」。换裸 sidecar 打同一个端点却是 200。
- **根因**：**两件事叠加**，两件都不报错：
  1. **sidecar 是独立打包的产物**（`server/dist/k12-agent-server/`，由
     `scripts/build_server.py` 生成），它**不随 `npm run build` 更新** ——
     那个命令只重建渲染进程与主进程的 JS。而 `npm run build:unpack` 只是把
     **磁盘上现成的那份** exe 拷进包里（`extraResources`）。
  2. 于是「改了 `server/` 但没重跑 `build_server.py`」= **包里跑的是几小时/几天前的后端**。
     实测：包里的 sidecar 是 **9-17 05:01** 的，而 P-063 的迁移修复是 **9-18 13:52**
     才进的源码 —— 那条 `database is locked` → HTTP 500 在源码里早就修好了，
     **在包里却一直活着**；同一份过期产物也缺 9-18 新增的 4 个知识库端点
     （实测打 `/api/knowledge/stats` 回 404）。
- **为什么它特别危险**：这是「**改了、测了、也过了，但交付物里没有**」。
  `npm test`（877 项）与 `npm run typecheck` **全部是绿的** —— 它们测的是源码。
  只有**真的去冷启动打包版**才会撞到。
- **解决（初版，只是纪律）**：改了 `server/` 就必须
  `cd server && uv run python scripts/build_server.py`（它自带 24 项产物自检）
  **再** `npm run build:unpack`。顺序不能反。
  ⚠️ 重打前先关掉正在运行的打包版，否则 `dist/win-unpacked` 里的文件被占用删不掉
  （报 `Device or resource busy`）。
- **★ 根治（见 P-074 / D-045）：把「记得先跑」变成构建链的一部分** ——
  `npm run build` 会先自动做一次「过期内重打」，`build:win` / `build:unpack`
  在装包**之后**校验**包里的那一份**的源码指纹，不对就非零退出。
  也就是说：**这个坑现在有自动拦路石了**，纪律不再是唯一防线。
- **报告用法**：
  ① 这是「**交付物 ≠ 源码**」最典型的一次 —— 讲工程纪律时非常好用：
     两条构建链（TS 与 Python）各自独立，**「我改好了」这句话对交付物不成立**；
  ② 也说明「测试全绿」的边界：877 项测试**没有一项**覆盖「包里的后端是不是最新的」。
     这类问题只能靠**真跑一次交付物**来发现，所以演示前的冷启动演练不是走过场。
  ③ ★ **更好的讲法**：先讲这个坑怎么被发现的（冷启动交付物），再讲**怎么把它变成不可能再犯**
     —— 「发现 → 加守卫 → 让人为纪律退场」。有自动拦截的坑才算真的修完，否则只是这次记得。

## P-073 冷启动时首屏取数必然早于后端就绪 —— 只发一次就会「就地定格」

- **现象**：打包版冷启动，顶栏永远写着「未配置模型」、侧栏「学段待判定」、
  右栏挂着「读取失败：sidecar 尚未就绪」。而**开发态复现不出来**（sidecar 早就起好了）。
- **根因**：sidecar 是**独立进程**，从启动到能应答要几秒；渲染进程一挂载就发首屏那批
  请求（侧栏昵称 / 模型 chip / 右栏画像）。打包态冷启动时 sidecar 还在初始化，
  这一批**必然先失败一次** —— 而它们只在自己那一处 `onMounted` 里发一次，
  失败之后**没有任何人重试**：状态就停在「读取失败」上。
- **解决**：抽 `composables/useOnBackendReady.ts` —— 立刻跑一次 + 在
  `sidecar.phase` 变成 `ready` 时**再跑一次**。用 phase 而不是定时轮询：
  它就是「后端可用了」的权威信号，不必猜要等 3 秒还是 10 秒。
  调用方只需保证幂等（本项目这些 `load()` 都带「已有数据就返回」的短路）。
- **报告用法**：
  ① 「**开发态跑得通 ≠ 打包态跑得通**」的又一例 —— 而且这次的原因恰恰是
     **两个进程的启动顺序**，这在单进程应用里根本不会出现；
  ② 也可以讲「失败要能恢复」：把失败就地定格，学生看到的是「这软件坏了」，
     而真相只是「没人再去问一次」。

## P-074 构建链的「顺序纪律」写在文档里 = 迟早会忘；写成代码才真的生效

- **现象**：P-072 的记录里写着「改了 `server/` 必须先跑 `build_server.py`，顺序不能反」。
  但这只是一句话：`npm run build:unpack` 照样能跑完、照样产出安装包，
  **包里的后端还是旧的**；下次换个上下文（或换个人）继续踩。
- **根因**：**构建系统不知道有两份产物**。`electron-vite build` 只管 TS 侧，
  `extraResources` 只是「把磁盘上现成的那份拷进去」——没有任何一步会问
  「这份 exe 是不是当前源码打出来的？」。
  文档能提醒人，但**不能失败**：它没有退出码。
- **解决（三块拼图，指纹算法只有一份）**：
  1. `server/scripts/build_info.py` —— 源码指纹：对「会进包的文件」按路径排序后做
     sha256（`app/` `scripts/` `packaging/` `knowledge/` `resources/` + `pyproject.toml` `uv.lock`；
     `resources/models/` 的 91MB ONNX **只记大小**；`tests/` `dist/` `resources/kb/` 不参与）。
     带 `FINGERPRINT_SCHEMA` 版本号：改算法即让所有旧产物失效。
  2. `server/scripts/build_server.py` —— **打包前**算指纹、打完写 `<dist>/build-info.json`，
     `--verify` 里断言「产物指纹 == 当前源码指纹」；新增 `--if-stale`（新鲜就秒退）。
     ⚠️ 顺序很关键：指纹必须在**起 PyInstaller 之前**算 —— 打完再算会把打包途中的改动
     一起认作「已包含」，那正是最危险的失败方向。
  3. `desktop/scripts/build-server.mjs` —— JS 侧**只调用** Python 取指纹并比对
     （自己再写一套哈希 = 两套算法迟早漂移，表现为「刚打过包却永远判过期」），
     并挂在 npm 脚本上：`build` 前置 `build:server`，`build:win`/`build:unpack`
     后置 `check:server:packaged`。
- **设计取舍（值得写进报告）**：
  ① **失败方向选对了**：缺 `build-info.json` 的旧产物一律判**过期** ——
     宁可多重打一次（几分钟），也不要「过期却判新鲜」（交付事故）。
  ② **`tests/` 不进指纹**：改个测试不该触发几分钟的重打包，否则大家会想办法绕过它。
  ③ **未提交的改动必须能让指纹变**：指纹哈希的是**文件内容**而不是 git commit ——
     若按 commit 判，那么「改了、没提交、直接打包」会被判成新鲜。
  ④ **逃生舱要响**：`K12_SKIP_SERVER_BUILD=1` 会打印警告后跳过 ——
     静默跳过正是这个机制要消灭的东西。
- **拦截证据**：机制上线后立刻对着**本机制之前**打出的产物跑校验 →
  ```
  ✗ server/dist/k12-agent-server 里没有可用的 build-info.json
  ```
  非零退出 —— 那正是 P-072 里那份「9-17 05:01 的旧 exe」会走到的分支。
- **报告用法**：
  ① 「**把人记住改成机器检查**」是本项目最值得讲的一条工程决策：
     所有靠人记的纪律都会在疲劳时失效，而构建链不会累；
  ② 可以顺带讲 ④ 的设计直觉：**能不让人绕过的机制才是机制** ——
     逃生舱必须有、但必须响（静默跳过等于没有守卫）。

## P-075 两个开关一叠加，构建联动的短路**静默失效**（`--if-stale --skip-verify` 每次都重打）

- **现象**：刚给 `build_server.py` 加好 `--if-stale`（新鲜就秒退），
  实测「无改动时跑一次」应该是 0.4 秒 —— 结果**每次都走完整打包**（54 秒），
  而且**一个错都不报**：它只是「没跳过」，看起来像「本来就该重打」。
- **根因**：短路写成了 `if args.if_stale and not args.skip_verify:`。
  我当时的思路是「`--skip-verify` 是**只打包**，那自然不需要判新旧」——
  但前端构建链的命令行里两个开关是**一起**给的，于是 `not args.skip_verify` 恒为假，
  **短路那一整段代码永远进不去**。
  真正的问题是**语义放错了位置**：`--if-stale` 的定义是「**不用干活就别干**」，
  它与其他开关是**正交**的（判新旧与「打完之后要不要自检」毫无关系），
  把它跟 `--skip-verify` 纠缠在一起，等于让一个开关悄悄否决另一个开关。
- **解决**：把短路提到**所有其他开关之前**独立判断，不再引用 `skip_verify`；
  并在 `server/tests/test_build_info.py` 加上源码级回归
  （`test_if_stale_short_circuits_before_other_flags`：断言短路条件里不得出现
  `skip_verify`、且必须真的有 `return 0`）。
- **为什么这类坑值得写进报告**：
  ① 它是**「功能加了但没生效」**的典型 —— 与 P-072 是同一个**大主题**（构建联动），

## P-076 ★★ 接真 Key 跑第一轮对话，学生看到的是带星号的句子（模型输出 Markdown，界面当纯文本渲染）

- **现象**：用临时 Key 接 DeepSeek `deepseek-flash` 跑通第一轮真对话，回答内容与学段语气都对，
  但正文长这样：
  ```
  **循环**，就是同一件事做完一遍，回到开头，再做一遍。
  生活里到处都是循环。
  ```
  —— 小学生读到的是**带星号的句子**。
- **根因**：`ChatMessage.vue` 渲染正文用的是 `{{ turn.text }}`（纯文本插值），
  而模型（实测 deepseek-flash）会**自然输出 Markdown**：`**加粗**`、空行分段、偶尔代码围栏。
  两端谁也不认为这是 bug —— 模型没说要用 Markdown（prompt 里没要求），
  界面也没说不支持；结果就是**把解析负担推给了学生**。
  这不是「格式不好看」，在 K12 场景里「孩子读到 `**`」属于硬伤：
  低龄学生读到星号会以为那是内容的一部分。
- **为什么之前所有测试都没发现**：全部单测喂的都是**我们自己造的** `turn.text`
  （纯中文短句），没有一份样本来自真实模型的输出。**只有接真 Key 才暴露**。
- **解决**：新写 `desktop/src/renderer/src/markdown.ts`（**纯函数**，输出结构化节点）：
  - 覆盖 `**粗体**` / `` `行内码` `` / 代码围栏 / 标题 / 列表 / 分隔线 / 空行分段；
  - **刻意不用 `marked` / `markdown-it`**：它们输出 HTML 字符串，要渲染就得 `v-html`，
    而正文是**模型生成的文本** —— 那等于在渲染进程开一个 HTML 注入面。
    本模块返回 `{blocks:[{runs:[{kind,text}]}]}`，由 Vue 用文本节点绑定，
    **一个字节的 HTML 都不会被解释**（XSS 面为零），且**零新增依赖**（断网可用）。
  - ★ **未闭合的标记原样保留**：模型逐字流式吐时 `**循` 这种中间态必然出现，
    此时吞掉星号会让学生看到「字在闪」——**宁可朴素，不可丢字**（宁可不加粗，不可少一个字）。
- **代价 / 风险**：
  - 只做**子集**（不做表格 / 图片 / 链接 / 嵌套列表）—— 课堂讲解几乎不用，
    且每多支持一种语法就多一份解析器要维护、多一处渲染要测；
  - 修这个 bug 时**顺手发现一段死代码**：源码里本来有个
    `if (bullet && !/^\s*\*\*/.test(line))` 的守卫去防「`**粗体**` 被当成列表」，
    但差分探针在 18 个样本上证明它**不可达**（`\s+` 已经排除了 `**`）——
    已删除，并补了一条测试钉住真实原因（是 `\s+` 在起作用，不是那个守卫）。
    留着一段「看起来在防御什么」的代码，会让后来人以为那里有坑。
- **防呆**：
  - `desktop/tests/markdown.test.ts`（14 条）：含**真实模型输出样本**的端到端断言
    （「无星号残留 + 一个字都没丢 + 加粗确实生效」三条同时成立 ——
    第三条专门防「把所有标记都删掉」这种假修复）；
  - 用**变异测试**验过不是空过：把 `parseInline` 改成直接返回原文 →
    4 条变红；把空行分段去掉 → 3 条变红；把未闭合标记改成「吃掉」→ 立刻崩。
  - `ChatMessage.vue` 的 `.text` 同步去掉 `white-space: pre-wrap`
    （换行现在由分段表达，留着会让「每行一个 `<p>`」与源文本换行叠成双倍行距）。
- **报告用法**：
  ① **「接真模型」是不可替代的一步** —— 这个 bug 在 585 项前端测试 + 904 项后端测试里
     一条都没覆盖到，因为测试样本是我们自己写的，而**模型的输出习惯不是我们定的**；
  ② 顺带能讲「为什么不用现成 Markdown 库」：**安全边界**（正文是模型生成的不可信文本，
     `v-html` 等于开注入面）与**零依赖**（断网演示）两条理由都很实在；
  ③ 也是「AI 输出要做**容错**而不是**严格解析**」的好例子：未闭合标记原样保留这条规则，
     正是从「流式输出的中间态」推出来的。

## P-077 动画的托管 nonce 是一次性的、120 秒过期 —— 卡片宁可降级也不肯用它手里的内联 HTML

- **现象**：打包/开发态跑过一轮对话后，动画卡片显示「动画没能加载，已用文字讲解」。
  查 sidecar 日志看到两种拒绝：
  ```
  WARNING app.routes.resources: 动画资源被拒：… 原因=used
  WARNING app.routes.resources: 动画资源被拒：… 原因=expired
  ```
- **根因**：动画 HTML 有**两条**下发路径（票 16 的设计）：
  ① **托管地址** `<iframe src=...?nonce=...>` —— 一次性 nonce，**TTL 仅 120 秒**；
  ② **内联 `srcdoc`** —— 完整 HTML 就在事件载荷的 `html` 字段里。
  卡片平时优先走 ①。可一旦 iframe **重新加载**这个地址（应用重启后回看历史、
  组件被重建、HMR 热更新），后端按设计拒收（`used` / `expired`），
  而**旧实现的失败处理是直接进降级视图** —— 明明手里握着完整的 ②，却告诉学生「动画没能加载」。
  即：**一次性资源 + 一次性加载**是配对假设，而「重新加载」在这套 UI 里是常态。
- **为什么它比「普通 bug」更值得记**：它**不是崩溃**，而是**静默降级**：
  卡片显示得体的「已用文字讲解」，学生不会报错，老师不会发现 ——
  只有对比「这里本该有个动画」的人才知道丢了东西。
- **解决**：失败处理改成**先回退、再降级**（`AnimationCard.vue` 的 `handleFailure`）：
  - 托管路径失败 → 把数据源切回**内联 HTML** 重建宿主（`useHosted=false` + `fellBackToInline`
    防来回重试），iframe 用 `:key` 换一个元素（只改同一个元素的 `src`/`srcdoc`
    不保证重新导航）；
  - 回退后**仍**失败（超时 / 沙箱自报错）才进降级视图 —— 降级仍是终态，**绝不白屏**；
  - 载荷里没有内联 HTML 时不进回退分支（不绕圈）。
- **防呆**：`desktop/tests/animation-extension.test.ts` 的
  「★★ 托管路径失败必须先回退内联 HTML」（源码级断言）。
  ⚠️ 这条测试**两次差点写歪**，都值得记：
  ① 第一版用 `onTimeout:[\s\S]{0,220}?handleFailure\(` 这种**宽松字符窗口** ——
     把回调体改回 `goDegraded(...)` 仍能匹配（窗口一路吃到下面 `onError` 里的
     `handleFailure`），**测试假绿**；改成贴着回调体取才抓住。
  ② 第二版切片锚点写 `\n`，而仓库工作区的 `.vue` 是 **CRLF** ——
     锚点匹配不到，`errorBody` 一路切到文件尾，于是「不得出现 goDegraded」的断言
     去扫了整份源码，**测试假红**。归一化换行后才对。
  最终三个反例（去掉回退分支 / 超时跳过回退 / 自报错误跳过回退）**实测全部变红**。
- **报告用法**：
  ① 「**一次性资源 + 常态重载**」是一类可复用的设计错误 —— 提问方式很简洁：
     「这份资源会被加载几次？」；
  ② 更能讲的是**两次测试写歪的经历**：假绿（窗口太宽）与假红（换行符）都是
     「测试看起来在把关，其实没把住」。**守卫要验证会红**这句话不是口号，
     是本项目真花时间做过的事（同一个坑在 `brand.test.ts` 的 G19-3e 上也验过一次）；
  ③ 顺带能讲「降级设计得越得体，越需要自动断言」——
     产品越优雅，静默丢失越难被发现。

## P-078 ★★ 自动滚动靠**手写依赖清单** → 引用块出现时视图掉队 759px（用户点名的那个问题）

- **现象**（用户原话）：「生成最新消息的时候自动滚动到最新一条，而不是在原来的消息傻傻呆着」。
  粗粒度看代码：「有 watch、有 scrollToBottom、最后也确实到底了」—— 像是好的。
- **根因**：滚动由一份**手写的依赖清单**触发：
  ```ts
  watch(() => `${轮数}:${最后一轮正文长度}:${卡片数}`, scrollToBottom)
  ```
  而「会让内容长高的东西」远不止这三样。用 CDP 逐类内容量了一遍，
  **引用块没被算进去**：一次插入 **376–663px**，视图**掉队 663–759px**
  （探针：`scripts/ux-scroll-probe3.mjs`，按「高度增长了但没贴底」筛采样并归因到具体区块）。
  另有第二处：`历史会话/新会话` 之后 `stick` 状态残留，学生看到的是「空屏在长」。
- **为什么粗粒度断言发现不了**：`ux-audit.mjs` 的初版只断言「回答结束时离底部 ≤8px」——
  而**引用块在正文之后到达、之后再无内容时，最后那次 scrollToBottom 会把一切抹平**。
  掉队只发生在过程中（几百毫秒到数秒），最终态是好的。
  **只看终态 = 把过程里的缺陷全部掩盖**。改成「流式期间持续采样、任一次 >24px 即失败」才抓到。
- **解决**（三件事，缺一不可）：
  1. **不再手写清单**：`ResizeObserver` 直接观察内容容器 —— 不管是谁把高度撑大的
     （正文 / 引用 / 提示 / 卡片 / iframe / 图片）都会触发，**新增内容块不需要来登记**；
  2. **跟随要有开关**（`stick`）：学生主动往上翻 → 停住不动 + 露出「回到最新」。
     无脑跟随与完全不跟随**都是缺陷**：前者让人没法在回答生成期间重读；
  3. **发新消息强制恢复跟随**，且这条**同时覆盖排队自动发出的那条** ——
     排队消息由 store 自动发出、**不经过组件的 `onSend`**，只挂在 `onSend` 上会漏
     （实测 B1 掉队 1527px）。用 `watch(turns.length)` 兜住「新轮次开始」这个**离散事件**。
- **★ 「依赖尺寸」与「依赖事件」的区别**（守卫的判据就建在这上面）：
  `turns.length` 是**离散事件**（一轮 = 一次提问，语义明确、必然触发）；
  `text.length` / `cards.length` 是**尺寸代理量** —— 想用它们覆盖「所有会长高的东西」永远会漏。
  所以守卫放行 watch，但只放行依赖 `turns.length` 的那种，并**禁止** `text.length`/`cards.length`/`scrollHeight`。
- **防呆**（`tests/ux-queue-and-scroll.test.ts` 的 4 条 + 真机 7 项）：
  - 真机：探针 ①②③④ 共 7 项（贴着底不出现按钮 / 翻上去停住+出现按钮 / 点击回到底部 / 发消息跟随）；
  - 源码级：ResizeObserver 回调里必须真的 `scrollToBottom()`；所有 watch 逐个检查依赖形态。
  - ★ **变异测试**：把 `showJump` 改回「只在 ResizeObserver 里设置」→ 立刻红
    （这正是初版修复的真实缺陷：学生往上翻时**没有任何内容增长**，
    观察器不触发 → 按钮永不出现 → 「停住不打扰」变成「停住且没有回去的路」）。
- **报告用法**：
  ① ★ **这是「用户报的现象 + 我写的粗粒度测试说没事」的经典对峙** ——
     最后靠「按内容类别拆开量」定位。教训很硬：**测试通过 ≠ 现象不存在，
     可能只是测的粒度不对**（终态 vs 过程）。这条几乎是本轮最有说服力的一段；
  ② 能讲「好的滚动是**双向**的」：跟随新内容 + 不打扰阅读，两者都要有，
     而「回到最新」按钮正是后者的配套 —— **停住却没路回去 = 卡住**；
  ③ 也能讲「离散事件 vs 尺寸代理量」这个可复用的判断标准。

## P-079 ★ 回答生成中按 Enter **零反馈** —— 消息丢了、也没人告诉学生为什么

- **现象**：学生在读回答的过程中把追问打好了，回车想再问一句 —— **什么都没发生**：
  输入框里的字还在，轮次数不变，界面上没有任何提示（探针 `scripts/ux-probe-busy-send.mjs` 实测）。
- **根因**：`stores/chat.ts` 的 `send()` 开头是
  `if (text.length === 0 || streaming.value) return` —— 忙的时候**直接丢弃**。
  唯一的线索是发送键被禁用 + `title="正在回答…"`，而 `title` 要**悬停**才看得到
  （触屏上等于不存在）。
- **学生体感**：不是「上一个回答还在生成」，而是「**键盘坏了 / 软件卡了**」。
  更糟的是他会**反复按回车**（每次都一样没反应），最后放弃这个动作。
- **解决**：**排队**（`queuedText`）。理由 —— 「不许并发」的理由仍然成立
  （两轮 delta 会交织在同一个气泡里），但**「不许发」不等于「按了没反应」**：
  - 忙时按发送 → 进队列，**输入框清空**（字已被接收的可见证据在排队条上）+ 露出「待发送：…」条；
  - 回答讲完 → **自动发出**（用「之前流式 → 现在不流式」这个**边沿**判定，不是「现在不流式」这个状态 ——
    后者会在每个非流式事件上误触发，把队列提前发出去）；
  - ⚠️ `error` 结束时**也要发**：出错的是上一轮，不该连坐；
  - 只保留最新一条，且**被替换的那条要说出来**（静默替换 = 把学生刚敲的字扔掉）；
  - 「取消」要把内容**还回输入框**（那是他自己敲的，不是我们替他删的）。
- **防呆**：`tests/ux-queue-and-scroll.test.ts`（含「排队赋值必须在任何 return 之前」
  「边沿判定」「不得绑死在 done 上」）+ `ux-audit.mjs` 的 G1/G2/G3 真机三项。
  同样过了变异测试：在忙分支开头插一个 `return` → 立刻红。
- **报告用法**：
  ① 「**静默丢弃是交互设计里最贵的省事**」—— 保存一行代码，代价是学生以为自己设备坏了；
  ② 可以对比讲两种修法的层次：「弹一句『请稍等』」只是把问题还给学生，
     **排队**才是把他的意图接住 —— 而且判据要用**边沿**而不是状态，这是个能讲出深度的技术点；
  ③ 与 P-078 同属「交互时序」，可以合并成一段「**流式界面的人因工程**」。

## P-081 ★★ 编程页把**后端的排障文案**原样摆给小学生看（HTTP 404 + 内部 kp_id + 服务器路径）

- **现象**（逐页体检的第一屏，编程页的**默认状态**）：
  ```
  读取失败（HTTP 404）：知识点 'pl-ai-around-me' 还没有预置代码模板。
  ```

  即：**一句话的受众错了**——写的人和用的人不是同一群人。
- **为什么它会「活到今天」**：所有测试都只断言「有没有报错」「错得对不对」，

  - 判据用「像不像技术信息」（含 `HTTP` / `server` / `/api/` / `kp_id` / `traceback` / 引号包住的 kp_id），
    **不是**精确匹配某一句（后端文案会变，特征更稳）；
  - 命中 → 换成「这道题还没有配套的代码模板。换一个知识点试试，或者先让团团用文字讲讲。」
    （**告诉学生下一步做什么**，而不是报告系统状态）；
  - **原文进 `console.warn`**——开发和老师排障时仍然看得到，只是不摆给孩子。
  - ⚠️ 两条失败分支（后端返回失败 / 抛异常）**都要过这个翻译**，漏一条就等于没修（守卫钉住数量）。
- **同类风险面**：其余六个页面扫下来**没有**这个问题（它们要么没失败态、要么文案本来就是可读中文），
  所以只改了编程页 —— **不为「统一」去改没出问题的地方**。
- **防呆**：`tests/ux-pages-regression.test.ts`（判据要含技术词特征 / 两条分支都要翻译 /
  不得出现 `templateError.value = result.message`）+ `ux-pages-audit.mjs` 真机扫「界面上是否出现技术词」
  （这条对**所有页面**生效，是防止同类回归的通用闸门）。变异测试：改回直出 → 4 条断言变红。
- **报告用法**：
  ① 「**同一句话，受众不同就该是不同的话**」——这条对 AI 产品的启发尤其大：
     模型输出、后端错误、日志，三者的读者都不一样，**不能共用一份字符串**；
  ② 也说明为什么 UX 体检要**逐页走一遍**：这个缺陷在对话页永远看不到，
     而编程页是学生真正会打开的一页；
  ③ 顺带能讲「扫特征而不是匹配句子」——后端文案改了，这条守卫照样有效。

## P-082 ★ 「回到最新」浮标**压住输入框 17px**（魔数定位；CDP 数字检查全过、只有量几何才发现）

- **现象**：`回到最新` 用 `position: absolute; bottom: 92px`（相对整个 `.chat`）定位。
  实测按钮下边缘 **810px**、输入条上边缘 **793px** → **重叠 17px**。
  学生想点输入框，点到的是浮标，然后**被滚到底部**——他不知道刚才发生了什么。
- **为什么它躲过了所有检查**：`ux-audit` 当时查的是「按钮存在吗」「点得动吗」「位置比底部高吗」，
  全都通过。**「两个元素是否重叠」是一个需要主动去量的关系**，
  不存在于任何单个元素的属性里 —— 只有 `getBoundingClientRect()` 互相比较才能发现。
- **解决**：
  - 把「浮标 + 待发送条 + 输入条」包进一个 `.chat__foot`（`position: relative`），
    浮标改成 `bottom: calc(100% + 8px)` —— **相对底部区**定位，与输入条实际多高无关；
  - 于是输入条变多行、待发送条出现时，浮标自动上移，**任何高度下都不会重叠**；
  - 魔数（92px）的另一个毛病也一并消失：它是按「输入条大约 92px」试出来的，
    **输入条一换行就失效**。
- **防呆**：`ux-audit.mjs` 新增 **H1**（量矩形、逐对判断是否相交）+ **H2**
  （要求与下方控件留 ≥4px 余量 —— 仅仅「不重叠」不够：贴边在视觉上像粘住，
  而且 DPI 取整一变就可能变成重叠）。变异测试：改回 `bottom: 92px` → H1 立刻红并**报出重叠对象与像素区间**。
- **报告用法**：
  ① 「**数字全对但界面是坏的**」的一个具体案例：元素存在、可点、尺寸达标，
     但它们**互相压住** —— 这类问题只能靠「量关系」发现，靠「查属性」永远找不到；
  ② 也是「**布局魔数**」的经典教训：任何按「另一个元素大约多高」写死的偏移，
     都会在内容变化（换行、加一行）时变成缺陷；能用相对定位就别用魔数。

## P-083 ★ 一批可点元素低于触控下限（散布五六个页面，逐页改会漏）

- **现象**：逐页体检量出多处 <28px 的可点元素：
  Element Plus 的单选框（22px）、分段控件（19px）、表格列头的排序按钮（24×14）、
  设置页的模型候选与选项（27px）、手写按钮（24px，五个卡片各自定义了一份 `.btn`）。
- **根因**：字号在 D-043 整体抬升过（12→13/14px），但**承载它们的容器尺寸没跟着改** ——
  padding 还是按旧字号定的（这与 P-071「抬字号连锁触发三类布局坏掉」同源）。
  更要紧的是**散落**：五份 `.btn`、每个页面的 chip 各自写 padding，改一处漏一处。
- **解决（分层，而不是逐页调）**：
  - Element Plus 组件 → 在 `assets/base.css` 的 **EP token/组件层**统一 `min-height: 28px`
    （`.el-button` / `.el-radio-button__inner` / `.el-segmented__item` / `.el-check-tag` /
    `.el-table th .caret-wrapper`）——**改一处全站生效**，新增 EP 组件自动继承；
  - 手写按钮 → 新增共享工具类 **`.k12-tap`**，并把「为什么是 28px」写在那一条规则上。
- **★ 28 而不是 44 的理由（必须写下来）**：本项目是**桌面应用**，精度由鼠标/触控板决定；
  照搬移动端的 44px 会让界面明显变松散。28px 是「不费劲点得中」的桌面阈值。
- **⚠️ 量法本身踩过坑（两次）**：
  ① **假阳性**：直接量 `<input type="radio">` 会得到 13×13 —— 那是它画的小圆点，
     学生实际点的是包着它的 `<label>`（46×22）。第一版据此误报了三个页面，白改一轮。
     现在改成「往上找 label / role=button 容器」，量**有效**可点区域。
  ② **判据过严**：一开始要求两维都 ≥28px，于是列头那个 24×28 的排序按钮被判过小 ——
     但它是**竖向**目标（高够就能点中），硬把宽顶到 28 只会让表头多出无语义的空白。
     现在改成「两维较小者 ≥20 且较大者 ≥28」。
- **防呆**：`ux-pages-audit.mjs` 的「可点目标不小于 28px」（逐页跑）+
  `tests/ux-pages-regression.test.ts`（钉住「必须在设计 token 层」+ 一律用 `min-height` 而非 `height`）。
  变异测试：删掉 `.k12-tap` 与 EP 下限 → 2 条断言变红。
- **报告用法**：
  ① 「**量法本身也会有 bug**」——这段最值得讲：同一个「触控目标过小」的结论，
     量法对了才发现其中一半是假阳性。**先怀疑量法，再改产品**；
  ② 「设计 token 层修一次 vs 逐页修六次」是工程判断的直观例子：
     后者不仅慢，还会漏，而且**下一个新页面会重新踩一遍**。

## P-084 ★★ 章分片题库被**整文件静默跳过** —— 覆盖率掉到 0/228，而日志只多一行字

- **现象**：把题库从「一学段一文件」改成「一章节一文件」（8 份 `ch01.json`…`ch08.json`）之后，
  `load_bank()` 报 `skipped: ['ch01.json: grade_level 非法（'''')…']` —— **八份全被跳过**，
  `entries` 仍是旧的 81 题。表现是「出题功能看起来正常，但新教材一道题都没有」。
- **根因**：`load_bank()` 在**文件级**读 `raw.get("grade_level")`，不在 `GRADE_LEVELS` 里就
  `continue`（整文件跳过）。而章分片**一个文件横跨四学段**，结构上给不出这个键 ——
  每题的学段只能由它自己的 `kp_id` 后缀决定。
  ⚠️ 我（主协调者）在派活时指定的 schema 就是章分片，等于**自己埋了这个雷**；
  四个并行子代理独立撞上同一条，各自用「拆成临时文件只加一个键」证明题目本身干净。
- **为什么危险**：`load_bank` 对坏数据的设计是「**只跳过、不抛异常**」（为现场演示做的取舍），
  于是这个「整库为空」的错误**不报错、不崩溃**，只往 `skipped` 里塞一行字。
  没有测试盯着 `skipped` 就永远发现不了 —— 而它比崩溃更糟：崩溃至少会被看见。
- **解决**：`load_bank()` 判据改成「文件级学段 **或** 章分片」二选一：
  ```python
  is_chapter_shard = declared_grade not in GRADE_LEVELS and bool(raw.get("chapter"))
  ```
  章分片里每题的学段用 `grade_from_kp_id()`（`-pl/-ph/-jr/-sr` 后缀）推导；
  **推不出来就跳过并报告，绝不默认成某个学段**（硬塞默认值会让学段隔离开天窗，
  小学低年级的题可能被当成高中的）。修完 684 题全部载入、`skipped` 为空、
  四个学段各 171 题。
- **★ 顺带暴露的第二处（同一类错误）**：`COLD_START_LEVEL_SEEDS` 还指向已删除的旧 kp
  （`pl-ai-around-me`），冷启动种子会全部落空。已按学段改成 `ai-definition-{pl,ph,jr,sr}`。
- **防呆**：`test_quizbank_coverage.py` 新增 `TestBankReadsBothShardForms`（5 条）——
  两种形态各自能读、**并存时都能读**、**`skipped` 必须为空**，
  并附一条**反向用例**（kp_id 没有可识别后缀的章分片**必须**被跳过且被报告）。
- **报告用法**：
  ① 「**只跳过、不抛异常**」是一种有意的取舍（为了演示不中断），但它把「灾难性错误」
     降级成「一行日志」。凡是选了这个取舍的地方，**都必须有一条盯着「跳过了什么」的断言** ——
     否则守卫只防住了崩溃，没防住静默失能；
  ② 也说明**并行子代理的价值**：四个人独立撞上同一条并各自给出可复现证据，
     比我一个人按顺序做更容易确认「这不是某个文件的写法问题，是加载器的缺口」。

## P-085 ★★ 关卡路径按「兼容学段」取，导致**高中生的 40 关里 0 关是自己的课**

- **现象**（迁移后实测）：冷启动后看四个学段的关卡路径 ——
  `primary_low` 40 关 / 其中本学段 40；`primary_high` 17/57；
  **`junior` 只有 4/57**；**`senior` 0/57**。
  即「我上高中了，进度里全是小学低年级和初中的课」。
- **根因**：`_default_level_order` 用 `_allowed_grades()`（本学段 + **更低**学段）当路径范围 ——
  这在**旧教材**下是对的：旧库是「一学段一本教材」，各学段的图互不相通，
  兼容范围只是个并集，拓扑序排出来的仍然是学生自己学段的内容（占多数）。
  而新库把概念串成了 **`X-pl → X-ph → X-jr → X-sr` 的跨学段加深链**：
  拓扑序要求**前置先出**，而前置就是更低学段 → 于是越低学段的内容越排在前面，
  40 关的配额被更低学段占满。
- **为什么这条特别值得记**：**测试全绿**。原有用例盯的是
  「路径里不得出现高于学生学段的关卡」+「每一关都取得到题」——
  两条都成立（低学段内容当然取得到）。**没有任何一条断言问「这条路径配得上这个学生吗」**。
  这是「**断言全对，功能是错的**」的典型：守卫覆盖了隔离，没覆盖配比。
- **解决**：把两个概念**明确分开**（这才是真正的一步）：
  - **关卡路径 = 本学段**（`_default_level_order`）—— 回答「我现在该按什么顺序练」；
  - **取题 / 检索 = 兼容学段**（`_allowed_grades` 不变）—— 学生随时可以回头取更低学段的题。
  ⚠️ **前置只在本学段内算数**：同一概念的低学段版本对高学段学生而言是「已学过的基础」，
  不该挡住他。新库每个学段的子图各自连通（实测四学段都 57/57 可达、各 6 个根），
  所以按本学段取路径不会丢内容。修完：四学段各 40 关、首关都是自己的
  `ai-definition-{pl,ph,jr,sr}`、取题 404 = 0。
- **代价 / 风险**：夹具里「跨学段的那一对」不再出现在路径里，
  `TestGateD` 改用同学段的一对真实边（`ai-hierarchy-jr → deep-learning-jr`）。
  这是**有意的**：跨学段那条边本来就只剩「取题兼容」这一个语义。
- **报告用法**：
  ① ★ **「测试全绿 ≠ 功能对」的最锋利的一个例子** ——
     原守卫问的是「有没有越界」（隔离），而功能错的是「配比」（该练什么）。
     排查提示词很值得记住：**「这些断言里，有哪一条在问『这对吗』而不是『这对得上吗』？」**
  ② 也说明**换数据会暴露旧假设**：旧库「一学段一本教材」这个隐含前提从没写进任何断言，
     但它在两处代码里被默默依赖（路径范围 + 冷启动种子），换库时才浮出来。
     事后看，把「路径范围 = 本学段」当独立常量命名，比让它跟着 `_allowed_grades` 走更稳。

## P-087 ★ 界面上的「错误显示」有四种形态，全都**只在真机截图里**看得见

- **现象**（本轮逐页截图抓到的四处，全部与「数据错不错」无关，而是**画出来错了**）：
  1. **被裁出省略号**：知识库表格「学段」列 `width=96` 而内容需要 111px →
     渲染成「小学低年级 …」；那个省略号既不是数据也不是任何标题，看着像界面坏了。
     同表「知识点」列 `min-width=150` 而最长的一条需要 ~222px，被裁成
     「教学短板（难自动分层适…」—— 知识点名是这一列的全部意义，裁掉等于没显示。
  2. **被浮层盖住**：依赖图谱的检查器是 absolute 浮层（设计上不占画布宽度），
     而节点行是 `flex-wrap` —— 节点流到它底下被盖住，卡片只露一半、
     kp_id 被裁成「algor…」。
  3. **被更高层压住**：顶栏学段气泡锚在顶栏右缘（x=1179），而右栏从 x=1152 起铺 ——
     气泡右边 27px 被右栏盖住，看到的是**缺一角的绿纸片**。
     ⚠️ 文字恰好完整，**只读文字永远发现不了**，只有量矩形才看得见。
  4. **两处真相导致的错位**：右栏硬写 `width: 288px` 而设计令牌 `--k12-w-rail` 是 300px。
     气泡按 300 算右边界、右栏按 288 铺 —— 差 12px 的账对不上。
     单看两边代码都「没错」，错在它们**不是同一个数**。
- **为什么这些都是「静默」的**：没有报错、没有崩溃、元素也都在（`getBoundingClientRect`
  有正尺寸）—— `verify-ui.mjs` 那类「元素在不在」的断言全过。
  它们只违反一件事：**画出来对不对**。
- **解决**：四处都按**内容/关系**而不是「大概够」来定：
  列宽按最长内容的实测宽度、浮层避让用**同一个变量**算、气泡改用视口定位 + 令牌让开右栏、
  右栏宽度统一读令牌。
- **★ 量法（值得抄）**：`clipped = scrollWidth > clientWidth+1`（裁切）、
  两两 `getBoundingClientRect()` 相交（覆盖/压住）。判据都是**关系**，
  不是单个元素的属性 —— 后面这类只能主动去比。
- **报告用法**：
  ① 与 P-082（浮标压输入框）同属「**几何关系**」这一类：不存在于任何单个元素的属性里，
     只能靠「取多个矩形互相比较」发现；
  ② 「**两处真相**」那一条尤其值得讲：它不是 bug 而是**设计缺陷** ——
     同一个量（右栏宽度）在两个文件里各写一遍，两边单看都对。
     凡是「同一个数出现在两处」，迟早会对不上。

## P-088 ★★ 修「单列被裁」时把**总宽**撑破了 —— 元素叠加的约束不只一条

- **现象**（三视口走查抓到）：知识库里表格「向量」列的表头被切成只剩一个「向」字，
  而且整条表头与表体**横向错位**；表体里的「已嵌入」标签也只剩半个。
- **根因**：上一轮修「学段列 96px 放不下『小学高年级』标签」时，我把
  学段列 96→120、知识点列 150→180，**每一列单独看都更对了**，
  但七列之和从 934 变成 988，超过了最紧那一档的可用宽度（**929**）。
  而 **Element Plus 在横向溢出时表头不跟着表体收**：表体被压到 929、表头仍是 988，
  于是表头被裁、且与表体错位。
- **★ 两个反直觉点（都踩了）**：
  1. **最紧的一档不是最窄的窗口**：1120 下右栏会**自动收起**，内容区反而更宽（1052）；
     真正最紧的是 **1280 + 右栏展开**（929）。「窗口越小越紧」是错的直觉。
  2. **修一个约束会破另一个约束**：列宽的约束有两条 ——
     「放得下最长内容」与「总和不超过可用宽度」，它们**方向相反**。
     只盯前者，就会像这次一样把后者撑破。
- **解决**：列宽收到 926（≤929）；长文本改成 `show-overflow-tooltip`
  （**明说被截断**，悬停看全文）。取舍写进了代码注释：
  「截断至少是明说被截了，而表格横向溢出会让**表头被切掉一半**（更坏）」。
- **防呆**：`ux-pages-regression.test.ts` 断言**列宽总和 ≤ 929**（而不是逐列对数字），
  并断言两列都开了 tooltip；变异验证：把列宽加回去 → 立刻红。
- **报告用法**：
  ① 「**约束不只一条，而且方向相反**」是工程里极常见的坑，
     值得单独讲一句：修 A 之前先问「这条约束的另一头是什么」；
  ② 「最紧的一档不是最窄的窗口」也可以直接讲成一条经验：
     **响应式的边界要实测，不要推理**。

## P-089 ★ 「刚好放不下」会被渲染成**从中间裁断**，比省略号糟得多

- **现象**：动画模板卡的学段标签，第 4 档「初中」只显示**上半截**，
  看起来像「初十」——不是缺字，是把一个字**横向切了一半**。
- **根因**：`.tpl__grades` 是 `flex-wrap: nowrap` + `overflow: hidden`。
  新库里出现了**四学段全适配**的模板（如「机器学本事：数据 → 训练 → 预测」），
  四个标签一行放不下，于是第四个被容器边缘**生生切断**：
  **没有省略号**（那需要 `text-overflow: ellipsis` + 单行）**也不能滚**
  （`overflow: hidden` 而非 `auto`）—— 学生完全不知道自己漏看了一档学段。
- **为什么它比省略号糟**：省略号是在**明说**「这里还有内容」；
  半截字则是在**伪装**成完整内容（「初十」看起来像个词）。
  信息丢失得**无声无息**，这比信息丢失本身更危险。
- **解决**：`flex-wrap: wrap`。卡片高度本来就随内容撑，`nowrap` 在这里没有收益 ——
  换行是唯一正确的表达。
- **★ 判据（可复用）**：区分三种「放不下」——
  `overflow: auto/scroll` = 用户能拿到（可接受）；
  `text-overflow: ellipsis` = 明说被截断（可接受）；
  **`overflow: hidden` + 没有省略号 = 内容永久不可达**（必须修）。
  走查脚本一开始把前两种也算成问题，误报一整轮才收敛到第三种。
- **防呆**：`ux-pages-regression.test.ts` 钉住 `.tpl__grades` 的 `flex-wrap: wrap`，
  并断言不得出现 `overflow: hidden` 与 `nowrap`。
  ⚠️ 该守卫**写错过两次**（都值得记）：
  ① 取规则体不能用「后一个选择器」当终点 —— `.tpl--on .tpl__grade` 在文件里
     比 `.tpl__grades` **更早**出现，切出来是空串；
  ② 断言前必须**剥掉注释** —— 那段注释里故意引用了坏写法（「原来是 nowrap + overflow: hidden」），
     不剥的话 `doesNotMatch` 会被注释绊倒、永远失败。
- **报告用法**：与 P-087 合成一句 ——「**元素的属性都对，但它们的关系是错的**」：
  这一条是「字被切一半」，P-087 是「被压住 / 被盖住"，都属于**只能量关系**才看得见的问题。

## P-090 ★★ 两个下拉**既不能 Esc 也不能点外部关闭** —— 学生点开就收不回去

- **现象**（交互态走查抓到）：学段选择器与章节选择器，学生点开、看了一眼不想选、
  点别处希望它收起来 —— **它不收**。唯一出路是再点一次触发器，或者被迫选一个。
  不选的面板会一直悬在内容上方（截图里能看到它叠在「新会话」那一行上），
  学生很容易以为界面卡住了。
- **根因**：两条关闭方式**都没实现**。而且项目里**已经有** `useEscape`（6 个组件在用），
  这两个下拉恰好一个都没用 —— 这正是「同一件事拆两处实现」的必然结果：
  有人记得加 Esc、没人记得加点外部。
- **解决**：新增 `composables/useDismissable.ts`，把两条收成**唯一实现** ——
  它们是**同一个意图**（「我不选了」）的两种表达，必须一起给。
  三条实现细节（都有其所以然）：
  - 用 `pointerdown` 而非 `click`：点外部时若目标可点（另一个按钮），
    `click` 会「先执行它的动作、再关面板」，而学生往往只想关面板；
  - 挂 **capture** 阶段：冒泡阶段的 document 监听会被中途任何 `stopPropagation()`
    吃掉（组件里到处可能有），那时面板就**卡住关不掉**了；
  - **面板内与触发器上的点击必须放过**：前者交给面板自己关（选完就收），
    后者交给触发器 toggle（否则「点一下开、再点一下关」会失效）。
- **防呆**：`ux-pages-regression.test.ts` 断言两个组件都用了 `useDismissable`
  且模板里真的绑了 `panelRef` / `triggerRef`；
  并断言该 composable 里 `addEventListener('keydown')` 与
  `document.addEventListener('pointerdown', …, true)` **真的挂上**（不只是名字出现）。
  ⚠️ 最初写的是 `/pointerdown/` 这种「文件里出现过这个词」的宽松断言 ——
  把 `addEventListener('pointerdown', …)` 删掉、留个别处的字面量就能骗过（变异测试暴露）。
- **报告用法**：
  ① 「**两条本该一起给的关闭方式，分散在两处实现**」是很典型的工程问题 ——
     它不是「忘了写」，而是「**没有一个地方对它负责**」。
     修法也不是补上那一条，而是**把它收成一个实现**；
  ② 可以顺带讲 `pointerdown` vs `click` 那个取舍：它体现的是
     「**先想学生的意图，再选事件**」—— 点别处时他要的是「关掉」，
     不是「顺手再触发一次那个按钮」。

## P-091 ★★★ 冒烟脚本**自己补上了那个必需字段** —— 它测的是脚本，不是产品

- **现象**（全仓功能审查抓到）：闯关页**提交任何一题都失败**；编程页的「报错感知 + 三级求助」
  **整块失效**。而 `npm test` 与 `server/tests` 加起来 1546 项**全绿**。
- **根因**：两个 IPC 通道（`quiz:grade` / `code:run-hint`）从渲染进程转发到 Python 时，
  **没有补上 `studentId`**；而 Python 侧两个契约模型的 `student_id` 是**必填**，
  pydantic 是 `extra="forbid"`。于是每次提交都被 422 拒掉。
  真正要命的是**为什么没人发现**：
  - `wire-smoke.mjs` 直连 HTTP，而它**自己手写出了 `studentId`**
    —— 它替被测的那一层补上了本该由那一层补的字段；
  - `desktop/tests/` 里**没有任何文件 import 过 `handlers-data.ts`**（21 条数据面通道零覆盖）
    —— 渲染侧测试用假桥、后端测试用 TestClient，**两者之间那一层谁都没测**。
- **解决**：两个 handler 注入 `studentId()`（身份由主进程决定，不放进渲染进程可见的类型）。
  顺带把 422 的**数组形态** `detail` 认下来（原先只认字符串，导致学生看到英文 `Unprocessable Entity`）。
- **防呆**：新增 `desktop/tests/data-plane-forward.test.ts`（18 条），用**假 request**
  捕获真正发出的 path 与 body，钉住「身份由主进程决定（载荷里塞 `studentId: 'attacker'` 被忽略）」
  「题库学段由主进程注入」「180s 长超时」「路径工厂的 snake_case 形状」四组断言 —— 这四组原先**全部零覆盖**。
- **报告用法**：这是全篇**最有方法论价值**的一条，可以放在「测试测的是什么」那一节：
  ① 「**覆盖率不是问题，被测对象错位才是**」——假桥测前端逻辑、TestClient 测后端逻辑，
     中间那层转发是**两者都假设对方会测**的地方；
  ② 「**验证脚本自己补齐了必需字段**」是一个非常隐蔽的自欺形态：
     脚本越「贴心」，它离真实客户端就越远；
  ③ 修完之后 `smoke:wire` 从 14/21 变成 **21/21** —— 这条链路第一次被真的连起来跑过。

## P-092 ★★ 「降级提示」被当成了「失败终态」—— 安全终审在最需要它的时候静默跳过

- **现象**：sidecar 没起来 / 断网 / 没配 Key 时，模型正文**未经任何审核**直接送到学生面前，
  而日志里写的是「本轮内容安全：生成侧终审 0 次」，看起来一切正常。
- **根因**：安全终审的门外层只看**事件名**（`error` → 标记本轮失败 → 跳过终审）。
  但 `events.ts` 把**工具失败**发成的是 `error{degraded: true}`，语义是
  「能力受限但本轮继续」—— 注释里写得很清楚：模型还会用文字把这一轮讲完，
  那两段正文必须继续送达。**两处对同一个事件的口径不一致**，
  于是「本轮还要继续讲」的那段正文落进了「已经失败、不用审」的分支。
- **解决**：门里改用与 `isTerminalTurnEvent()` **同一判据**（`degraded === false` 才算终态）。
- **防呆**：`safety-review.test.ts` 补**两条互补**断言 ——
  「degraded 的工具失败之后**仍然**走到终审」＋反向对照「真终态错误仍然跳过」。
  只写前者会让「所有 error 都不跳过」也能变绿。
- **报告用法**：**同一个事件在不同层有不同解读**，是异步事件流最常见的结构性缺陷
  —— 修法不是「加个判断」，而是**让两处共用同一个判据函数**。
  另外值得讲：这个缺陷的触发条件（断网、没 Key）恰恰是**兜底机制最该起作用**的场景。

## P-093 ★★ 两条「冻结契约」的守卫是**纸糊的** —— 同一行第二个字段、属性式方法都看不见

- **现象**（审查时用守卫**自己的提取函数**跑违规输入复现）：
  - 把 `ChatSendRequest` 从 `text: string` 改成 `text: string; gradeLevel?: GradeLevel`（TS 合法），
    G6c 仍只提取出 `['text']`，断言**通过** —— 而 G6c 是「学段绝不加回对话请求」的**唯一机器判据**；
  - 在 `K12Api` 里加 `readAnyoneProfile: (studentId) => Promise<unknown>`（箭头属性方法，
    在 `contextBridge.exposeInMainWorld` 下**真的会暴露出去**），G9 看不见它，
    方法数仍是 48，断言**通过**。
- **根因**：两个提取器都是**先按 `\n` 切、再要求标识符在行首** ——
  于是「同一行用分号分隔的第二个字段」与「属性式方法」天然不可见。
  另外 `interfaceBody` 要求右花括号顶格独占一行，**单行接口**整份都读不到。
- **解决**：成员切分改为 `split(/[\n;]/)`；方法正则同时认签名式与属性式；
  G9 增加「从 `api` **对象字面量**取键」这第二条判据（那才是真正暴露出去的集合）；
  `interfaceBody` 改花括号配平，并加一条「接口不得写成单行」的兜底断言。
- **防呆**：**变异验证**四步（改回坏写法确认变红）全部记录在案 ——
  仓库既有纪律「没验过会红的守卫不算守卫」在这里第一次抓出了**两条不合格的守卫**。
  ⚠️ 加固时必须先确认**现有期望值不变**（我实测 8 个被测接口没有行内 `;`、没有属性式方法，
  加固后 48 项与 `['text']` 原地通过）——否则就成了「为了让测试变绿而放宽期望」。
- **报告用法**：这是「**守卫测试本身也需要被测**」的最佳例子。
  可以讲成一句：**断言写得太宽松时，它比没有断言更危险** ——
  因为它会让人以为那条纪律已经被机器守住了。

## P-094 ★ 手动学段的「10 轮冷却」实际是 **1 轮** —— 冷却读的是一对**不同行**的 `(turn, source)`

- **现象**：学生点「我就是小学低年级」确认了学段，**两三**轮内系统就把它改走；
  更怪的是 `GET /grade/state` 说「还剩 10 轮」，`POST /grade/turns` 说「剩 1 轮」——
  **两个出口对同一状态给出互相矛盾的冷却值**。
- **根因**：冷却窗口的算法是「长度取自 `source`、已过轮次取自 `turn`」，
  而 `observe_turn()` 传给它的这两个值**来自两个不同的方法**：
  轮次号取 `last_change_turn()`（只认 `from != to` 的**真变更**行），
  来源取 `last_cooldown_anchor()`（认任何 `from_level` 非空的行，**包括**学生显式确认那一行）。
  于是学生确认学段写下的那条 `explicit` 行，**来源算进去了、起点却没算进去** ——
  冷却从更早那次真变更起算，早就过期了。
- **实测**（真库插入，非推演）：
  `inferred change @3` + `explicit confirm @12` → `state()` 报 10 轮，
  `decide()` 报 **1** 轮、@13 归零、@15 已经可以再改。
- **解决**：让冷却的 `(turn, source)` **来自同一行**；`last_change_turn` 降级为纯展示字段
  （它回答的是「上一次真正变更在哪一轮」，与「冷却从哪算」**不是同一个问题**——
  混为一谈正是缺陷本身）。参数也一并改名（叫 `last_change_turn` 就会有人往里塞真变更）。
- **防呆**：`test_grade_override.py` 补两条**走 `POST /api/grade/turns`** 的断言
  （原先那条是**假绿** —— 它只读 `state()`，而 `state()` 走的是**对**的那条路），
  外加一条「两出口必须给出**一致**的冷却值」和一条「重复确认要重新计时」。
- **报告用法**：与 P-093 合成一组 ——「**两个出口各算一遍，就一定会分叉**」。
  这里的教训是**命名**：把两个不同的「上一次」都叫 `last_change`，
  缺陷几乎是被名字诱发的。

## P-095 ★ 判分完全没有幂等 —— 同一道题连点 4 次就能通关

- **现象**：学生在闯关页对同一道题连点「再提交一次」，掌握度 0.15 → 0.6、
  关卡状态直接变 `mastered`、后继关卡全部解锁。徽章从「起步-1」一路刷到「精通-4」。
- **根因**：每次提交都无条件 `apply_mastery(±delta)` 并推进 `progress`，
  **没有任何「这道题是否已作答」的判据**（`learning_history` 只追加，
  `qid` 只藏在 `detail` 的 JSON 里，连索引都没有）。
  于是掌握度不再是「能力信号」而是「点击次数」，画像 / 推荐 / Prompt 全被污染。
- **解决**：**首次作答决定**（与用户确认的口径）—— 重复提交**照常判分并给反馈**
  （学生要看对错），但**不再改掌握度、不重复计数、不重复解锁**。
  三样东西的区别写进了 docstring：`learning_history` 照写（那确实是又一次作答），
  `progress` 与 `mastery` 不动。反馈文案明说「这次不计分」，**不撒谎**。
  ⚠️ 主观题尤其需要这一条：LLM 判分本身不稳定，同一份答案反复提交易靠分数抖动把掌握度推上去。
- **防呆**：新增「重复作答不动掌握度」「流水照写但徽章只加一次」「按 qid 而非按 kp 判幂等」
  三组断言，全部做过变异验证。
- **报告用法**：这是「**教育数据里，什么算『一次作答』**」的产品判断题 ——
  可以讲清为什么选「首次作答决定」而不是「首次答对才算」（后者会让「纠错成功」
  与「一次答对」在掌握度上等价，而掌握度是要拿去喂推荐算法的）。

## P-096 ★★ 重建教材**中途失败会留下半成品库** —— FTS 索引空了、依赖图没了，而学生只看到「重建失败」

- **现象**：重建教材时若中途抛异常（或**重建到一半关掉应用**），
  FTS 全文检索从 99 条命中变成 **0**、依赖边从 483 变成 **0**，
  而回执只有一句「重建失败」—— 学生看不出**旧教材已经被改坏了**。
  更糟的是有 `kb.rebuilt` 标记时用户库会顶掉随包库，坏库**直接生效**。
- **根因**：`build()` 名义上是「一个事务」，但 `_insert_documents` 内部**自己 commit 了一次**。
  而 FTS 是**外部内容表** —— `DELETE chunk` 与 `rebuild_fts` 分属两个事务时，
  「正文清了、索引没重建」这个中间态被**永久固化**。
  重建跑在线程池里，应用退出走 `taskkill /PID /T /F`，所以「重建到一半关掉」就命中。
- **解决**：清表 + 写正文 + 重建 FTS + 写依赖合并成**同一个事务**，只在最后 commit 一次；
  失败路径显式 `rollback()`。
- **防呆**：新增 `test_kb_rebuild_atomicity.py`（15 条）—— 注入一个「FTS 重建之后才抛」的异常
  （用悬空依赖，那本来就有意报错中止），断言 `chunk / chunk_fts / fts_probe / deps / kp / vec`

## P-097 ★ 两处「看起来是安全的边界」，实际上是**读-改-写**竞态

- **现象**（两个同形缺陷，一处在下游、一处在上游）：
  - `POST /profile/{id}/events`（每轮 `agent_end` 都会发）为了刷新「活跃时间」，
    读出 student 行 → 改个名字原样写回。与「学生手动改学段」并发时，
    它会把**刚生效的新学段打回旧值**，而 `grade_history` 里已经记了新学段、章节也已清空 —— **两处真相**。
  - 教材重建的 `clear_knowledge_tables` 在 vec 扩展没加载时**直接抛**，
    导致 `/api/knowledge/rebuild` **永久失败**并回一句学生读不懂的 `no such module: vec0`；
    而此时检索链的 numpy 兜底**本来是好的**，那 361 条向量一行没少。
- **根因**：都属「**用一个大的操作去做一件小事**」。
  刷活跃时间只需要更新**一列**，却复用了「整行 upsert」；清表只需要清**能清的那几张**，
  却让一张可选的表把整件事拖死。
- **解决**：① 新增 `touch_last_active()` —— 单列 `UPDATE`，结构上不存在读-改-写窗口；
  ② 清表对 vec 表降级为 `warning` 并跳过，**其余三张表照旧抛**（那才是真错误）。
  两条都在注释里写清了「为什么只有这一处可以容忍」。
- **防呆**：① 的断言用**钩子复刻竞态**（读快照后、写回前把学段改掉），
  断言学段**没有**被打回 —— 单线程下这个缺陷是**测不出来**的，所以还额外加了一条源码级断言
  「学生行已存在时不许走整行回写」；
  ② 的断言包含反向对照「非 vec 表失败**仍然要抛**」（别顺手把真错误也吞了）。
- **报告用法**：与 P-095 合成「**并发与部分失败**」一组。
  核心一句：**「能被中断的地方，就是会产生中间态的地方」** ——
  要问的不是「它会不会失败」，而是「**失败之后它留下什么**」。

## P-098 · 用 `getEntries().length` 判「会话是不是空的」→ 开场语永远发不出来

**现象**：主动发起对话功能接好了、接口也对了，但**新会话永远不出现开场语**。
没有报错、没有异常、日志干干净净 —— 只是「没动静」。

**根因**：判据写成了「会话里有没有条目」。而 Pi 的会话文件在**第一条用户消息之前**
就已经有好几条条目了：

```
0  type=session                 ← 头部
1  type=model_change            ← 建会话时写
2  type=thinking_level_change
3  type=message  role=user      ← 到这里才是「真的有内容」
```

所以对一条刚建好的会话，`getEntries().length` 是 2~3 而不是 0 —— 判据恒为假。

**解决**：只数**可显示的问答条数**（`type === 'message'` 且角色是 user/assistant，
复用 `projectTranscript()` 的过滤口径）。`ChatRuntime.messageCount` 就是这个数。

**为什么这是一个值得记住的坑**（而不是「一个 off-by-N」）：
这是**代理量选错**的典型形态 —— 「会话是空的」这个语义被换成了一个看起来等价、
实际上不等价的量。同类错误在本仓库有前科（见 P-057 的「章节顺序不能按 rowid」：
rowid 是文件名字典序，看起来像顺序、其实不是）。共同点是：
**它不会报错，只会让功能静默不生效**，而排查方向会被「接口是对的」带走。

**防呆**：`session-boot.test.ts` / `opening-guidance.test.ts` 里的判据是**行为面**的
（真的跑一遍 store，看 `showOpening` 是不是 true），不是「读源码里有没有那一行」——
后者在判据被换成别的等价物时会照样通过。
另外 `runtime.ts` 的 `countMessages()` 与 `readExistingSession()` 刻意复用
**同一个过滤口径**（都走 `projectTranscript`），注释里写明「数错一个就能让开场语多发一次」。

**报告用法**：这是「判据/代理量选错」这一类缺陷的第 2 个实例（第 1 个是 P-057）。
汇报时把它与 P-057 并排讲，能说明「不是修了一个 bug，是识别出了一类风险」。

## P-099 · `custom_message` 会被 Pi 转成 **user** 消息 —— 「AI 主动开口」变成伪造学生发言

**现象**：开场引导写进会话后，模型在下一轮表现得**像是学生自己说了那句开场白**：
学生只说一句「好呀」，模型却接着答「好的，那我们从循环开始讲」——
它以为开场语是学生的意思表示。

**根因**：待实现文档建议用 `SessionManager.createCustomMessage()`（实际 API 是
`appendCustomMessageEntry`）。而 Pi 0.85.1 的 `convertToLlm()` 里：

```js
case "custom":
  return { role: "user", content: typeof m.content === "string" ? [...] : m.content, ... }
```

`custom_message` **参与**模型上下文，但会被当成 **user** 消息。
于是上下文里出现了学生从未说过的话 —— 这不是「显示得不对」，是**伪造对话记录**：
模型据此产生的每一句回答都建立在一个不存在的学生发言上。

**解决**：用 `appendMessage()` 写一条 `role: 'assistant'` 的普通消息。
三种候选形态的取舍（`runtime.ts` 的 `appendOpeningMessage` 里有同一张表）：

| 形态 | 进模型上下文吗 | 判定 |
| --- | --- | --- |
| `appendCustomEntry`（`custom`） | **不会** | 否掉：学生回「好呀」时模型不知道自己在跟什么约定，引导退化成一句没人接得住的话 |
| `appendCustomMessageEntry`（`custom_message`） | 会，但**变成 user** | 否掉：伪造对话记录 |
| `appendMessage` + `role:'assistant'` | 会，就是助手自己的话 | **采用**：与屏幕上的显示一致 |

**附带发现**：`usage` 全 0 **是事实不是占位符** —— 这句话由服务端模板拼出
（没花任何 token），写全 0 让轨迹与成本统计能对上账。

**防呆**：`session-switch.test.ts` 有一条断言直接在源码里找
`role: 'assistant'`，并**反向断言不许出现** `appendCustomMessageEntry` / `appendCustomEntry`。
变异验证：把 `'assistant'` 改成 `'user'` → 断言当场变红（已验）。

**报告用法**：这是「用第三方 SDK 时**读它怎么消费**比读它怎么提供更重要」的实例。
汇报里可以这样讲：文档写的是「用 Pi 的 createCustomMessage」，而跑起来才发现
那个 API 的语义是「以**用户身份**注入一段上下文」—— 差一个 `role` 字段，
功能从「AI 主动开口」变成「伪造学生发言」。

## P-100 · 「新会话」按钮其实只是清屏（会话文件一直没换）

**现象**：连续几天用下来，历史会话列表里只有**一条**会话，而且它越来越长。
学生每次点「新会话」都确实看到界面清空了，所以没人觉得有问题 ——
直到有人问「为什么我从来只有一条历史记录」。

**根因**：`newSession()` 的实现是 `chat.resetConversation()` ——
**纯本地清屏**，Pi 那一侧的会话一个字节都没动。于是「新会话」之后说的每一句话
都追加进**同一个** JSONL 文件。按钮叫「新会话」，做的是「清屏」。

**为什么长期没被发现**：

1. 界面上**看不出区别**（清屏与换会话在视觉上是同一件事）；
2. 单测也看不出来（它们断言的是「清空后 turns 为空」——
   而换会话与清屏**都**满足这一条）；
3. 会话列表页那时只有「只读回看」，看不出「所有消息都在同一条里」有什么不对。

**解决**：`newSession()` 改走 `chat.startNewSession()` → `session:new` 通道 →
主进程 dispose 旧会话 + 开一个新 JSONL 文件；**旧会话不删除**，仍在列表里可切回。
界面上按钮文案从「新会话」改成「新对话」（它现在真的是「开一段新的」）。

**防呆**：`ui-shell.test.ts` 的断言从「`newSession` 里必须有 `resetConversation()`」
改成「必须调 `startNewSession()`」+「失败时必须提前 return（不许先把界面清空）」。
★ 旧断言正是漏掉这个缺陷的原因 —— 它检查的是**手段**（调了哪个函数），
而不是**目的**（会话到底换没换）。

**报告用法**：这是「测试断言了手段而不是目的」的典型。
汇报时讲这条比讲「修了一个按钮」有价值：**一条断言写对了手段，可以长期掩盖一个功能没生效**。
同类：本项目「开场的判据必须是 `messageCount === 0` 而不是 `source === 'new'`」也是同一回事。

## P-101 · 开场引导放错了分支：生成了、写进会话了、界面上一个字都看不到

**现象**：主动发起对话接完，主进程日志明明白白写着
`[agent] 已把开场引导写入会话（35 字符，未消耗 token）`，
会话文件里也真有那条 assistant 消息 —— **但界面上什么都没有**，还是原来的静态问候。

**根因**：两件事各自都对，凑在一起就是矛盾：

- 开场引导**只在会话为空时才有值**（`messageCount === 0` 才去取）；
- 而它被渲染在**「有消息」那个分支**里（排在 `<ChatMessage>` 前面），
  理由是「它要显示在第一条消息之前」。

于是那个分支永远进不去 —— 有开场语 ⇔ 会话为空 ⇔ `isEmpty` 为真 ⇔ 走的是空态分支。
两个条件互斥，代码却要求它们同时成立。**这是纯逻辑矛盾，不是时序或数据问题。**

**发现方式**：`npm test` 741 项全绿、`typecheck` 干净、`smoke:wire` 22/22 ——
三套检查全过，因为这个缺陷**不在它们测的那个层次上**：
单测断言的是 store 的 `showOpening`（它是对的），
而「这个值被渲染到哪个分支」只有真把界面跑起来、点一下「新对话」才看得见。
★ 这正是 `AGENTS.md` §7「UX 体检与单测是两件事」那张表的第 2 类
（「只在某个状态下才发生」）。

**解决**：把开场引导移到**空态区块内**（`v-if="isEmpty"` 那个 div 里），
有开场语时它**替代**那句静态问候（两句「你好」叠着是重复的），
没有则退回原来的静态问候。学段那一行两种情况下都保留（它是状态说明，与谁在打招呼无关）。

**防呆**：`opening-guidance.test.ts` 的判据从「在 `<ChatMessage>` 之前」改成
**「在空态区块之内」**（`chat-empty` 与 `v-else` 分支边界之间）。
⚠️ 这条断言本身也踩过一次：初版用 `emptyAt < openingAt` 判「在空态里」，
而那只是那个 div 的**起始位置** —— 把整块移到 div 收尾之后、`v-else` 之前，
它照样成立（变异验证实测：**改回坏写法仍然是绿的**）。改成以 `v-else` 为边界后，
变异立刻变红。

**报告用法**：这是「三套检查全绿但功能是坏的」的一个干净样本。
汇报时讲它能把「为什么要做 UX 体检」讲清楚：**单测覆盖的是我们写下的逻辑，
而分支归属是逻辑之外的事**。附带一条方法论：**守卫自己也要做变异验证** ——
初版那条守卫看起来完全合理，而它抓不住它要防的那个改动。

## P-102 · 列出历史会话的 cwd 与建会话的不一致 → 会话列表**恒为空**

**现象**：会话列表页永远显示「还没有历史会话 —— 到对话页问第一个问题吧」，
而 `students/<id>/pi-agent/sessions/` 下躺着 **19 个** `.jsonl` 文件。
不报错、不告警、日志干净。

**根因**：Pi 的 `SessionManager.list(cwd, sessionDir)` 在**传了自定义 `sessionDir`** 时，
会**额外按 `cwd` 过滤**。源码（0.85.1 `session-manager.js`）：

```js
const filterCwd = sessionDir !== undefined && dir !== getDefaultSessionDirPath(cwd)
const sessions = (await listSessionsFromDir(dir, onProgress))
  .filter((session) => !filterCwd || sessionCwdMatches(session.cwd, resolvedCwd))
```

而 `listStudentSessions` 传的 cwd 是 `<studentDir>`，会话文件头里记的却是
`<studentDir>/pi-agent`（`createChatRuntime` 用的是 `paths.root`）——
两个字符串不相等，19 条**一条都通不过过滤器**。

实测对照（同一个目录）：

| `list()` 的 cwd | 结果 |
| --- | --- |
| `<studentDir>` | **0 条** |
| `<studentDir>/pi-agent` | **19 条** |

★ 更值得记的是**为什么这个错误看起来是对的**：那段代码上方的注释写着
「第一个参数只用于推导默认目录，第二个参数给了就以它为准」——
这句话描述的是 Pi 的**默认目录推导**逻辑（那部分确实如此），
但漏掉了后半段：传了自定义 sessionDir 时它**变成了过滤器**。
注释与代码都「自洽」，只是对第三方库的理解少了一句。

**解决**：`pi-paths.ts` 新增 `piSessionCwd(paths)`（返回 `paths.root`），
**建会话与列会话都从它取**——一个拼装点，两处不可能再漂移。

**防呆**：`session-reader.test.ts` 里一条源码级断言：runtime 必须用
`piSessionCwd(paths)`、sessions 必须用 `SessionManager.list(piSessionCwd(paths), …)`，
并**反向断言**不许再出现 `list(paths.studentDir`。变异验证：改回坏写法当场变红（已验）。

**报告用法**：这是**「第三方库的语义比它的签名更难」**的实例 ——
`list(cwd, sessionDir)` 的签名里两个参数看着是「主 / 备」，实际是「过滤器 + 目录」。
汇报时可以和 P-099（`custom_message` 会被转成 user 消息）并排讲：
两条都说明读 SDK 要读**它怎么消费这个参数**，而不是只看它怎么接收。

**规模**：这条一修，历史会话列表从**永远 0 条**变成 19 条 ——
而它是「重启后数据延续」那条验收的一半（另一半是主进程把恢复出的正文给前端）。

## P-103 · `tsconfig.node.tsbuildinfo` 被误提交（每次 typecheck 都制造一次假 diff）

**现象**：`npm run typecheck` 跑完之后，`git status` 里总多出一个
`desktop/tsconfig.node.tsbuildinfo` 的修改 —— 而它是编译缓存，不是源码。

**根因**：`desktop/.gitignore` 只忽略了 `node_modules/` / `out/` / `dist/`，
没忽略 `*.tsbuildinfo`。而 TypeScript 的增量构建缓存里含时间戳与文件哈希，
**每次编译必然变化** —— 于是它成了一个「每次跑检查都会脏」的文件。

**代价（为什么值得修）**：它让 `git status` 长期带着一个无意义的条目。
真正的风险不是噪音本身，而是**习惯化**：当「总有一个文件是脏的」变成常态，
真出现意外改动时就更容易被一眼扫过去。

**解决**：`desktop/.gitignore` 加 `*.tsbuildinfo` +
`git rm --cached desktop/tsconfig.node.tsbuildinfo`（文件保留在磁盘上，
只是不再跟踪）；顺手删掉未跟踪的 `tsconfig.web.tsbuildinfo`。

**报告用法**：这是「工程卫生」类的素材 —— 报告第 7 章讲「我们发现了什么」时，
这类条目不如 P-101/P-102 有分量，但它体现的是**对仓库状态的敏感度**：
一条长期存在的假 diff 说明没人认真看过 `git status`。

| --- | --- | --- |
| 恢复的历史会话 | 有 | ✅ |
| 实时对话 | **无** | ❌ |

**解决**：主进程在**每轮结束后**读一次会话文件末尾那一对 (user, assistant)、
把它们的条目 id 按 `requestId` 推给渲染进程（新通道 `turn:entries`）。

★ **为什么不塞进 6 事件**：事件词表被守卫 G4 冻结为恰好 6 个，而这条信息不属于任何一轮的
**对话状态机**（它不改变正文、也不终结本轮）—— 硬塞进 `payload` 或 `done` 会让每个
消费方都被迫理解一个它不关心的字段（与 `trace:changed` 同一个判断：并列通道，不是第 7 个事件）。

**两条容易踩的次生问题**（都补了测试 + 变异验证）：

1. **超前到达**：主进程的推送可能**早于** `sendChat` 的回执（渲染进程是在回执里才建轮的）
   —— 与 6 事件的缓冲是同一个竞态。不缓冲的话，快的那条推送被丢掉，
   表现与「这轮本来就取不到条目」**一模一样**（最难查的那种）。加了 `pendingTurnEntries`。
2. **`lastTurnEntries()` 不能按「条数差」算**：开场引导、`model_change`、失败轮次都会让
   条数对不上。它取的是**投影里末尾的那一对 (user, assistant)** —— 与 `messageCount`
   那条教训同源（判据要选有语义的量）。

**防呆**：`session-branch.test.ts` 里三条 —— 两条行为面（实时轮次拿得到 id、
超前到达要缓冲）+ 一条**源码级**（主进程必须真的调 `pushTurnEntries(handle.requestId, entries)`）。
⚠️ 第三条是**变异验证逼出来的**：只写前两条时，把主进程的推送删掉**测试仍然全绿**
（因为那两条用的是假 bridge，从来没经过主进程）。

**报告用法**：这是「**审计脚本的判据写细了才抓得到**」的又一例 ——
初版 D7 只查「有没有按钮」，正是它让我以为功能是好的。改成「该有几个 vs 有几个」之后
缺陷立刻现形。与 P-080（输入框没自动聚焦）属于同一类：**没有逻辑可断言，
只有量出来的数**。

## P-106 · 恢复的历史对话长成「一半一半」（每条消息各占一轮）

**现象**：`npm run ux` 的 D7 报「7 轮有回答、只有 4 个按钮」。查下去才发现更根本的问题：
历史会话恢复出来之后，界面上是这样的：

```
[我的问题]              ← 一轮：学生气泡 + **一个空的回答块**
[（空）][他的回答]        ← 另一轮：空的学生气泡 + 回答
```

**根因**：`restoreConversation()` 把主进程投影出来的**每条消息各当成一轮**
（`messages.map(...)` → 一条一个 turn）。而 `restoredTurn()` 的两条分支本来就写着
「学生消息的 `text` 留空 / 助手消息的 `userText` 留空」—— **那正是配对的写法**，
初版却把它们拆开各建了一轮。于是每一轮永远只有一半。

**为什么单测没抓到**：那时的断言是「`turns.length === 2`（两条消息）」——
**它描述的正是缺陷行为**。★ 这是「测试把 bug 固化成规格」的典型：
断言与实现出自同一次思考，所以它只能证明「代码与我想的一样」，不能证明「结果是对的」。

**解决**：`restoreConversation()` 改成**配对**：

- `user` 开头 → 建一轮（`userText` + `userEntryId`）；
- 紧跟的 `assistant` → **补进同一轮**（填 `text` + `entryId`），不新建轮；
- 连续两个 `user`（上一轮没有回答）→ 前一轮就那样收尾 —— **如实反映，不是缺陷**；
- 开头就是 `assistant`（开场引导）→ 单独一轮。

⚠️ 配对时最容易犯的错是**替换整轮而丢掉学生那半**
（`turns[i] = restoredTurn('assistant', …)` 造出来的对象 `userText` 是空的）——
实测踩到过，所以测试里有一条 `deepEqual` 逐轮比对四个字段。

**防呆**：`session-branch.test.ts` 两条（五条消息 → 三轮的逐字段比对；
开场引导单独一轮）+ 四处既有断言从「按条数」改成「按轮数」。
变异验证：把配对关掉 → 7 条断言当场变红（已验）。

**报告用法**：与 P-100（「新会话」其实只是清屏）并排讲最好 ——
两条都是「**断言写的是手段而不是目的**」：P-100 检查「调了哪个函数」，
这条检查「有几条消息」。两次都是**换个问法**（「会话真的换了吗」「这是一轮对话吗」）
之后缺陷才现形。

## P-107 · CI 首跑连爆四处：三处「中文遇上西文 locale」+ 一处「管理员权限才复现的符号链接」

**现象**：CI/CD 写好后全部推上云端执行，**四次红**。每一处都是
「本机永远绿、云端必红」—— 也就是**本地开发结构上不可能发现**的缺陷。

### ① 中文输出遇上非 UTF-8 stdio（**三处，同一类**）

| # | 位置 | 报错 |
| --- | --- | --- |
| 1 | `scripts/build_server.py` 的 `sys.exit("[FATAL] …互斥…")` | 中文被转义成 `\u4e92\u65a5` |
| 2 | `tests/test_build_info.py` 的 4 处 `subprocess.run(text=True)` | `TypeError: can only concatenate str (not "NoneType")` |
| 3 | `packaging/k12-agent-server.spec` 的 `print("[spec] 项目根目录 = …")` | `UnicodeEncodeError: 'charmap' codec can't encode` |

**根因（三个各不相同，但同一个根源）**：输出端与解码端对编码的约定不一致，
而**本机是中文 Windows（默认 cp936/utf-8），正好把它掩盖了**：

- ① 缺 `install_utf8_stdio()` —— 三个兄弟脚本都装了，只有它漏了；
- ② 子进程输出 UTF-8（因为它装了 ①），父进程却按 `locale.getpreferredencoding()` 解码
  —— 英文 runner 上是 cp1252，中文的某个字节（实测 `0x8d`）在 cp1252 里**未定义**，
  reader 线程抛异常、`stderr` **静默变成 `None`**。★ 报出来的错
  （`can only concatenate str`）与真正的原因（编码）**毫无关系** —— 这是最贵的部分；
- ③ spec 被 PyInstaller **exec**，继承的是 PyInstaller 进程的 stdout（runner 上是 cp1252），
  一行中文 `print` 就让**整个打包中止**。

**解决**：① 与 ③ 补 `install_utf8_stdio()`（且必须在**任何中文输出之前**）；
② 给 `subprocess.run` 显式 `encoding="utf-8"` ——
★ **修消费端**而不是让子进程别输出 UTF-8：后者的 UTF-8 输出是**刻意的**
（`app/console.py` 的约束），父进程按 locale 猜才是错的。

### ② HF 缓存的符号链接让 7-Zip 中止（**只有管理员权限才复现**）

```
WARNING: The directory name is invalid.
.\…\snapshots\46fbe…\config.json\ : The directory name is invalid.
⨯ 7za.exe process failed 1
```

**根因**：HuggingFace 缓存默认用**符号链接**指向 `blobs/`，而能否建链接**取决于权限**：

| 环境 | 能建链接 | HF 落盘 | 打包 |
| --- | --- | --- | --- |
| 开发机（非管理员）| ❌ | 实体文件 | ✅ |
| GitHub runner（管理员）| ✅ | **符号链接** | ❌ |

实测确认：本机 `blobs/` **空的**、`snapshots/` 里 5 个都是实体文件；
连 `New-Item -ItemType SymbolicLink` 都报「此操作需要管理员权限」。

★ **一次误判值得记下来**：我最初判断是「Windows 260 字符路径上限」，
因为报错是「目录名无效」。**量了一下才发现 CI 的路径比本机还短 1 个字符** ——
假设当场被数据推翻，才转向符号链接。**先量再改**。
★ 报错里路径**末尾那个反斜杠**（`config.json\`）是 7-Zip 把链接当成目录的指纹。

**解决**：`materialize_symlinks()` 把链接读出来写成实体文件再删链接（幂等、无损），
在 **spec 里**（打包必经之路，无论模型从哪来）实体化 + 再查残留，有残留就**中止打包**；
`fetch_embedding_model.py` 的下载后**与幂等短路分支**都调它（CI 缓存命中走的正是后者）。

### ★ 这一组的共同教训

四条都不是「CI 配错了」，而是**真实的可移植性缺陷**被云端环境照出来了。
它们的共同形态是：**某个隐含假设在本机成立、在云端不成立** ——
「locale 是中文」「有权限建链接」。而这类缺陷**不可能靠本地反复跑发现**，
只能在**交付环境**里跑一次。

**报告用法**：这是「为什么要 CI」这个问题最好的一份答案 ——
不是「省得手动跑测试」，而是**换一个环境跑同一段代码**。
四次红里有四次都是本机永远绿的那种；把它们并排列出来，
比任何一句「我们重视工程质量」都有说服力。

## P-108 · 分叉成功后，学生**在列表里找不到自己刚分叉出来的那条**

**现象**：点「从这里重新问」→ 确认 → 界面确实切到了新会话（消息区换了内容），
但左侧列表里**看不到它** —— 要手动点「刷新」才出现。

**根因**：侧栏的刷新判据是「**消息条数**变化」（`currentSessionMessageCount`
的边沿，见 D-058）。而**分叉出来的新会话天生就带着历史消息**（它就是「根 → 分叉点」
那一段的复制），条数一开始就 > 0 —— 所以「0 → N」那个边沿**根本不发生**，
列表于是不刷。

★ 这是**判据选错**的又一种形态：D-058 用 `messageCount` 是**对的**
（那时要解决的是「新会话第一轮跑完才落盘」），但那条判据**只覆盖了
「会话从空变成有内容」**这一种增长方式；**分叉是另一种**（会话一开始就有内容）。
一个判据对了，不代表它覆盖了所有情况。

**第二层**（同一个现象、另一个原因）：即使列表刷新了，如果那条新会话的**父
正好被折叠着**，它照样看不见。表现与「没刷新」**完全一样**（都是「点了没出现」）
——排查时容易只修一层就以为好了。

**解决**：`watch(() => chat.currentSessionId, …)` —— 当前会话**换了**就
① 把它祖先链上的节点从 `collapsed` 里移除，② 重取列表。

★ 为什么不直接用 `currentSessionId` 而保留 `messageCount` 那条：
两者覆盖的是**不同事件**（内容增长 vs 会话切换），都需要。合成一条
「任一变了就刷新」也可以，但那样会把「为什么在这里刷」的理由埋掉。

**防呆**：实测（CDP 真跑）——分叉前 21 行 → 分叉后 **22 行、嵌套 3 条、
当前高亮 1 条**，无需手动刷新。UX 体检 D10–D12 盯着树的几何与折叠。

## P-109 · UX 体检的判据自己错了（「连接线宽度 = depth×12」）

**现象**：`npm run ux` 的 D11 报红：「嵌套行的前导宽度与 depth×12 一致=false」，
而界面看上去完全正常。

**根因**：**判据写错了**，不是代码错。一层树形前导 = `depth` 段**祖先竖线**
+ **1 个本层拐角**（`├`/`└`）：

| depth | 前导构成 | 宽度 |
| --- | --- | --- |
| 1 | [竖线][拐角] | 24px |
| 2 | [竖线][竖线][拐角] | 36px |

实测正是 24 / 36 —— 代码对，而我按 `depth × 12` 去判，于是**假红**。

**解决**：判据改成 `(depth + 1) × 12`，并在断言文案里写明构成。

★ **这是 AGENTS §7 那条纪律的第三次实例**：「**量法本身也会有 bug，先怀疑量法**」。
前两次是「量 `<input type=radio>` 得到 13×13（那只是它画的小圆点）」与
「要求两维都 ≥28px（列头 24×28 是竖向目标）」。

**报告用法**：三条并排讲，能说明「写体检脚本与写被测代码是两种不同的能力」——
**量得对**本身需要一次独立的、以被测量为对象的思考。
README 里那句「假阳性会让人白改一轮」在这里是字面意义的：
如果当时信了那条红，就会去『修』一个本来就正确的 CSS。

## P-111 「守卫看起来在守，其实守不住」（根因：判据的锚点选在了注释 / 子串 / 定义上）

**现象**：本轮新写的守卫套件第一次跑是 **14 条全绿**，看起来「该守的都守住了」。
做变异验证（把每处修复**改回坏写法**，看断言会不会红）之后，**3 条当场露出原形**：

| 变异（把修复改回坏写法） | 守卫的反应 | 为什么守不住 |
| --- | --- | --- |
| 把 `visibleInSidebar` 的第一行从 `=== true` 改成 `!== false` | **照样绿** | 断言只检查「函数存在 + 侧栏调了它」，**从没执行过**它 |
| 把「重建索引」按钮整段删掉（store 里仍有 `rebuild()`） | **照样绿** | 判据说的是「文件里出现过 `rebuild`」，而 store 的引用就能喂饱它 |
| 把技术词从「高级区」挪进**学生那一节**（豁免是按文件给的） | **照样绿** | 判据是「这个词在这个**文件**里被豁免了」，而豁免理由说的却是「它只在高级区」 |

第二批变异又抓出两条：
- 把档案页的译文调用删掉、**注释留着** —— 仍然绿（判据匹配到了注释里的函数名）；
- 只改 `@click="rebuild"` 的**第一处** —— 仍然绿（同一字符串在文件里出现两次，
  第二处仍匹配断言）。

**根因**：**判据的锚点选错了层**。四类错误锚点，本轮全部踩到：

1. **锚在「定义」上**（函数存在就算守住了）→ 要锚在**行为**上（把函数当函数调）；
2. **锚在「子串」上**（`k12-cta` 匹配到了 `k12-cta--mutated`）→ 要锚在**词边界**上；
3. **锚在「注释」上**（注释里引用了函数名 / 坏写法）→ **先剥注释再断言**；
4. **锚在「唯一性」假设上**（以为 `@click="rebuild"` 只出现一次）→ 出现两次时要 `all`。

还有一类是**判据本身错**（不是锚点错）：D12 的「收起一个节点要藏掉整枝」最初写成
「列表里还有没有嵌套行」——而列表里有**多个互不相关的会话家族**，
收起 A 不会让 B 消失，于是那条断言**恒假**，每次跑都报一条红，而产品是对的（假红）。
改成「被收起那一行的子树必须消失」才对；而且必须**专门挑一个有孙辈的节点**去收 ——
收一个「孩子是叶子」的节点时，「藏整枝」与「只藏直接子级」看起来一模一样（变异验证抓到）。

**解决**：

- 每条断言都做**变异验证**，并把这一步固化成脚本：`npm run guards:mutation`
  （`desktop/scripts/verify-guard-mutations.mjs`，19 条变异，每条都附「改哪个文件、
  把什么改成什么、期望哪条断言变红」，跑完逐条恢复原文件）；
- 断言尽量落在**行为**上（`visibleInSidebar(PAGES.knowledge, false) === false`），
  source 级断言只用于「CSS / 模板结构」这类没有运行时的东西；
- 所有源码级断言**先剥注释**（本仓注释偏爱引用坏写法，不剥就会被自己的说明书绊倒）。

**防呆**：`npm run guards:mutation` 现在是可重复执行的脚本（不属于 `npm test` ——
它会临时改文件，不适合放进常规测试）。

**报告用法**：这是「测试的有效性」这一层的素材 ——
**「测试全绿」与「代码是对的」之间隔着一层「断言是否真的在测那件事」**。
可以配上那句结论：**一条永远通过的断言，和没有断言是一样的**；
而「永远通过」最常见的成因不是写错判据，是**判据选错了锚点**。
（与 P-109 / `AGENTS.md §7` 的「量法本身也会有 bug，先怀疑量法」是同一条纪律的延伸：
上次怀疑的是**量**，这次怀疑的是**断言**。）

## P-112 「窗口不可见时，探针量到的是一具尸体」（根因：hidden 窗口停掉渲染生命周期）

**现象**：`npm run ux` 报 8 条红，其中最刺眼的是
`B1 回答流式输出时视图一直跟着新内容走`（实测掉队 205→759px）与
`A2b/A3/A5`「按 Enter 发不出去、输入框不清空」。
看起来像**产品坏了**，而且掉的都是「用户点名要测」的那几条。

**根因**：**窗口处于 `document.visibilityState === 'hidden'`**（后台窗口 / 无人操作时的常态），
而 Chromium 在 hidden 状态下**停掉渲染生命周期**。实测数据（同一时刻、同一页面）：

| 测量 | hidden | 调 `Page.bringToFront` + `Emulation.setFocusEmulationEnabled` 之后 |
| --- | --- | --- |
| `document.visibilityState` | `hidden` | `visible` |
| 1 秒内 `requestAnimationFrame` 次数 | **0** | **239** |
| 1 秒内 `setInterval` 次数 | 2 | 2（不受影响） |
| `ResizeObserver` 回调次数 | **0** | 正常 |

★ 关键推论链（缺一环就看错方向）：
1. 应用的自动跟随**全靠 `ResizeObserver`**（内容变高 → 滚到底）；
2. RO 回调在**渲染生命周期**里派发 → hidden 时**一次都不触发**；
3. 于是「内容长高却不跟随」——**代码是对的，测量环境是死的**；
4. 而 `setInterval` 照常，所以「轮询式」的断言（轮次数、输入框内容）看起来也"部分正常"，
   进一步把方向带偏（A2b/A3/A5 正是被这条带偏的）。

**解决**：探针在 attach 之后统一调 `ensureRendering()`
（`ux-audit` / `ux-scroll-attribution` / `ux-pages-audit` / `ux-layout-audit` / `ux-student-view-scan` 五处），
依次尝试 `Page.bringToFront` → `Emulation.setFocusEmulationEnabled` → `Emulation.setPageVisibility`，
并把**实际的 `visibilityState` 打印出来**；仍不是 `visible` 就显式警告
「与渲染时序相关的断言可能失真」，而不是让它静默地红成产品缺陷。
实测效果：同一轮体检的红条从 **8 条降到 1 条**（剩下的那条正是依赖渲染的那一条）。

**防呆**：`ensureRendering()` 在各探针里（含函数头的完整说明）；
告警文案里点名「可能失真」，让人先怀疑环境再怀疑代码。

**报告用法**：这是「量法本身也会有 bug」的第 **四** 次实例
（前三次：`depth×12` 假红 / radio 量到小圆点 / 两维都 ≥28px 过严）。
它的价值在于**这次错的是环境而不是判据** ——
前三次是「判据写错」，这次是「被测对象根本没在运行」，
而两者在报告里长得一模一样（都是一条红）。可以配一句总结：
**调试探针时，先确认被测的东西真的在跑，再去读它的数字。**

## P-113 ★★ 冷却期是一把**永不释放**的锁 —— 两个会话的轮次号被相减（学段「证据够了却永不动」）

**现象（学生侧）**：学段永远不跟着学生调整。学生连续问了三轮明显更深的问题，
指示器纹丝不动；`grade_history` 里也长时间没有新行。**没有任何报错**，
所有测试全绿，界面一切正常 —— 只有「自适应」这件事本身静默失灵。

**怎么发现的（不是推演，是读真实运行数据）**：翻 `%APPDATA%/k12-agent-desktop/logs/sidecar.log`
（5 天、436 次判定）按 `reason` 分组统计：

```
reason=cooldown          226 次（50%）   ← 一半的判定卡在这里
reason=no_direction      196 次（45%）
reason=changed            14 次（3%）
low_confidence/at_boundary/llm_conflict   各 0 次
```

再逐条看那 226 次的**上下文**，就看到了自相矛盾的组合：

```
2026-09-21 10:41:20  学段判定：… 第 [1] 轮 → junior（changed=False reason=cooldown 置信度=0.90 连续=4）
```

第 **1** 轮就报「连续 4 轮同向」（第 1 轮不可能真的连续 4 轮），
而且 `连续=4` 已经**远超**阈值 3、`置信度=0.90` 也远超 0.6 —— **证据双双重超标，判定却不动**。

**根因**：冷却算的是 `elapsed = turn - anchor_turn`，而这两个数来自**两个不同的轮次空间**：

- `turn` 是**每会话**计数器（桌面端换一个会话就从 1 重来）；
- `anchor_turn` 来自 `grade_history`，是**上一个会话**写下、长期留在库里的号。

实测锚点 `turn=22`（2026-09-18 的一次手动设定）对比随后新会话的 `turn=1..8`：

```python
elapsed = max(0, 1 - 22) = 0          # ← 钳位把负数吃掉了
remaining = MANUAL_COOLDOWN_TURNS - 0 = 10
```

于是每一轮都报「还剩 10 轮」。而锚点**在冷却期内不会被新的锚点取代** ——
所以这个 10 永远不会递减，**唯一出路是在同一个会话里聊到第 23 轮**。
实测会话长度上限是 8 轮。它是一把**活锁（livelock）**，不是「偏保守」。

★ 这一条此前**被当成已知偏差留在代码注释里**：`rules.py` 写着「新会话会重新获得一段完整的冷却，
方向上是保守的（宁可多观察几轮）」。那个判断错了 —— 它不是「多观察几轮」，
而是「再也观察不完」。**注释里的自我安慰比缺陷本身更危险**（它让接手人不去查）。

**解决**：换一个**单调**的度量 —— 不再问「`turn` 差多少」，而问
**「锚点之后真实又发生了几轮」**：

1. `grade_history` 加一列 `signal_mark`（v3 迁移），记下写那一行时 `grade_signals` 的**最大 id**；
2. `GradeEngine.turns_since(mark)` 数 **id 大于 mark 的轮次桶**有多少个
   （用 `(session_id, turn)` 分桶，与 `verdicts()` 同一口径）；
3. 冷却 = `窗口 - turns_since`，窗口长度仍由 `source` 推导（手动 10 / 自动 5）。

`id` 是 AUTOINCREMENT，**全局单调、跨会话连续**，所以「过了几轮」不再需要
比较两个会话的轮次号。历史锚点没有 `signal_mark`（v3 之前写入）→ 走旧的钳位兜底
（**不会比修复前更糟**：旧锚点最多再挡一个窗口，此后新锚点就带上位标了）。

★ 顺带修掉一个**计数单位**错误：`MAX(id) - mark` 数的是**信号条数**，
而一轮最多写 4 行（三路 + M-10 占位）——拿它当冷却会把 5 轮窗口缩成一两轮就过完。
所以 `turns_since` 数的是**不同的 `(session_id, turn)` 桶**。

**复现（真引擎 + 真 SQLite，非推演）**：

```python
# 会话 A：三句受挫表达 → 第 3 轮自动下调一级
# 会话 B：轮次号从 1 重来，上交够格向上证据
turn=1 reason=no_direction   cooldown=4
turn=2 reason=no_direction   cooldown=3
turn=3 reason=cooldown       cooldown=2
turn=4 reason=cooldown       cooldown=1
turn=5 reason=changed        cooldown=5   ← 走满窗口就真的放行（修复前恒为 5、永不归零）
```

**防呆**：`server/tests/test_grade.py` 的 `test_cooldown_releases_across_sessions`
（换会话后冷却必须走完，且**真的改了学段**）、
`test_d1_cooldown_is_measured_in_real_turns_not_turn_numbers`（按真实轮数算，不是轮次号相减）；
变异验证：把冷却改回「两个轮次号相减」→ **5 条断言变红**。

**报告用法**：这是「**机制不生效**被误当成**机制不灵敏**」的典型案例，
也是本仓库里**第一次靠读生产日志而不是读代码**发现的缺陷。
报告里值得写的两句话：① 「50% 的判定卡在一个恒等于窗口长度的冷却值上」；
② 「代码注释当时还把这件事描述为『方向上是保守的』——注释里的话也要能被证伪」。

## P-114 ★★ 三路信号里有**两路**在把学段往下拽 —— 「问得浅 / 用词日常」被当成「学段低」

**现象**：中、高中学生用着用着会被**降级**。具体到最容易复现的一类：
一个初中生连问三句「什么是X」—— 这是最自然的提问方式 —— 学段就掉到小学高年级。
日志里的现场（`sidecar.log`）：

```
2026-09-16 21:00:51  学段判定：… 第 [8] 轮 → primary_high（changed=True reason=changed 置信度=0.75 连续=4）
```

`置信度=0.75` 是关键线索：它是 `0.5 × 1.5` —— **单路**证据（差一级 = 0.5 强度 × 增益 1.5）。
也就是说这次降级只靠**一路**信号就完成了，而且是往下的一路。

**根因（两处同类错误，都是「绝对档位」被拿去和「当前学段」求差）**：

1. **问题深度**：`classify_depth()` 返回的是**绝对档位** ——
   `什么是X` → `primary_high`、`链式法则怎么推导` → `senior`；
   `_reading()` 再对**当前学段**求差。于是初中生问「什么是矩阵」得到 `primary_high - junior = -0.5`，
   连问三句就是「连续 3 轮同向 + 0.75 ≥ 0.6」→ **自动降级**。
   ★ 但「任何学段的学生都会用『什么是…』去问一个自己刚接触的概念」——那是好奇心的常态，
   **不是学段证据**。这个推理链本身就不成立。
2. **词汇复杂度**：`DAILY_TERMS`（电脑 / 动画 / 图片 / 机器人 / 手机 / 小猫…）命中即产生
   一条到 `primary_low` 的 `-0.5`。可这些词**在四个学段的教材里到处都是** ——
   初、高中生聊「机器人」是很自然的事，连提三轮同样够格降级。
   ★ 它的设计意图是「与专业术语互为反向证据」，但**反向证据 ≠ 可以下调**：
   专业术语往上是对的（问「梯度下降」大概率是高学段），
   「用了日常词」却什么也说明不了（低学段学生也会说「梯度」）。

**为什么之前没被发现**：两条路都被**单独的守卫**盯着，而守卫的判据是
「某个词该不该命中」——它们**没有问「这个方向对不对」**。
`test_d3_*` 甚至专门修过深度词的**优先级**（「什么是公式」不许被判成推导档），
但那修的是「档位取哪一档」，不是「档位比当前学段低时该不该下调」。
★ 教训：**分类器的守卫往往只测分类，不测分类结果的用途**。

**解决**：`_reading(..., only_up=True)` —— 档位**低于**当前学段时，方向取 0：

- **证据照记**：`level_hint` 与 `raw` 都保留，仍然落库、仍然可审计、
  仍然是一条会**打断**「连续同向」的中性轮（这正是我们要的：它确实不是证据）；
- **只上不下**：这三条路只负责「学生表现出更高学段的样子」；
  **下调只由元认知负责**（「听不懂 / 太难了 / 跟不上」）——
  那说的是「刚才那一段讲深了」，与「你是几年级」是两件不同的事。

**顺带删掉两个误报**：
`META_REPHRASE` 里的「举个例子 / 详细一点 / 讲详细」——
「能举个例子吗」是**听懂了、想更深一层**，不是「听不懂」；
把它们当受挫信号会让**积极提问的学生被降级**，而这类话在低学段尤其常见，方向恰好是反的。

**复现（真引擎 + 真 SQLite；起始学段钉在 junior）**：

```
--- 问题深度（问得浅）：起始 = junior ---
  turn=1 reason=no_direction 方向=0  学段=junior
  turn=2 reason=no_direction 方向=0  学段=junior
  turn=3 reason=no_direction 方向=0  学段=junior
  → 最终 = junior（修复前：连问三句「什么是矩阵/公式/循环」就降级到 primary_high）

--- 反向对照：真受挫仍然下调（别修过头）---
  起始=primary_high → 最终=primary_low   ✓ 真的掉了一级
```

**防呆**：`test_depth_never_pulls_the_grade_down`（含整轮聚合断言）、
`test_daily_terms_are_neutral_not_downgrading`、
`test_neutral_evidence_is_still_written`（中性证据**必须照记**，不能靠删证据来实现「不下调」）；
**反向对照** `test_depth_still_raises_the_grade` / `test_professional_terms_still_raise_the_grade` /
`test_real_struggle_words_still_downgrade`（防止「只上不下」被修成「什么都不做」）。
变异验证：撤掉 `only_up` → **7 条变红**；撤掉词汇那处 → **4 条变红**。

**报告用法**：这是「**判据看起来合理、方向其实错了**」的样本。
可以配一句：*一个信号的提取器写完，要问的下一个问题是「它指向哪个方向，而那个方向对我这个学生成立吗」*——
深度词命中「推导」是往上（成立），命中「什么是」拿来往下（不成立）。

## P-115 ★ 一句话的受挫被算了**两遍** —— 两条信号路都在读同一批词

**现象**：学生说一句「太难了」，该轮信号强度直接**顶到 1.0**（单路本应是 0.5）。

**根因**：`TOO_HARD_TERMS`（`太难了/太难/好难/不会做`）与 `META_STRUGGLE` 是**同一批词**，
而「答题表现」那一路（`extract_quiz_perf_signal`）会去**读学生原话**找它们：

```python
too_hard = quiz.too_hard or bool(find_terms(text, TOO_HARD_TERMS))   # ② 答题表现
struggle = find_terms(text, META_STRUGGLE)                            # ④ 元认知
```

于是同一句话既算元认知 `-0.5`、又算答题 `-0.5`，该轮 `total_value = -1.0`（强度封顶）。
★ 它还**绕过了自己的设计**：那一路的注释写着「答题表现从 `learning.db` 读、桌面端不用上交」，
却偷偷从对话原文里取了证据。

**解决**：把「答题表现」那一路**整体移除**（三路信号 → 词汇 / 深度 / 元认知）。
两条理由（都在 `signals.py` 模块 docstring 里）：

1. **概念错位**：答错两道题说明「这个知识点没掌握」，不等于「学段更低」——
   那本来就是 `mastery` 该管的事（`MASTERY_GAIN_CORRECT` / `MASTERY_LOSS_WRONG` 已有一套独立机制）。
   让答题表现去改学段，等于把「掌握度」和「学段」两个量混在一起。
2. **重复计数**：如上。

**连带改动**（都做了，没有留半套）：删掉 `QuizPerformance` / `extract_quiz_perf_signal` /
`quiz_performance_from_history` / 六个 `QUIZ_*` 阈值 / `TOO_HARD_TERMS`；
契约里 `GradeTurnInput.quiz` 字段**删除** → 老调用方拿到 **422**。

★ 这里有个**契约纪律**值得写进报告：**契约收下一个字段，就等于承诺它会参与判定**。
所以移除时不是「保留字段但不用」（那会让人以为「我传了答题数据所以学段变了」），
而是**响亮地拒绝** —— 并用一条测试钉住 422（`test_quiz_field_is_rejected_by_the_contract`）。

**防呆**：`test_same_turn_evidence_is_counted_once`（单路 = 0.5，不是被重复计到 1.0）、
`test_turn_aggregates_three_classes`（信号词表恰好三路）、
`test_quiz_records_no_longer_drive_the_grade`（连对连错都不改学段）。

**报告用法**：「同一个事实被两条路各记一次」是信号系统里最隐蔽的加噪声方式 ——
它不会报错，只是让每一次调整都**比设计更猛**。

## P-116 ★ 守卫被**注释**满足了 —— 「抽掉欢迎页」变异竟然是绿的（假守卫第 6 次）

**现象**：D-067 给安装器加了个「欢迎页必须存在」的守卫（`installer-config.test.ts` 的 G21-4）。
写完之后跑 `guards:mutation` —— 把欢迎页**从宏里抽掉**（只留空的
`!macro customWelcomePage` / `!macroend`）—— 结果那条守卫**照样是绿的**。

**根因**：守卫当时是在**整个 `.nsh` 文件**里搜那串字：

```ts
assert.match(nsh, /!insertmacro\s+MUI_PAGE_WELCOME/, '...')
```

而那个文件的**头部注释里就写着这串字** —— 因为注释正好在解释「为什么要补这一页」：

```nsis
;   **默认没有欢迎页** —— `assistedInstaller.nsh` 只在「宏 `customWelcomePage`
;   已定义」时才 `!insertmacro MUI_PAGE_WELCOME`。
```

于是宏被掏空之后，注释仍然满足断言。**判据锚在了注释上，而不是代码上。**

**解决**：把判据锚到**宏体**上 —— 先取出宏的内容，再在宏体里断言：

```ts
const macro = /!macro\s+customWelcomePage([\s\S]*?)!macroend/.exec(nsh)
assert.ok(macro, '必须定义 customWelcomePage 宏')
assert.match(macro[1], /!insertmacro\s+MUI_PAGE_WELCOME/, '空宏等于没加欢迎页')
```

改完复跑变异：㉞ 变红 ✅。

**报告用法**：这是「**没验过会红的守卫不算守卫**」的第 6 次实例，也是**代价最高的一次** ——
前面几次抓到的都是「判据太宽」，这次抓到的是「判据被**解释性文字**满足」：
**你越是在注释里把这个机制讲清楚，就越容易让一条按整文件搜索的断言变成假绿。**
一句话可以写进报告：*写守卫时，判据要指向「代码做了什么」，而不是「文件里出现过什么字」——
注释里的字也是字。*

> 定位手段没有任何技巧：**把修复改回坏写法，看它红不红**。
> 这一步不做，上面那条断言会一直绿着，且看起来完全合理。

## P-117 ★ 把 vite 的「入口桩 + worker 实体」误判成构建残留 —— 差点把一个不存在的现象写进决策记录

**现象**：拆 asar 时看到 `out/renderer/assets/` 里有两个 `editor.worker-*.js`
（`BwBjdhCz` 与 `pDQdyQEP`）。当时的判据是"同名不同 hash 的文件数 > 1" →
判定「上一轮构建残留下来的死文件」，并据此给 renderer 段加了 `build: { emptyOutDir: true }`，
还把「**实测**多出一个 0.56MB 的死文件」写进了配置注释与守卫说明。

**真相**：vite 对 `?worker` 的产物**本来就是两个文件**：

| 文件 | 大小 | 是什么 |
| --- | --- | --- |
| `editor.worker-BwBjdhCz.js` | 584,829 B | worker **实体**（真正跑在 worker 线程里的代码） |
| `editor.worker-pDQdyQEP.js` | **208 B** | **入口桩**，主 bundle `import` 的正是它，它再 re-export 实体 |

两个 hash 不同是**设计如此**，不是残留。三处实测：大小、时间戳（同一秒，都是本次构建）、
引用关系（在 `index-*.js` 里 grep 到的 worker 文件名是那个 208 字节的桩）。

**为什么差点写错**：判据只用了"文件名像不像"——没看**大小**、没看**引用关系**、没做**对照实验**。
若照此写进 D-068，后人会继承一个**不存在的现象**（"monaco 换 hash 会留死文件"）
和一个错误因果，而且**复现不出来**。

**怎么暴露的**：因为要在文档里写下"实测"两个字，才去补对照实验 ——
往 `out/renderer/assets/` 放一个假文件，分别在 `emptyOutDir: false` / `true` 下构建：
前者它**还在**、后者被清掉。这一下就把"真残留"与"正常的两文件结构"分开了。

**留下的有效结论**：`emptyOutDir` 仍然要设（vite 的 outDir 在项目 root 之外时它默认是 `false`，
残留**是**真实存在的口子，只是我举的例子错了），但理由换成了正确的那个。**判据没变，理由换了。**

**报告用法**：与 AGENTS.md §7 里那两条"量法本身的 bug"（直接量 `<input type=radio>` 得到 13×13、
把 24×28 的列头判成过小）同一类。一句话：*判断"重复"要证明到「同一份内容出现了两次」，
而不是「看到两个相似的文件名」—— 后者连大小都不看，就只是个猜测。*

## P-118 ★★ 顶层 `node_modules` 里的包**不等于**本项目的直接依赖 —— 删依赖前必须算闭包

**现象**：清点 asar 时看到 `openai`(7.3MB)、`@google/genai`(11.8MB)、`@anthropic-ai/sdk`(6.8MB)、
`web-streams-polyfill`(8.5MB)、整片 `@aws-sdk/*` 与 `@smithy/*` 都躺在**顶层** `node_modules` 里
—— 而 `package.json` 里根本没有这些名字。一个很自然的判断是"这是 devDependencies 漏进来的，可以删"。

**真相**：它们是 **Pi 的依赖被 npm hoist 上来的**。证据有三条：
① Pi 自带 `npm-shrinkwrap.json`（依赖被锁定）；② `scripts/pi-import-graph.mjs`
（只跑**包根**导入）**看不到**它们，说明不在急切导入图上；③ electron-builder 真机日志里的
`duplicate dependency references` 列出的正是这一批 —— 它们属于 Pi 的 **provider 懒加载路径**。
所以删掉它们有相当的风险：**可能不影响 DeepSeek，但会让别的 provider 在真正被用到时崩**。

**根因（判据层面）**：`node_modules` 的**物理布局**（在顶层还是嵌套）
**不表达"谁依赖谁"**。npm 的 hoisting 会把深层依赖提到顶层，
于是"在顶层"既可能是本项目的直接依赖，也可能是**任何**传递依赖 —— 从外观上无法区分。

**解法**：**算闭包，不看位置**。`scripts/check-bundle-size.mjs` 从 `package.json` 的
`dependencies` 出发，按 Node 的解析规则（从包所在目录向上找 `node_modules/<name>`）
求传递闭包；asar 里**不在闭包里**的包才是"不该进包的"。
排查阶段也是先用这套算法，才敢把"**31 个包 / 167MB**"这个结论说出口 ——
否则那 167MB 里到底哪些是垃圾、哪些是 Pi 的依赖，只能靠猜。

**报告用法**：依赖治理里最容易犯、也最贵的一种错 —— 按"名字眼熟不眼熟"删包：
删对了省体积，删错了**只有当学生用到那条路径时才崩**（演示现场才炸的那种）。
一句话：*要判断一个包该不该在包里，问的是「**谁依赖它**」，
而这个答案在 `package.json` 的依赖图里，不在 `node_modules` 的目录树里。*
