## D-001 嵌入模型选 fastembed bge-small-zh-v1.5（512 维 / 约 90MB / 无 Ollama）

- **日期**：2026-09-16
- **决策**：本地嵌入使用 fastembed + ONNX 推理的 `BAAI/bge-small-zh-v1.5`，维度 512；不引入 torch，不依赖 Ollama。
- **理由**：「这是本方案最大的风险消除」——原方案的「Ollama 需用户另行安装」是**演示现场头号翻车点**，改为模型随应用打包后**开箱即用、纯 CPU、离线可用**；体积 90MB 对 2.24GB，安装包体积相差 **20 倍以上**。反向论证同样成立：若改用 Ollama，「零依赖、开箱即用」这条创新点将不再成立（自相矛盾）。
- **被否决的方案**：BGE-M3（1024 维，2.24GB，需 Ollama + torch）——需用户另装 Ollama，是演示现场头号翻车点；安装包体积相差 20 倍以上。PiAgent 提案第 3.1 节也写 BGE-M3 + Ollama，但**未给出回退理由**，且该改动与 Pi 无关。
- **代价 / 风险**：检索质量可能不足；升级路径按序为 `bge-base-zh-v1.5`（768 维）→ 更大模型，**升级时须同步改 `vec0` 维度并重建索引**，维度必须写在配置常量里、勿散落硬编码。缓解手段是检索侧还有 FTS5 + numpy 混合召回（见 D-013）。
- **服务哪条评分**：创新性（数据不出端、零依赖开箱即用）；同时直接消除演示现场头号翻车点。

## D-002 契约唯一来源 = pydantic → OpenAPI → 生成 TS（含 Tool 参数一致性断言）

- **日期**：2026-09-16
- **决策**：`server/app/contracts.py` 的 pydantic 模型是**唯一手写契约来源** → FastAPI 自动产出 `/openapi.json` → `openapi-typescript` 生成 `desktop/src/shared/api-types.ts`（**生成物，不手改**）。Pi Tool 的参数用 TypeBox `TSchema` 声明，但**必须与 pydantic 模型做一致性断言**。
- **理由**：整套防漂移机制已经在运行——`scripts/export_openapi.py --check` 做**字节比对**，TS 编译报错即为契约漂移告警；改为手写 TS 接口会使这套机制**整体作废**。v2 补充：TypeBox 与 pydantic/JSON Schema **不是逐字段等价**（`Record<string, number>`、`unknown`、`Optional` 的映射有差异），所以 Tool 的 `parameters` 必须由 `api-types.ts` 里的对应类型手写 TypeBox，再用**断言脚本**校验其 JSON Schema 与 pydantic 导出结果一致——**不允许出现「pydantic 改了、Tool 参数没改」的静默漂移**。
- **被否决的方案**：手写 TypeScript 接口（PiAgent 提案第 6 项）——提案未给理由；一旦手写，`--check` 字节校验 + 架构守卫这套防漂移机制全部失效。
- **代价 / 风险**：改任何模型都要重跑「OpenAPI 导出 → TS 生成」，并再跑一次 Tool 一致性断言；因此纪律是**每完成一步跑一次 `npm run typecheck`**，不要攒到最后修。断言脚本 `desktop/scripts/check-tool-schema.mjs` 是 D4 产出。
- **服务哪条评分**：设计合理性 25%（工程严谨性）；对应风险表 #12「契约前后端漂移」。

## D-003 动画 = 模板优先 + 生成补充

- **日期**：2026-09-16
- **决策**：内置 6–8 个高质量动画模板（排序、神经网络、决策树、梯度下降、循环、变量）；LLM 只负责「按知识点选模板 + 填参数 + 生成文案」，**自由生成仅作为模板未命中时的补充路径**。配套容错链路：错误捕获 → 重试 ≤3 → 仍失败 → 降级 `fallback_text` + 静态 SVG。
- **理由**：原方案**自认**「一次性生成 HTML 失败率过高」是**头号风险**（Deepseek 研判与 PiAgent 提案都写的 LLM 一次性生成完整 HTML，而提案并未回应这条自认风险）。模板优先把不确定性从「生成整页代码」压到「选模板 + 填参数」，从而**可校验、可重试、可降级**。
- **被否决的方案**：LLM 一次性生成完整 HTML——失败率高，且失败后没有任何可回退的结构（没有模板就没有 `source: "template"` 这条稳定路径）。
- **代价 / 风险**：模板库需要人工建设与校验；模板未命中的场景仍需自由生成兜底。砍单顺序第 3 档即「动画自由生成 → 全模板化」。
- **服务哪条评分**：多模态交互质量 25%；用户体验 15%（失败时界面不白屏）。

## D-004 编排迁移到 Pi Agent SDK（TypeScript，嵌入 Electron 主进程）

- **日期**：2026-09-16
- **决策**：编排框架从 **LangGraph（Python）** 换成 **`@earendil-works/pi-coding-agent`**（纯 ESM TypeScript），**内嵌 Electron 主进程**；**锁 `^0.85.1`**（0.85.0 在 Electron 里因 `esbuild` 崩溃，0.85.1 修复）。SubAgent 用自有 Extension + Tool 注册实现。
- **理由**（三条实质理由，逐条引自执行文档第 0 节）：① 「**状态流转图不再是必需品，而 Extension/Tool 注册是**」——`before_agent_start` 允许**每轮**替换 systemPrompt，比 LangGraph 的固定图更贴合「学段语气逐轮微调」；② 「**会话持久化与『一人一库』的冲突自动消失**」——原方案 `compile(checkpointer=...)` 把 checkpointer 绑死在图实例上，而学生库一人一文件；Pi 把对话历史交给原生 JSONL 会话树、按学生分目录，**冲突从根上不存在**，且分支/恢复能力是白送的；③ 「**路由从确定性条件边改为 LLM 自主选 Tool**，更贴合真实教学对话的多意图混合」。
- **被否决的方案**：① **维持 LangGraph（Python）**——状态流转图这个主要卖点已由工具调用轨迹图替代（D-014），且固定图与「每轮微调学段语气」的需求不匹配；② **把 Pi 的 RPC 模式作首选**（`pi --mode rpc` 作子进程、不 import SDK）——能绕开 `esbuild`，但会形成 **Electron → pi 子进程 → Python sidecar 三进程**，且 RPC 模式下 `before_agent_start` 等 hook 的注册要走额外 IPC 层。**保留为 D3 打包冒烟的 Plan B**，不作首选。
- **代价 / 风险**（已接受，务必知悉）：① **失去原生模块零依赖**——Pi 包根导入会拖入 `esbuild`，需 asar 解包 / 按架构打包 / 签名，**是 v2 最大新增风险**（风险 #15，见 P-024）；② **v2 时期的 S01/S02 实现已随删码作废**（v3 从零重建）——但设计结论直接继承：sidecar 握手、token 鉴权、pydantic 契约链、架构守卫的意图全部保留，**传输层从零即 IPC、没有「SSE → IPC」返工**（D-007）；③ **多语言边界移动**——编排移到 TypeScript，Python 侧退化为「数据/RAG/嵌入服务」，`TutorState`（LangGraph TypedDict）作废。
- **服务哪条评分**：设计合理性 25%；对应汇报预设第 1 问「为什么用 Pi 而不是 LangGraph」——**主动讲代价比被问出来更可信**。

## D-005 保留 Python sidecar，不做「Pi + better-sqlite3 全进 Electron」

- **日期**：2026-09-16
- **决策**：编排进 Electron 主进程，但**数据 / RAG / 嵌入仍留在 Python sidecar**（FastAPI，绑定 `127.0.0.1` + 随机 token 鉴权）。这是主动权衡，不是妥协。
- **理由**：① 「**保住『Electron 侧无原生数据库模块』**」——数据库、sqlite-vec 扩展、fastembed ONNX **全部留在 Python**，这是**刻意保留的风险隔离**，不因换编排框架而放弃；② **继承 S01/S02 已验证的设计结论**——sidecar 端口握手、随机 token 鉴权、pydantic 契约链、架构守卫测试按同一方案重建（v3 从零实现，落点是票 02 / 04 / 05 / 09）；③ `before_agent_start` 每轮可换 systemPrompt、对话历史交 Pi JSONL、工具调用轨迹可导出，这三条收益与进程模型无关，不需要为此删掉 sidecar。
- **被否决的方案**：**Pi + better-sqlite3 全进 Electron，删除 Python**——需主动废除 `AGENTS.md` §4「Electron 侧不得引入任何原生数据库模块」这条硬约束，并放弃 S01/S02 时期定型的数据侧设计（sidecar 握手与鉴权、契约链、守卫）；还要把 sqlite-vec 换掉、把 fastembed 换成 Ollama 或云 API，**等于把「零依赖、开箱即用」这个演示优势丢掉**。收益不足以抵消。
- **代价 / 风险**：多语言边界从「HTTP 两侧都是代码」变成「TS 编排 + Python 服务」；Sidecar 多一个进程要管理生命周期（见 P-006 / P-007）。**决策翻转代价最大的一条**——B-1 若翻转，会连带作废执行文档第 6、7、8 节与数据侧的既有设计。
- **服务哪条评分**：设计合理性 25% + 创新性（数据不出端、本地化隐私架构）。

## D-006 混合后端（TS 编排 + Python 数据服务）与「一套逻辑只写一遍」的四条边界规则

- **日期**：2026-09-16
- **决策**：接受后端**两种语言**（TypeScript 编排 + Python 数据服务），但用四条边界规则约束，防止同一逻辑在两侧各写一遍：
  1. **编排与 LLM 调用只在 TS 侧**（Electron 主进程的 Pi）；Python 侧**无编排、无 LLM 调用**（`server/` 不建 `llm/` 与 `agents/`，见执行文档 §7.2 的 v3 变更）。
  2. **数据 / RAG / 嵌入只在 Python 侧**；**Electron 侧不得引入任何原生数据库模块**。
  3. **RAG 四级降级链只在 Python 侧一次调用内完成**，编排层不感知降级（见 D-013）。
  4. **契约只在 pydantic 一处手写**，TS 类型是生成物、不手改（见 D-002）。
- **理由**：边界一旦模糊，迁移的代价就会以「同一逻辑维护两份」的形式反复出现——执行文档在降级链处把这条讲得最直白：降级链若不留在 Python，**「TS 侧要重复实现一遍同样的逻辑」**。这四条把「谁能写哪段逻辑」钉死，是 D-004 + D-005 这个混合架构成立的前提。
- **被否决的方案**：① 全 Python 单栈（回到 LangGraph 方案，见 D-004）；② 全 TS 单栈（见 D-005）；③ 两侧都实现关键逻辑（看似保险，实则两份实现必然漂移，且现场无法判断哪份生效）。
- **代价 / 风险**：跨语言调用必须走冻结的 HTTP 契约，禁止临时加松散字段；Python 侧的能力边界要靠 code review 守（如「Python 里不得出现 LLM 调用」）。
- **服务哪条评分**：设计合理性 25%（分层清晰、职责单一）；汇报预设第 3 问「为什么编排在 TS、数据在 Python，不统一」。

## D-007 渲染进程 ↔ 主进程传输层用 IPC，不用 HTTP + SSE

- **日期**：2026-09-16
- **决策**：渲染进程 ↔ 主进程的传输层用 **IPC 事件流**（`webContents.send` / `ipcRenderer.on` + preload 白名单），**不用 HTTP + SSE**，但**6 事件词表一字不改**：`delta | citation | payload | blocked | done | error`。
- **理由**：执行文档第 6.4 节原文——「编排运行在 Electron 主进程内，渲染进程与它同属一个应用 —— **IPC 比「本机 HTTP + token + CORS + 禁用缓冲」更简单、更快、且天然没有跨源与鉴权问题**」。补充判断：**本项目从零实现，传输层一开始就是 IPC**，不存在 SSE 通道、也不存在 SSE 解析层——因此**不给不存在的实现写反向守卫断言**（§6.4 要求守卫一律写成正向断言）。
- **被否决的方案**：沿用 HTTP + SSE——需要自己处理本机端口、token 传递、CORS、响应禁用缓冲四件事，且这四件事每一件都能在演示现场翻车（见 P-008）。
- **代价 / 风险**：**没有返工成本**——前后端一开始就按 IPC 写（v3 抹掉了「SSE → IPC」这一步），前端取数直接写订阅回调；**不变的是词表**。守卫写成**正向断言**：「聊天事件流必须经 preload 白名单 IPC 通道送达」（§6.4）。
- **服务哪条评分**：设计合理性 25%；并实测消除了一整类现场故障（见 P-008）。

## D-008 渲染进程不直连 sidecar，主进程是唯一的 HTTP 客户端

- **日期**：2026-09-16
- **决策**：渲染进程只经 IPC 与主进程通信，**不直接访问 sidecar 的 `/api/*`**；sidecar 的 HTTP 客户端集中在 `desktop/src/main/bridge/`，由主进程**统一注入 `X-Auth-Token`**。
- **理由**：① **token 与端口都不进渲染进程**，暴露面最小；② IPC 天然没有跨源请求，**401 缺 `Access-Control-Allow-Origin` 那类「假故障」整类消失**（P-008）；③ Tool 是调 Python 的唯一入口（`rag_search` → HTTP → Python），把 HTTP 客户端集中在一处，脱敏与鉴权才有唯一的落点。
- **被否决的方案**：渲染进程直接 `fetch` sidecar（S02 的原形态）——需要在浏览器侧处理自定义 header、CORS、缓冲区，且 renderer 必须持有 token。
- **代价 / 风险**：所有需要 sidecar 数据的新功能都要在主进程加一层转发（Tool 或 IPC handler），不能图省事在 renderer 里直接发请求。
- **服务哪条评分**：设计合理性 25%（安全边界清晰）；合规（凭据不进渲染进程）。

## D-009 学段 = 显式选择为权威 + 自动推断为增强　**【已废止，被 D-020 取代（2026-09-16）】**

> ⚠️ **本条决策已被推翻，正文仅作历史留档，不要照它实现。** 取代它的是 **D-020**；
> 现行口径见执行文档 §10（§0.4、§13.2 第 8 项、§13.3 B-3、§14.1、§15、§16 均已同步翻转）。

- **日期**：2026-09-16
- **决策**：**学生显式选择过 → 显式值为权威，自动推断只写「建议」、不直接改**；从未选择 → 冷启动默认值（小学高年级）生效，推断达阈值后弹建议条、由学生确认；确认后写入 `grade_history(source=confirmed)`。规则引擎三重约束：置信度 **< 0.6 不调整**、**连续 3 个信号同方向**、调整后 **5 轮冷却期**；并保留**人工纠偏出口**（学生可随时显式重选，重选后冷却期重置）。
- **理由**：需求原文是「**学生可选择所在学段**（小学低年级/小学高年级/初中/高中）或教材，智能体根据选择自动匹配……」，**「可选择」是明确要求**；且验收标准含「同一问题在四学段下回答的深度与语气可明显区分（留四张对比截图）」，那是 20% 教育适配性的**现场演示动作**，去掉按钮该动作就不成立。但推断机制必须做：它是 15% 创新性里可讲的实质技术，且演示效果更好——「系统发现你连答对 3 题，建议升到初中 → 学生点确认」，**既展示了机制，又把控制权留给学生**（对未成年人产品是加分项）。
- **被否决的方案**：**纯自动推断、不设前端按钮**（PiAgent 提案第 8 项）——去掉按钮会让验收动作不成立；且原提案缺人工纠偏出口，**误判会锁死体验**。
- **代价 / 风险**：双层判定的工程量（规则层每轮同步 + 第 3 轮触发的轻量 LLM 判定）与 `grade_signals` / `grade_history` 两张表的维护成本。砍单顺序第 5 档即「学段自动推断 → 只保留显式选择」，**砍掉不伤主链路**，因为显式选择才是需求要求。
- **服务哪条评分**：教育适配性 20%（四学段对比演示）+ 创新性 15%（学段信号双层判定）。

## D-010 沙箱三重隔离（且「学生代码绝不在主进程执行」上升为硬约束）

- **日期**：2026-09-16
- **决策**：① 动画在 `<iframe sandbox="allow-scripts">` 中运行，**绝对不加 `allow-same-origin`**；② Pyodide 跑在**独立 Web Worker**；③ **不得与 sidecar 进程或主线程共享执行环境**。v2 强化：因为 **Pi 的 Extension 与 Agent 同进程且拥有完整系统权限**，**「学生代码绝不在主进程执行」上升为硬约束**——`evaluate_code` 必须把代码经 IPC 交给渲染进程的 Pyodide Worker 执行、结果回传，**并写进架构守卫测试**。
- **理由**：一旦加上 `allow-same-origin`，iframe 内代码即可访问宿主，**沙箱形同虚设**；Pyodide 中的 Python 与 sidecar 的 Python 是**两个独立运行时**，学生代码跑在浏览器沙箱里、**绝不接触 sidecar**。PiAgent 提案自己承认「Extension 与 Agent 同进程、拥有完整系统权限」，这**加重**了而非减轻了沙箱的必要性。
- **被否决的方案**：① 为方便通信打开 `allow-same-origin`；② 在 `evaluate_code` 里直接在主进程执行学生代码（最省事，但学生代码与 UI、Agent 同命）。
- **代价 / 风险**：跨沙箱通信必须走 `postMessage` + `payload_id` 校验；执行结果要经 IPC 往返，链路比本地执行长；「主进程不含执行学生代码的路径」这条要有守卫测试兜住（D12）。
- **服务哪条评分**：设计合理性 25% + 合规（K12 未成年人数据）；对应验收清单 v2 新增的两条（学生代码不在主进程执行、沙箱内无法访问宿主）。

## D-011 路由交给 LLM 自主选 Tool、不设 `intent` 字段，但四条关键约束仍在代码层强制

- **日期**：2026-09-16
- **决策**：主 Agent **不设 `intent` 字段**，对话答疑**不封装为 Tool**（LLM 在「无工具可调用」时自然生成回答）；路由由 LLM 通过 Tool 调用自主决定。**但四条关键约束不放给模型**：① 学段隔离在 `rag_search` Tool 内部**由 Python 强制**（模型改不了 WHERE 条件）；② **安全终审是流式之后的独立步骤**，与 Tool 选择无关；③ **沙箱隔离是 iframe/Worker 的运行时属性**，与 prompt 无关；④ Tool 的参数用 **TypeBox 校验**，越界直接拒。
- **理由**：路由从确定性条件边改为 LLM 自主选 Tool，「更贴合真实教学对话的多意图混合」。**这不是「把控制权交给模型」**——「模型自由的只是『选哪个能力』，不是『能不能越界』」。
- **被否决的方案**：LangGraph 条件边 + 显式意图分类（原方案）——意图分类字段在多意图混合的真实对话里会持续失配，且每加一个能力就要改图。
- **代价 / 风险**：路由行为不可完全预测，因此**必须能解释**——靠工具调用轨迹图（D-014）把「LLM 为什么选了这个 Tool、关键约束在哪一层强制」讲清楚（25% 设计分的汇报动作）。另：Tool 名 → 事件 `kind` 映射已冻结（`generate_animation→animation`；`get_code_template`/`get_coding_hint`/`evaluate_code→coding`；`generate_quiz`/`submit_quiz`/`generate_variants→quiz`），**新增 Tool 必须同步登记**，否则前端收到未知 `kind`。
- **服务哪条评分**：设计合理性 25%；汇报预设第 2 问「路由交给 LLM 自主决定，还算架构设计吗」。

## D-012 三处存储分离（kb.sqlite / learning.db / Pi JSONL 会话树）

- **日期**：2026-09-16
- **决策**：**`kb.sqlite`**（全局只读，随应用分发：教材 chunk、embedding、依赖图、题库）+ **`learning.db`**（每人一份：画像、掌握度、学习历史、闯关进度、学段信号与轨迹）+ **Pi JSONL 会话树**（每人一份：对话历史、工具调用记录、分支，落 `students/<id>/pi-agent/sessions/`）。**SQLite 不存对话正文**，两者经 `studentId` + `sessionId` 关联。
- **理由**：原方案用 `SqliteSaver` 挂在**每人一份**的学生库上，导致 `compile(checkpointer=...)` **无法全局复用**（checkpointer 绑死在图实例上，而学生库一人一文件）——**冲突从根上消失**，且分支/恢复能力还是白送的。另一条是避免知识库被复制 N 份（旧研判的「每人一个库（含知识库）」）。
- **被否决的方案**：① 每人一个库且含知识库（Deepseek 研判第 5 项）——知识库被复制 N 份；② 用 SQLite 存对话正文——与 Pi JSONL 会话树职责重叠，且涉未成年人对话正文的合规成本更高。
- **代价 / 风险**：**必须显式改道**——Pi 默认写到 `~/.pi/agent/sessions/--<cwd>--/`，不改道就会跨学生混放，是**合规硬伤**（见 P-030）；**必须加自动化断言**：检测 `students/<id>/` 之外是否出现本应用的 `.jsonl`（D4 产出）。
- **服务哪条评分**：设计合理性 25%（报告第 2 章重点写「三处存储分离」）+ 合规。

## D-013 RAG 四级降级链放在 Python 一次调用内完成，编排层不感知降级

- **日期**：2026-09-16
- **决策**：降级链四级——**① 主路径** fastembed 本地向量 → sqlite-vec KNN（`WHERE grade_level = :grade`，允许向上兼容并标 `compat=true`）；**② 降级 1** 用户自填的云端 Embedding API；**③ 降级 2** FTS5(trigram) 关键词检索；**④ 兜底** 依赖图 + 章节大纲直接注入上下文——**全部在 Python 侧一次调用内完成**，编排层不感知降级，只读结果里的 `degraded: "vector" | "cloud" | "fts" | "outline"` 供轨迹图展示。
- **理由**：「**不要让编排层去感知降级——否则 TS 侧要重复实现一遍同样的逻辑**」。FTS5 那一级**必须实现**：即便 fastembed 随包分发，也可能因模型文件损坏/内存不足而失败，而 **FTS5 内置于 SQLite，永不失败**。另：sqlite-vec 加载失败时回退 numpy 暴力余弦，属**第 1 级内的子兜底**（数千 chunk 的暴力余弦是毫秒级，可接受）。
- **被否决的方案**：仅 sqlite-vec（Deepseek 研判第 7 项）——一次扩展加载失败就整条检索链路不可用，且演示现场无法回退。
- **代价 / 风险**：Python 侧检索实现复杂度上升（四个分支 + 子兜底）；结果契约里必须稳定带 `degraded` 字段，否则轨迹图讲不清「这一轮走的是哪一级」。演示前必须演练「把模型目录改名 → 自动降级 FTS5 仍能检索」。
- **服务哪条评分**：创新性 15%（嵌入式 RAG）+ 用户体验 15%（弱网/断网优雅降级）；汇报预设「网络断了怎么办」。

- **日期**：2026-09-16

## D-018 sidecar 握手：自己绑 socket，并在 serve **之前**输出单行 JSON

- **日期**：2026-09-16
- **决策**：Python 侧**不把绑端口的活交给 uvicorn**。自己 `socket.bind((host, 0))` → 拿到系统分配的真实端口 → 往 stdout 打**恰好一行** `{"event":"ready","port":N,"pid":P,...}` → 再把 socket 交给 `uvicorn.Server.run(sockets=[sock])`。绑定失败则打一行 `{"event":"error","message":"..."}` 并以退出码 2 结束。
- **理由**：
  ① `--port 0` 的真实端口只有在 uvicorn 内部建好 server 之后才知道，而握手必须在「上层能开始轮询」之前发出；
  ② uvicorn 绑定失败时的行为是 `sys.exit(1)` + 只写 stderr —— **上层拿不到可读原因**，界面只能显示「进程意外退出」，说不清是端口占用还是配置错误（票 01 实测撞到过这个场景）；
  ③ 自己绑端口后，「端口已知」「失败可读」两件事都掌握在自己手里。
- **被否决的方案**：① 用**固定端口**（如 8756）—— 端口冲突会变成常态故障，且同一台机器上跑两个实例直接互撞；② 让 uvicorn 绑端口、从 `server.servers[0].sockets[0].getsockname()` 反查 —— 能拿到端口，但**绑定失败仍然无法拦成一行可读错误**；③ 用 stderr 报错 —— Electron 只看得懂 stdout 的握手通道，写 stderr 等于没报。
- **代价 / 风险**：**握手发出的一瞬间端口尚未进入 LISTENING 状态**（uvicorn 还没开始 accept）。因此上层**必须**在握手后继续轮询 `/health` 直到 200，不能「收到握手就直接发请求」。这不是冗余设计，是协议的一部分。（开发期踩过一次：把「pid 是否等于占端口的进程」的断言放在握手后立刻执行，得到 `None`。）
- **服务哪条评分**：设计合理性 25% —— 进程生命周期与失败语义的显式设计；也直接支撑「打包后仍能跑」这条验收。

## D-019 Pi 的接入形态：主进程产物改 ESM；原生解包范围按**实测导入图**确定

- **日期**：2026-09-16
- **决策**：① 主进程构建产物从 CJS 改为 **ESM**（入口 `out/main/index.mjs`）；② `asarUnpack` 覆盖 `esbuild` / `@esbuild` / `@mariozechner/clipboard*` / pi-tui natives 四组；③ 不启用 Plan B（RPC 模式）。

  会让安装包略大（可接受）。
- **服务哪条评分**：设计合理性 25% —— 「用导入图实测确定打包边界」是可展示的工程方法；

## D-020 学段 = **完全自动推断、自动生效**（没有人工选择入口，界面只读）

- **日期**：2026-09-16
- **决策**：**取消「学生选择学段」这个人机接口**。学段由系统推断并**自动应用**：
  ① 第一层（每轮，不调 LLM）从规则里抽四类信号 —— **词汇复杂度 / 问题深度 / 答题表现 / 元认知表达** —— 写入 `grade_signals`；
  ② 第二层（第 3 轮触发，证据不足退到第 5 轮）跑**一次**轻量 LLM 判定 `{suggestedGrade, confidence}`，**它只是提议**；
  ③ **决策权在规则引擎**（`server/app/grade/rules.py`）：置信度 < 0.6 不改、连续 3 轮同向、调整后 5 轮冷却、单次最多动一级、LLM 提议与规则反向即否决；
  ④ 达阈值即**自动切换**，原子写入 `student.grade_level` + `grade_history(source="inferred")`，**下一轮** `before_agent_start` 装上新 prompt；
  ⑤ 界面**没有选择器**，只有**只读指示器**（「当前：初中」/「待判定」）。冷启动默认小学高年级，基线轨迹 `from_level = NULL`（**不算一次变更**，不触发冷却）。
  **无 API Key 时第二层整层跳过**，第一层照常工作、照常能改学段，但显式报 `degraded="no_llm"`（降级不许静默）。
- **理由（用户的）**：**学段应当由模型从学生的输入里判断出来**，人工选一遍是冗余的。
  让未成年人先自报「我属于哪个学段」，等于把系统该做的判断转嫁给他；而系统本来就在读他的用词、提问深度与答题表现。
  约束条件也没变差：**判定权仍在规则引擎**（不在 LLM），关键路径没有变得更不可控。
- **被否决的方案**：① **D-009 的「显式选择为权威 + 建议条 + 学生确认」** —— 即本条的取代对象：
  它要求学生先理解「学段」这个系统概念并主动操作，对低龄用户是额外认知负担，且推断明明已经能给出结论；
  ② 保留**只读 + 隐藏的手工兜底入口**（如设置页里的学段下拉）—— 会重新引入「两套真相」（手选值 vs 推断值）与优先级判定，
  而那正是 D-009 复杂度的来源，**要么有入口要么没有**，不做半套。
- **接受的代价（主动写进报告与汇报，不要回避）**：
  ① **需求里的那句「学生可选择所在学段……智能体根据选择自动匹配」不再被字面满足** —— 我们把它实现为
  「系统自动判定 + 只读展示」。这是**用户明知并接受的取舍**，不当作遗漏来处理（执行文档 §10.1 与 §0.4 已如实记录）；
  ② **四学段对比演示失去 UI 入口**（原验收动作是「点按钮连切四学段」）：改为**同一话题由浅入深连续提问**，
  让系统自己判上去，四张截图对应四次自动判定生效后的回答（§14.1 与 §15 已同步改写）；
  ③ **原「误判可由学生重选纠正」的出口随选择器一并取消** —— 替代机制见下条。
- **误判的补偿（没有人工纠偏出口之后的兜底，汇报必答）**：
  ① **元认知表达信号本身就是向下方向** —— 学生说「听不懂」「再讲一遍」「换个说法」，连续 3 轮同向且置信度达标即**自动下调一级**；
  **学生不需要知道「学段」这个概念，也不需要找到任何设置项**；
  ② 规则引擎四条硬约束把影响面限制在「**一次最多一级、且至少持续 5 轮**」，不会来回跳变；
  ③ 第二层的 LLM 提议若与规则反向会被直接否决（`llm_conflict`），**单次模型误判推不动学段**；
  ④ 顶部只读指示器让当前判断**始终可见**，误判是可被观察、可被复盘的（`grade_history` 全程留痕）。
- **代价 / 风险**：双层判定的工程量与 `grade_signals` / `grade_history` 两张表的维护成本（与 D-009 相同，未减少）；
  **新增风险 #21**：误判且无人工出口 —— 对策如上，并在执行文档 §17 登记。
  砍单顺序第 5 档由「退回显式选择」改为「**只保留第一层规则信号**（砍掉第二层 LLM 复核）」——**不存在退回选择器这条退路**。
- **服务哪条评分**：教育适配性 20%（学段随输入自动适配 + 只读展示自适应证据）+ 设计合理性 25%（判定权在规则引擎、
  关键约束不交给模型）+ 创新性 15%（学段信号双层判定）。

## D-021 扩展的触发方式：不依赖 Pi 事件，由 runtime 显式驱动

- **日期**：2026-09-16
- **决策**：把「依赖 Pi 事件钩子」改成 **runtime 显式调用扩展的入口函数**。学段扩展只暴露
  `observeTurn(text)` / `systemPromptFor(incoming)` / `appliedGrade()`，由 `runtime.ts` 在自己的
  回合流程里调用（**早返回之前**），不再 `pi.on('input')` / `pi.on('before_agent_start')`。
- **理由**：
  ① 实测发现这两个事件在「无 API Key」路径上**根本不会到达**（`prompt()` 在派发 `input` 前后
     都要过凭据校验，而 runtime 早已 return）——**依赖一个可能不来的事件，等于把功能建在流沙上**；
  ② runtime 本来就掌握回合的完整生命周期（它决定何时不调 `prompt()`），
     让扩展被动等事件反而制造了「注册成功但不生效」这种静默失败；
  ③ 显式入口**可单测、可断言调用次数**，不再需要构造 Pi 的事件对象来测。
- **被否决的方案**：① 保留 `pi.on('input')`，在无 Key 分支里**手工**补发一次事件 ——
  依赖内部 API 形状，且「手工补发」与「真实事件」两条路径迟早分叉；
  ② 保留事件钩子，另加一个 runtime 侧的兜底调用 —— **双计风险**（同一轮被观察两次，
  连击计数被污染，学段会因错误证据而升降）。
- **代价 / 风险**：扩展不再「自注册即可用」，多了一层 runtime 与扩展的接口约定需要维护；
  新增扩展时必须显式接线，否则同样会静默不生效。**缓解**：把入口函数作为导出的类型契约，
  并用守卫断言扩展不得订阅 Pi 事件（防止两种机制混用又回到双计问题）。
- **服务哪条评分**：设计合理性 25% —— 「把不确定性从运行时事件挪到显式调用」是典型的
  提高可预测性的架构决策；也是 P-038 那条踩坑的正式结论。

## D-022 BaseURL「什么都不规范化」：探测的就是将要保存的那个地址

- **日期**：2026-09-16
- **决策**：设置页**不**对用户填的 BaseURL 做任何自动规范化（不去 `/v1`、不补 `/v1`）。
  「连通性探测」**原样探测用户填的那个地址**，因为那就是**保存后实际会被使用的地址**。
  当探测拿到 404/405（路径不存在）时，另做一次**只用于诊断**的对照探测（`/v1` ↔ 无 `/v1`），
  然后把结果**明说**给用户：告诉他该改成哪个地址，**但不替他改**。
- **理由**：OpenAI 兼容网关这件事有**两种都合法**的形态——有的网关只认
  `https://host/v1`，有的（含 Pi 内置的 DeepSeek provider）用的是 `https://host`（**无 `/v1`**）。
  既然两种都可能是「唯一正确」的那个，任何一侧的静默改写都会**重新制造**我们要消灭的故障：
  「默认值能跑、用户改一下就连不上」——用户填的和他保存的不一致，而界面上看不出来。
  探测的意义是**如实反映保存后的行为**，不是把用户的输入改成我们喜欢的形状。
- **被否决的方案**：① **自动补 `/v1`**——对直连式网关（`https://api.deepseek.com`）会直接改坏；
  ② **自动去掉 `/v1`**——对网关式部署会改坏，且会悄悄覆盖用户的显式输入；
  ③ **只探测默认地址**——那就测不出 HTTP 语义，等于没探测。
  最终保留的「诊断对照」是**输出信息**而不是**修改动作**：给出替换地址，让用户自己决定。
- **代价 / 风险**：用户要自己照着提示改一次地址（多一步操作）；
  探测逻辑要分两步（原样 + 对照），比「先规范化再探测」复杂一些。
  实测收益：`/v1` 正确 → `ok`；缺 `/v1` → 可读 404 文案**并点名该换成哪个 URL**；
  Key 错 → 401 文案；端口无人监听 → 「连接被拒绝」2.0s 返回；黑洞地址 → 「连接超时」3.0s 返回。
- **服务哪条评分**：设计合理性 25%（探测的语义边界清晰、不替用户做隐式决定）+
  用户体验 15%（失败原因是可读中文并带**可执行的下一步**，不是只吐一个 `false`）。
  这也是需求「必须支持下改供应商 / BaseURL / ModelID」那条硬要求的正确实现方式。

## D-023 答案防泄漏用**两个模型**（内部 `QuizQuestion` / 对外 `QuizQuestionOut`），不用 pydantic `exclude=True`

- **日期**：2026-09-16
- **决策**：契约层定义**两个模型**：内部 `QuizQuestion`（**含 `answer`**）与对外
  `QuizQuestionOut`（**根本没有 `answer` 这个字段**）。两者之间只有一个显式转换入口；
  对外模型才进 OpenAPI、才生成 TS 类型。
- **理由**：`exclude=True` 是**每次序列化时都要正确执行**的约定，而两个模型是**结构上不存在**
  那个字段——后者不会因为「有人在某处忘了传 `exclude`」而泄漏。
  实测两种证据并存：对同一条哨兵标准答案走完 `/api/quiz/variants` 与 `/api/quiz/grade` 全链路，
  **响应里既没有答案值、也没有 `answer` 这个键**；而同一时刻
  `answer in QuizQuestion.model_fields` 为 **True**。
  也就是说：**「答案在后端存在」与「答案不可能到前端」同时成立**，这两件事不再互相牵制。
- **被否决的方案**：① **单模型 + `exclude=True`**（或在出参时 `model_dump(exclude={"answer"})`）——
  依赖「每一处调用都记得排掉」，一处漏掉就是答案泄漏，而且漏掉时**没有编译期/类型期信号**；
  ② **前端收到答案后自己剥离**——等于把答案发给了不可信端，最坏的一种；
  ③ **黑名单删字段**（把 `answer` 键从对象里 `delete` 掉）——同样依赖执行到位，
  新增 `answerText` / `solution` 之类的同义字段时立刻失守。
- **代价 / 风险**：多一个模型与一个转换函数要维护；字段增减时**两处都要改**
  （转换函数逐字段显式列出，**不用** `model_dump(exclude=…)`——漏一个字段会立刻被断言抓到，
  这正是把「隐式」换成「显式」的收益）。编排层还有第二道：投影用**白名单**挑字段，
  测试往载荷里硬塞 `answer` / `answerText` / `solution` / `correctOption` 也带不出去。
- **服务哪条评分**：设计合理性 25%（把「防泄漏」从运行时纪律变成**类型层事实**）。
  报告里这是「**约束应该建在结构里，而不是建在提醒里**」这个论点的具体证据。

## D-024 第一层学段信号的**提取与规则只在 Python 侧**，桌面端只上交原始证据

- **日期**：2026-09-16
- **决策**：四类学段信号（词汇复杂度 / 问题深度 / 答题表现 / 元认知表达）的**提取**与
  **判定规则**（阈值、方向一致性、冷却期、单次最多动一级）**全部只在 Python 侧实现**
  （`server/app/grade/signals.py` + `rules.py`）。桌面端 `extensions/grade.ts`
  **不做任何规则/词表匹配**，只上交「本轮证据」（`{turn, text, sessionId}`）并**只认服务端回的结论**。
  连「答题表现」这一路也由服务端**自己从 `learning.db` 读**，桌面端不上交答题数据。
- **理由**：**两份实现必然漂移，而漂移的表现是「学段莫名乱动」**。
  这是最难排查的一类 bug：两边各自看都正确，合起来才错，且表现为一个**随时间变化的行为**
  而不是一次崩溃。把提取与判定收成一份，等价于把「学段为什么变了」这个问题
  变成**一个可查询的单一事实来源**。
- **被否决的方案**：① **桌面端也做一份规则匹配**（哪怕只是为了「快速给个初步判断」）——
  两套阈值迟早不一致，而学段会因此来回跳；
  ② **桌面端算好信号再上传**——桌面端一旦承担判定，就有了第二份口径，
  且服务端无法复核（它拿到的是结论而不是证据）；
  ③ **把判定下放到桌面端以省一次 HTTP**——学段是跨模块共享的状态（`student.grade_level`、
  `grade_history`、RAG 的 SQL 过滤都依赖它），权威必须在一处。
- **代价 / 风险**：桌面端每轮要多一次 fire-and-forget 的上交请求（**不阻塞对话**，
  判定的产物**下一轮**才用，失败只记日志）；「无 API Key」时第二层整层跳过，
  由服务端显式回 `degraded="no_llm"`（**降级绝不静默**），第一层照常工作、照常能改学段。
  另外 D-021 已记录：扩展改为由 runtime **显式驱动**（不依赖 Pi 事件），
  这也是为了让这条上交路径在「无 Key」的情况下**仍然可达**。
- **服务哪条评分**：设计合理性 25%（单一判定权威 + 边界清晰）+
  教育适配性 20%（学段能自动适配，且适配过程可复盘——`grade_signals` 与 `grade_history` 全程留痕）。

## D-025 砍掉 matplotlib：用 8.8 MB 换「编程模块体积不翻倍」

- **日期**：2026-09-16
- **决策**：Pyodide **只预置 `numpy`**，**不预置 `matplotlib`**。
  `import matplotlib` 会报 `ModuleNotFoundError`，由报错翻译给出可读中文提示。
- **理由**：实测 matplotlib 的**依赖闭包共 12 个包、约 8.8 MB**（其中 matplotlib 本体 6.98 MB、
  pillow 1.04 MB）。加上 Pyodide 运行时本体（wasm 9.2 MB + stdlib 2.4 MB）与 numpy（2.8 MB），
  编程模块的静态资源会从 **约 16 MB 涨到约 25 MB**。
  本项目是**随包分发的桌面安装包**（不是网页），这 8.8 MB **直接进安装包**；
  而教学场景里的排序 / 决策树 / 神经网络都只需要 `print` 与 numpy。
  同一轮还砍了 Monaco 里 **约 17.4 MB** 用不到的语言 worker（**只注册 Python 一个语言贡献**）。
- **被否决的方案**：① **预置 matplotlib**——为「将来也许要画图」付 8.8 MB 与更长的加载时间，
  而本期的四种交互里没有一处需要它；
  ② **改成按需从 CDN 加载**——**任何 CDN 引用都是断网演示的必然翻车点**，
  与本项目「全本地、开箱即用」的卖点直接冲突，这条不可谈；
  ③ **先预置、体积超预算再砍**——Pyodide 的包加载是**构建期产物**，
  临时砍会造成「文档写了、包里没有」的不一致，不如一开始就定清楚。
- **代价（主动记录，不回避）**：学生写 `import matplotlib` 会失败。
  缓解方式是把这条**并入既有的报错翻译链**（`ModuleNotFoundError` 已有面向学生的中文反馈），
  学生看到的是「这个环境没有这个模块」而不是一个原始 traceback。
  另一处代价是**未来恢复需要重新走一遍打包验证**（资源要重新自托管，不能走 CDN）。
- **服务哪条评分**：用户体验 15%（更小的安装包、更快的编程卡片首次加载）+
  设计合理性 25%（**有数字支撑的体积决策**，而不是「感觉有点大」）。
  报告里与「砍单顺序」那一节配套讲：这是**在明确的预算约束下做的取舍**，
  且代价与恢复路径都写清楚了。

## D-026 知识库作为随包只读资产：解析顺序「随包优先于 per-user」

- **日期**：2026-09-16
- **决策**：`kb.sqlite` 的解析顺序为 `K12_KB_PATH` 环境变量 → **随包只读库** → per-user `<data-dir>/shared/kb.sqlite`（重建目标）→ 缺席时诚实降级到 `outline`。发布前把库 VACUUM 并切成 `journal_mode=delete`。库**由构建产出、不入 git**（`.gitignore` 的 `*.sqlite` 规则保留）。
- **理由**：
  ① 执行文档 §8.1 要求知识库「随应用分发、只读」——它是**版本化的内容资产**，
     不是用户数据；用户不该为了「第一次能用」而先跑一遍建库脚本；
  ② **随包优先于 per-user 是刻意的**：反过来会让上一次重建留下的旧库**遮住**随包的新内容，
     表现为「装了新版本，还在检索旧教材」——这种 bug 极难归因；
  ③ 环境变量仍然**无条件压过一切**，保住「指向一份坏库来现场演示降级链」这个演示手法。
- **被否决的方案**：① 用 `extraResources` 放到 `<resourcesPath>/kb/`——
  那样库就在 sidecar 产物**之外**，sidecar 不再自包含、路径要穿过 TS↔Python 的 spawn 契约，
  而且构建自检**根本看不到它**（正是当初漏掉这个缺陷的原因）；
  ② 首次启动时就地建库——需把教材与嵌入模型都在启动路径上跑一遍，冷启动从秒级变成十秒级，
  与「零依赖开箱即用」的演示优势冲突；③ 把库提交进 git——二进制、每次内容更新都产生巨大 diff。
- **代价 / 风险**：内容更新要**重建并重签 sidecar**（约 6s 建库 + PyInstaller）；
  库进了签名载荷。安装包 +0.94 MiB（NSIS 压缩后）。
- **服务哪条评分**：创新性 15%（数据不出端 + 开箱即用）与教育适配性 20%（内容随包可检索）。

## D-027 验收驱动方式：必须走用户真实入口，不做「直调底层接口」的采样

- **日期**：2026-09-17
- **决策**：所有对外宣称的验收（尤其关卡判据）**必须以用户能做出的动作为驱动**：

     两者的差异不是理论问题 —— 实测中它**凭空制造了一个不存在的渲染 bug**，
     我还派了子代理去修，等于把误判固化成代码与测试（见 P-046/P-047）；
  ② 用户路径隐含了 UI 里的状态建立（`store.send()` 建轮次、回执与流式事件的配对），
     绕过它等于把这些前提删掉再看行为，结论不可外推；
  ③ `scripts/verify-ui.mjs` 一直坚持「填输入框 + 点按钮」，这条既有纪律在本次直接避免了误判。
- **被否决的方案**：① 直调 IPC 接口（更快、更好写）—— 就是本次踩的坑；
  ② 只跑单元测试 —— 单测都绿着，真实路径曾经是坏的（另一个方向的教训）；
  ③ 用截图判断 —— 本机截图受前台窗口/DPI 影响不可靠，且不可断言。
- **代价 / 风险**：每个验收脚本都要处理「填值触发 v-model」「等按钮可用」这类 UI 细节（`verify-ui.mjs` 里已有可复用写法）；
  比直调慢几十秒。**这个代价必须付。**
- **服务哪条评分**：验收可信度本身（报告与汇报的「你怎么知道它是好的」）。

## D-028 供应商配置的权威源是**设置页**：`models.json` 由设置派生（语义反转）

- **日期**：2026-09-17
- **决策**：把「设置 → Pi」从**两条互不相通的路径**收敛成一条：
  ① 契约加 `providerId`（Pi 的 provider id，与纯显示的 `providerName` 分工）；
  ② `models.json` 从「首次运行写一次、之后一个字节都不动」改为**由设置派生、每次建会话/保存重写**；
  ③ 新增 `GET /api/settings/runtime`（**含明文 Key**，仅主进程）作为这条链路唯一载体，
     主进程启动先读它、保存后热应用它。
- **理由**：
  ① 改造前的实际状态是**断的**：设置写 Python 的 `config.json`，Pi 读
     `students/<id>/pi-agent/agent/models.json`，两者永不相通 ——
     表现为「设置页改完、重启应用，Pi 用的还是旧值」（实测确认）；
  ② `models.json` 旧语义（幂等不覆盖）本意是「不覆盖用户手改」，代价是**设置永远进不去 Pi**：
     文件在首次运行后就是死值。既然设置页已成为唯一写入入口，`models.json` 就应当降级为**派生产物**；
  ③ 明文 Key 必须有个通路，但**不能**经渲染进程（它的读接口恒回掩码是有意设计）。
     选「主进程专用接口」而不是「TS 自己读 config.json」：后者会把原子写/损坏备份/
     snake-camel 双容忍这套容错逻辑在两侧各写一遍，两套实现必然漂移。
- **被否决的方案**：① 主进程直接 `readFileSync(config.json)` —— 容错逻辑重复实现（见上）；
  ② 写进 Pi 的 `auth.json` —— 盘上多一份明文副本，且与既有「Key 只进内存」的决议冲突；
  ③ 把 `providerId` 塞进 `providerName` 复用 —— 显示名允许随便填，两者语义不同，混用必然出错。
- **代价 / 风险**：明文 Key 多了一条出站路径（已用三层边界约束：token 鉴权 + 渲染进程无通道 +
  只经 `setRuntimeApiKey` 进内存，并加了守卫 G13 把「前端没有入口」钉成断言）。
- **服务哪条评分**：创新性 15% / 用户体验 15% —— 「不写死供应商」是需求硬性要求，
  而 Pi 内置 40 个 provider 的现成端点与模型清单让「换一家」从手输四个字段变成一次选择。

## D-029 默认值必须与 Pi 内置目录**一字不差**，且查不到模型时**回落**而不是抛

- **日期**：2026-09-17
- **决策**：契约与 Pi 侧的默认值统一为
  `provider_id="deepseek"` / `base_url="https://api.deepseek.com"`（**无 `/v1`**）/
  `model_id="deepseek-v4-flash"`；并且 `resolveModelForProvider()` 在
  `getModel()` 落空时**回落到该 provider 的第一个可用模型 + 打一条可读日志**，而不是抛异常。
- **理由**：
  ① 老默认值 `deepseek-chat` **不在 Pi 的内置 deepseek 目录里**（目录里只有
     `deepseek-v4-flash` / `-vision-exp` / `-pro`），`getModel()` 返回 `undefined`
     直接抛「Pi 里找不到模型」—— **第一条消息必炸**；
  ② 用户手填错模型名是常态（这也是「拉取模型」这个能力存在的理由），
     为一个可修正的配置错误让**整个对话不可用**，代价与收益不成比例；

- **服务哪条评分**：设计合理性 25% —— 「默认配置开箱即用」是最基本的设计合理性。

## D-030 学段第二层（LLM 判定）的接线改为「调用时判可达性」，不再建会话时传 null

- **日期**：2026-09-17
- **决策**：`gradeExtension.useJudge(...)` 恒接线，可达性（有 Key + checkAuth 通过 + 非探针）
  在**判定被触发时**再判；不可达就 `return null` 让扩展走 `no_llm` 降级。
- **理由**：
  ① 旧形态 `useJudge(有Key ? fn : null)` 只在**建会话时**算一次，而
     `useJudge()` 全项目只此一处调用 —— 传 null 等于把第二层**永久**关闭；
  ② 而会话可能是在「sidecar 还没起来」时降级建出来的（渲染进程挂载即读学段，
     早于 sidecar 就绪，实测确认），那种会话即便后来配好了 Key 也再不会判学段；
  ③ 判定本身有超时与异常兜底（`JUDGE_TIMEOUT_MS`），调用时多一次布尔判断零成本。
- **被否决的方案**：① 保持 `useJudge(null)`，改成「拿到 Key 后重新调一次 `useJudge`」——
     能work，但把「什么时候重调」这个时序问题留给了调用方，容易漏；
  ② 干脆不断言可达性、永远走 `lazyComplete` —— 无 Key 时会白等一次超时。
- **代价 / 风险**：判据散在闭包里，所以加了接线守卫（J4）断言「不可达时确实返回 null」
  与「判据与补全器共用同一套口径」。
- **服务哪条评分**：设计合理性 25% —— 这是「同一份配置在冷启动/热切换两条路径上行为一致」的一个实例。

## D-031 个性化记忆 = 「结构化画像注入 + 模型主动写偏好」：不引第三方 memory 插件，也不做跨会话原文召回

- **日期**：2026-09-17
- **决策**：个性化记忆只做两件事，且都在**既有骨架上接线**：
  ① **画像注入** —— 把已经算好的画像（掌握度 / 学习偏好 / 推荐下一步）**每轮**注入 system prompt，
     走既有那条唯一的 prompt 出口（与学段覆盖同一处拼装），**不再只靠模型自己想起来去调 `get_student_profile`**；
  ② **偏好采集** —— 新增 `remember_preference` Tool（模型主动写）+ `PUT /api/profile/{id}/preferences` 端点，
     补上 `profile_pref` 表缺失的写入路径（该表此前有 DDL、有读接口，**生产代码从不写它**，见 P-054）。
  **明确不做**：不引入任何第三方 memory 插件；**不做跨会话召回对话原文**。
- **理由**：
  ① **数据层已经齐了，缺的是接线不是机制**：一人一库（`learning.db`）里掌握度 / 学习历史 / 闯关进度 / 偏好表都在，
     前三个**每轮真写**（learning-log extension → `POST /api/profile/{id}/events`，判分侧写掌握度），
     偏好表是唯一缺写入路径的那个（见 P-054）；
     缺口只有两处 —— 画像**没接进 prompt**、偏好**没有写入口**。为两处接线引入一套新记忆子系统，
     等于把「断了一条线」当成「缺一台机器」。
  ② **生态调研结论（pi.dev/packages 全量枚举）**：画廊共 **5,562** 个包，其中**零个**是 RAG / 检索类领域包；
     memory 类里最接近的几个都不对口 ——
     `pi-hermes-memory` 与 `context-mode` 依赖 **`better-sqlite3`**（撞架构守卫
     **G1「Electron 侧不得引入任何原生数据库模块」**，`desktop/tests/architecture-guards.test.ts:149`；
     且 `desktop/electron-builder.yml:76` 是 `npmRebuild: false`，原生模块**不会**为 Electron 重编译，装上也加载不了）；
     `@amaster.ai/pi-memory-mem0` 需要**外部服务**（断网演示不可用，与「全本地、开箱即用」直接冲突）；
     `pi-memory` 的检索范围是 agent 自己的日志 / scratchpad，**不是领域数据**。
  ③ **更根本的一层：本项目的记忆是「有领域结构的」，通用 memory 装不下**：
     掌握度是 **0..1 的连续量**（写入必限幅，P-015）、**33 个知识点之间有 47 条依赖边**
     （`kb.sqlite` 实测：`kp` 33 行；`knowledge_dependencies` 47 行 = 44 条 `prerequisite` + 3 条 `related`）、
     闯关状态**四档**（`locked | learning | quizzed | mastered`，`server/app/store/migrations.py`）、
     学段是**可变的推断结果**（D-020）。第三方 memory 的记忆模型是「把对话压成摘要」，
     用它就要把这套结构**压扁**；而需求里的那句「根据答题表现和兴趣偏好**动态调整**后续推荐」里的「调整」，
     靠的正是依赖图 + 掌握度这套结构。
  ④ **安全考量（未成年人数据）**：Pi 官方安全文档原文 ——「Pi does not include a built-in sandbox. …
     Extensions are TypeScript modules that run with the same permissions」
     （本机 `desktop/node_modules/@earendil-works/pi-coding-agent/docs/security.md:33`；
     `docs/extensions.md:111` 同口径：「Extensions run with your full system permissions and can execute arbitrary code」）。
     装一个第三方扩展 = 把第三方代码以**完整系统权限**放进主进程，而本项目处理的是未成年人数据。
  ⑤ **成本 / 收益**：注入块的 token 增量约 **150–250**，相对四学段模板各约 **2.5k token** 是零头
     （`architecture/notes-main.md:391` 记的 "~2.5k-token templates"）；
     而跨会话原文召回要新建「切片 + 索引 + 召回 + 留存策略」**一整套子系统**，还要额外承担对话正文入库的合规成本。
- **★ 边界（本条最重要的部分，改这块代码前先看）**：
  - **偏好 key 固定词表 4 个**：`interest` / `explain_style` / `pace` / `note`。
    因为 `profile_pref` 是 `key TEXT PRIMARY KEY`（`server/app/store/migrations.py:246`），
    **总条数天然 ≤ 4，不需要任何清理 / 淘汰逻辑** —— 这正是选「固定词表」而不是「自由 key」的直接理由
    （自由 key 会立刻长出「谁来决定删哪条」这个问题）。
  - **「模型写掌握度」在类型层面不可能**：`remember_preference` 的参数 schema 只接受上面 4 个 key，
    掌握度**没有任何写入入口** —— 它是判分规则算出的**客观量**（限幅逻辑在写库唯一路径上，P-015）；
    一旦模型能写，就会出现「模型觉得学生懂了就改分」的漏洞，个性化闭环会当场失去可信度。
  - **值限幅 1–40 字、单行、不含个人信息**（由写入端点校验）。
- **被否决的方案**：
  ① **引入第三方 memory 插件** —— 理由 ②/③/④（原生依赖撞守卫、领域结构被压扁、第三方代码以完整权限进主进程）；
  ② **跨会话召回对话原文** —— 要建索引就意味着**对话正文进 SQLite**，直接破坏「SQLite 不存对话正文」这条纪律
     （D-012），是**合规倒退**，不是功能增强；
  ③ **用 LLM 每轮自动抽取偏好**（照学段第二层 LLM 复核的形态）—— 改为**模型主动调 Tool**：
     不增加每轮 LLM 调用；且每次写入都会出现在**工具调用轨迹图**里（D-014，服务 25% 设计分），
     符合「能力经 `registerTool()` 暴露、路由交 LLM 自主选择」的既有架构（D-011）。
- **代价 / 风险**：偏好写入是**模型主动行为**，不能保证每次都写 —— 但 key 固定词表 + 条数上限让错误的**影响面有界**；
  注入块与学段覆盖共用同一条 prompt 拼装链，必须保持拼装**幂等**（P-038 的教训与防呆：覆盖段要可 grep 验证生效）。
- **服务哪条评分**：教育适配性 20% —— 「根据答题表现和兴趣偏好动态调整后续推荐、提供个性化学习路径」是需求中明列；
  同时不把未成年人数据与主进程权限交给第三方代码（合规）。

## D-032 注入进 System Prompt 的内容必须**逐字节稳定**：块不放时间，渲染与顺序都确定

- **日期**：2026-09-18
- **决策**：给 system prompt 里那段**每轮重拼**的内容（画像块，D-031 的 A 项）立三条硬规则：
  ① **不放时间** —— 块里不再渲染「最近活跃」（`student.lastActiveAt` 仍然保留在契约里给界面用，只是不进给模型的那一段）；
  ② **顺序确定** —— 偏好按固定词表顺序渲染（`PREFERENCE_ORDER`），不用 `Object.entries` 的原始顺序；
  ③ **不依赖调用方** —— 掌握度平局按 `kpId` 兜底排序，不依赖服务端返回的数组顺序。
  结论：**同样的画像 → 逐字节相同的块**；只有画像真的变了，块才变。
- **理由**：system prompt 是**前缀缓存的最前面一段**，缓存按「从头开始的最长相同前缀」命中 ——
  块里任何一个每轮都变的字节，都会让整段前缀**连同它后面的全部对话历史**一起丢掉命中。
  Pi 内置目录里 `deepseek-v4-flash` 的缓存读价是输入价的 **2%**（`cost.cacheRead = 0.0028` vs `input = 0.14`，
  单位 $/M token），且**写缓存不收费** —— 也就是「没命中」不是多付一笔，而是拿不到那个 50 倍折扣。
  本次实测的触发路径非常隐蔽：`learning_log` 每轮会 `upsert_student` 刷新 `last_active_at`，
  而块里那行「最近活跃」精确到分钟 —— 学生两次提问隔了一分钟以上（正常对话几乎必然发生），
  下一轮的 system prompt 就整体变一个字节，**整个会话历史一起掉出缓存**。
  学生感觉到的是响应变慢（重新预填充），账单上是成本。
- **被否决的方案**：
  ① **降低注入频率**（比如只在第 1 轮注入画像）—— 那就退回成「只在开头个性化」，
     需求要的「动态调整 / 个性化学习路径」直接作废；省下的还是分级金额（实测整份 system prompt 约 1.6–1.8k token，
     一次十轮对话的差额在**分**的量级）。
  ② **把画像改成每轮追加到对话里**（让 system prompt 冻结、历史 append-only，缓存最友好）——
     追加内容会**永久驻留**在对话历史里逐轮叠加（第十轮累积到约 4k token，长期反而更贵），
     且会写进 Pi 的会话 JSONL，等于把内部画像混进学生的对话记录，破坏「画像只在数据层」的边界。
  ③ **为了缓存把四学段模板拆成「公共基座 + 风格段」** —— 学段模板整份替换（约 1.8k token）
     只在学段**真的被推断切换**时才发生（规则引擎有 5 轮冷却 + 连续 3 轮同向），那是**该付的代价**；
     而「四学段语气可明显区分」是评分表上的明文验收项，为缓存拆它等于拿得分点换半分钱。
- **代价 / 风险**：模型看不到「这个学生多久没来了」。判断依据是 —— 这个信息对**本轮教学**没有价值
  （真正有意义的「好久没来」是**天级**信号，需要时应该由推荐链或专门字段表达，而不是靠一个每分钟都变的时间戳顺带捎上）。
  若将来确实要给它，必须做成**天级**字段并同步更新 G21 组断言，不能退回分钟级。
- **服务哪条评分**：用户体验 15%（首字延迟）—— 缓存命中直接影响的是**响应速度**，
  而速度是学生能直接感觉到的；成本只是顺带的收益。

## D-033 学习档案的四个只读聚合端点：跨表聚合放 Python，**导出格式放渲染进程**

- **决策**：把「错题本 / 学习报告 / 章节进度 / 学习地图」做成四个**只读**端点
  （`/api/quiz/mistakes/{id}`、`/api/profile/{id}/report`、`/api/knowledge/chapters/{grade}`、
  `/api/graph/overview/{grade}`），其中：
  ① 一切**聚合与判定**（连续天数、正确率、章节排序、错题归并、分层）在 Python；
  ② 而**导出成 Markdown 的拼装**放在渲染进程（`study/report-markdown.ts`，纯函数）。
- **理由（① 为什么聚合必须在 Python）**：这是混合后端的既有边界 ——
  TS 侧不读 SQLite、不自己拼 SQL、不自己算向量。报告要跨 `learning_history` /
  `mastery` / `progress` / `grade_history` 四张表 + `kb.sqlite` 的章节清单，
  让 TS 做等于把数据域撕开一半。而且「连续学习天数」这类口径一旦两边各算一份，
  界面上与模型看到的值就会不一致。
- **理由（② 为什么导出格式可以放渲染进程）**：它是**展示文本**，不参与持久化、
  不影响推荐、不进 Prompt —— 与「掌握度、推荐、学段必须在 Python」那类**业务判定**
  有本质区别。数据在点导出时已经在这台机器上（store 的 ref），为了一个格式转换
  再送回 Python 等于多开一趟 HTTP + 多定义一对契约模型。
  代价：导出格式的权威在 TS。**如果哪天导出物要参与合同或对外交换，必须挪回 Python**。
- **为什么做成四个端点而不是一个大接口**：四个页签各自独立取数（报告慢不该让
  地图转圈），分开之后每个端点都能单独测、单独缓存、单独降级。
- **被否决方案**：
  1. **在渲染进程聚合**（一次拿原始行，前端 group by）——违反数据域边界，
     且要新增能读原始 `learning_history` 的通道（把学生全部学习流水推给渲染进程）；
  2. **把章节清单存进 `learning.db`**（跟着学生走）——教材内容会在每个学生的库里
     各存一份，改教材时到处对不上，且与学生数据混在一起；
  3. **错题本 join `generated_question` 取完整题干** —— 那张表带 `reference_answer`，
     把带答案的表接进对外响应收益极小、风险极大（§6.3 答案泄漏防护）；
  4. **给学习报告加 LLM 生成的「点评」** —— 报告是**按需页面**，加一次云端调用会把
     「打开报告」变成付费且可能失败的操作；点评交给对话（那是 LLM 该在的地方）。

## D-034 历史会话只做「只读回看」，**不做**「点开继续聊」

- **决策**：本轮把 Pi 的会话列表、搜索、正文回看接出来，但**不做**会话切换/续聊、
  不做分支 UI、不做启动自动恢复最近会话。
- **理由**：数据一直在存（Pi 每个会话一个 JSONL），缺的只是「能看见」。
  而「切过去继续聊」是**另一件事**：要先 `dispose()` 当前 runtime（否则 JSONL 半写，
  这是 §5 第 13 条硬约束）、要把 Pi 的 `SessionEntry[]` 投影成前端的 turns、
  还要处理「装配期间被 dispose」的代际竞态。把「看得见」与「接着聊」分开落地，
  比半途接管会话安全得多 —— 后者一旦做错，代价是**学生的历史对话文件被写坏**。
- **★ 附带定下两条安全约束**（不是风格问题，是漏洞与不漏洞的区别）：
  1. **只接受会话 id，绝不接受路径**：渲染进程递进来的东西先与
     `SessionManager.list()` 的结果**对齐**（白名单），再用 Pi 自己给的 `path` 打开。
     若直接打开前端给的路径，渲染进程就等于拿到了「读任意文件」的能力；
  2. **会话目录显式指向该学生**（`resolveStudentPiPaths().sessionDir`），
     否则 Pi 会退回 `~/.pi/agent/sessions/`（用户自己 CLI 的目录）。
- **被否决方案**：把 Pi 的 `SessionInfo[]` 原样丢给渲染进程 —— 那会把**宿主绝对路径**
  （含用户名）带到前端，既泄漏环境信息，也让「渲染进程不该知道文件系统」这条线失效。
  所以主进程要投影成只有 `{id, title, messageCount, modifiedAt, createdAt, preview}` 的摘要。

## D-035 导出的文件名清理用**白名单重建**，不用黑名单过滤

- **决策**：`sanitizeFileName()` 先按两种分隔符切出最后一段，再用**白名单**把
  「非汉字/字母/数字/空格/`-`/`_`/`.`」的字符全部替换成 `-`，最后强制 `.md` 后缀。
- **理由**：黑名单式过滤（`replace(/\.\./g, '')`、`replace(/[<>:"|?*]/g, '')`）看起来更短，
  但**可以被绕过**（`....//`、`..\/`、超长名、`.env` 这类以点开头的名字都要单独想）。
  白名单重建的性质更强：**输出里不可能出现白名单外的字符**，于是「能不能得到一个路径」
  这个问题在构造上就无解。
- **负向对照的发现（值得记下来）**：给这条规则做回归注入时发现，
  单独把「切分隔符」步骤退化成黑名单，18 条断言**全绿** ——
  因为白名单那一步已经兜住了。这说明**两层保护里只有一层是真正承重的**，
  于是补了一条注入把两层同时退化的用例（3 条断言变红），
  确认「路径穿越」那组断言确实有牙齿，而不是靠另一层顺手挡住。

## D-036 学习地图**自绘内联 SVG**，不引入任何图表库

- **决策**：依赖图全览在渲染进程用自写的分层布局 + 纯 SVG 画出来，
  不加 `mermaid` / `echarts` / `d3` / `cytoscape` 中任何一个。
- **理由**：① 本项目**零新增 npm 依赖**（打包风险与断网演示是硬约束）；
  ② 手画需要的只是一次分层遍历 + 一点几何（四学段各 5–7 章、单学段 8–9 个知识点，
  实测 33 个 kp / 47 条边，规模远没到需要图算法的程度）；
  ③ 布局写成**纯函数**之后可以单测「确定性」—— 引库反而测不了这一条。
- **布局的三条确定性质**（都有断言）：分层来自服务端算好的最长前置链（箭头永远向下）、
  同层内按 kpId 排（不依赖入组顺序）、直角折线不画曲线（任意缩放下观感一致）。
- **被否决方案**：把 Mermaid 文本塞进既有主进程的 `toMermaid()` 输出 ——
  那是给 `docs/tool-trace.mmd` 用的**文件导出**，渲染进程没有 Mermaid 运行时；
  真要用就得把 Mermaid 打成依赖（与①冲突），或者退回 CDN（断网白屏）。

## D-037 学段 = **默认自动推断 + 学生可手动指定**（手动后冷却 10 轮回归自动）—— 把 D-020 删掉的人工入口收回来

- **日期**：2026-09-17
- **决策**：学段保留**两条写路径，但只有一个决策者**：
  ① **自动**（默认）：规则引擎从四类信号判定，原子写 `student.grade_level` + `grade_history(source="inferred")`，
  **下一轮**经 `before_agent_start` 生效 —— 与 D-020 完全一致，**一个字没改**；
  ② **手动**（新增）：学生点指示器或设置页 → `grade:set` IPC → `POST /api/grade/override` →
  写 `grade_history(source="explicit", confidence=1.0)`，**立即生效**，之后 **`MANUAL_COOLDOWN_TURNS` = 10 轮**内
  自动判定不生效，期满平滑回归自动。
   **两处界面入口共享同一个 store action**（`chat.setGrade`）；指示器显示**来源标签**（「手动选中」/「AI 引擎推算」）。
  ★ **对话请求仍然不带学段**：`ChatSendRequest` 里没有 `gradeLevel`（G6c 钉死只有 `text`）——
  手动走**独立通道**，因为「发一条消息」不该是「顺带改一次学段」的副作用。
- **理由**：D-020 对**默认行为**的判断是对的（学段应当由模型从学生输入里判断出来，
  让未成年人先自报是冗余的一步），但它把代价算错了：需求原文
 「**学生可选择所在学段**（小学低年级/小学高年级/初中/高中）或教材，智能体根据选择自动匹配对应的知识库内容、
 交互风格和难度梯度」是一句**明确的可选择性要求**，也是 20% 教育适配性的现场演示动作。
  D-020 用「系统更聪明」换掉了「需求那一句被字面满足」，而这**两者不必二选一** ——
  推断引擎当着默认，人工入口当着逃生舱：**默认不要求学生做任何事，但他想做的时候必须有地方可做**。
- **D-020 当年三条顾虑的逐条处理**（这是本条最该讲清的地方）：
  ① 「把判断责任转嫁给未成年人」→ 默认路径**不要求他做任何事**，人工入口是**可选**的，不是必经一步；
  ② 「重新引入两套真相（手选值 vs 推断值）与优先级判定」→ **一套真相**：两条路径写**同一列**、
     同一张轨迹表，只有 `source` 不同；优先级不需要判定（谁最后写谁生效），冷却窗口按来源自动切换（10 / 5）；
  ③ 「要么有入口要么没有，不做半套」→ 这一条**当年是对的，现在也照办**：不是隐藏的兜底入口，
     而是明说的、带来源标签的正式入口。
- **被否决的方案**：① **维持 D-020 原样**（不给人入口）—— 需求那句继续不被满足，演示动作也不成立；
  ② **退回 D-009 的「显式选择为权威」** —— 那会让**系统再也不自动判**，等于放弃双层判定这条创新点；
  ③ **在请求里加 `gradeLevel`**（顺手改学段）—— 会让每轮对话都带一个只在设置时才变的值，
     且把「改学段」变成发消息的副作用，G6c 会红。
- **★ 关键实现取舍：冷却长度**按「最近一次写入的来源」推导，**刻意不新增列**。
  锚点 = 最近一条 `from_level` 非空的 `grade_history` 行（真变更**或**学生确认）。
  加列会让迁移变复杂，更重要的是会引入**第二处真相**（列里的值与轨迹可能不一致）。
- **★ 关键实现取舍：不提供 `note` 字段**。`grade_history` 表没有可写列，而「不许加列」是硬约束；
  把学生输入塞进日志又违反「日志里不出现学生文本」。
  **收下一个写不进去的字段等于让接口撒谎**（调用方以为留痕了，其实被丢弃），所以宁可不提供 ——
  并把这个取舍钉成一条断言（`PRAGMA table_info(grade_history)` 里没有 `note`）。
- **★ 实现中实测抓到的两个坑**（都写进了 §10.3 与 P-060）：
  ① **冷却锚点的 `turn` 必须用「当前轮次水位」**：写 0 会让 `state()` 一算 `elapsed = 当前轮 - 0`
     就把「冷却剩余 10」当场报成 3 —— 验收项真假绿；
  ② **在途的自动判定会覆盖手动选择**：判定在服务端算完、回程路上学生点了别的学段，
     那个**按旧学段算出**的结论回来会把学生刚选的值顶掉（表现成「我明明选了，它又跳回去」）。
     解法是 `epoch`：手动采纳 +1，上交任务 `await` 前后比对，不一致就丢弃（与 F3 跨学生丢弃同一手法），
     并有**反向对照**（不调 `adoptOverride` 时那条结论必须被采纳）。
- **接受的代价（主动写进报告，不要回避）**：学生可能把自己**锁在错档位最多 10 轮**。
  兜底：冷却期**不是**关闭自动（期满立刻按积累的证据判定，期间信号照常收集）；
  学生**随时可以再改**（重复选择写新锚点行、冷却重新计时 —— 这是「以最后一次意图为准」，不是惩罚）。
- **收益**：需求原文「学生可选择所在学段」**重新被字面满足**；四学段对比演示重新有 UI 入口
  （点一下就切，比「由浅入深提问」快得多，两条演示路径都保留）。
- **服务哪条评分**：教育适配性 20%（需求字面兑现 + 推断引擎仍在工作 + 现场可演示）；
  设计合理性 25%（两条路径一套真相、冷却按来源推导不加列、在途结论的作废机制）。

## D-038 教材章节 = **软偏好 + 学生显式选择**（模型不可写、不做 SQL 硬过滤、学段变更即清空）

- **日期**：2026-09-18
- **决策**：学生可以**显式选定「当前在学哪一章教材」**；该章节作为**软偏好**进每轮 System Prompt
  （渲染进画像块的一段固定文本，**无章节时整行不出现**），**不改检索契约、不做 SQL 硬过滤**。
  存储 = `learning.db` 的 `student.current_chapter` 列（迁移 v2 加列，读写各只有一个原语）。
  **学段变更即清空当前章节**。契约新增 `ChapterUpdateRequest` / `ChapterStateOut`，
  路由 `GET|PUT /api/profile/{student_id}/chapter`（与画像同域）。
- **理由**：
  ① **需求原文字面兑现**：`docs/项目简介.md` §2.1「学生可选择所在学段（小学低年级/小学高年级/初中/高中）
     **或教材**，智能体根据选择自动匹配对应的知识库内容、交互风格和难度梯度」——
     学段那半句已由 D-037 收回，本条正是「**或教材**」这半句；
  ② **章节是「学生的意图」，不是推断量**：与学段不同（学段由规则引擎从四类信号判定、模型不可靠），
     「我在学哪一章」没有任何可推断的证据，只有学生自己知道 —— 所以它是**显式选择**，
     且**模型不可写**（写入口只有一个学生动作触发的端点）；
  ③ **软偏好而不是硬过滤**：学生问「前面学的那个…」「换个章节讲讲」时，硬过滤（SQL `WHERE chapter=…`）
     会在 KNN top-k 之前就把其它章节截断掉，追问直接失效；软偏好的意思是**检索契约一个字不改**，
     只在 Prompt 层引导「优先围绕本章；学生若问其他章节，照常回答」；
  ④ **学段一变就清空**：章节属于**某一本教材**，学段换了那本书就不存在了 ——
     不清空就会出现「学段已是初中、Prompt 还说在学小学低年级第4章」这种**第二处真相**。
- **被否决的方案**：
  ① **把章节塞进 `PreferenceKey`** —— 那等于**让模型获得写章节的能力**（`remember_preference` 的参数就是
     这个词表）；而且该词表之所以能保持「**总条数天然 ≤ 4、不需要任何清理 / 淘汰逻辑**」，
     正是因为它是 `profile_pref` 主键上的封闭词表（D-031）—— 多开一个 key 就走上了「自由 key」那条路，
     立刻长出「谁来决定删哪条」这个问题。章节是**学生的显式选择**，不该由模型决定；
  ② **存 `profile_pref`（另开一个 key / 另起一行）** —— 同一理由（模型可写、词表被撑开）
     **外加语义错位**：`profile_pref` 是「学习偏好」（兴趣 / 讲解风格 / 节奏），章节是「课程位置」；
     两者生命周期也不同 —— 章节要随学段清空，偏好**不**应该随学段消失；
  ③ **SQL 硬过滤**（在 `rag_search` 的检索里按章节过滤）—— 追问答不上，见理由 ③；
  ④ **每轮多打一次 HTTP 取章节** —— `fetchStudentContext` 每轮已经在打 `GET /api/profile/{id}`，
     章节就在**同一个响应**里（给 `ProfileResponse.student` 补一个 `currentChapter` 即可）；
     另开一次请求是白付一次往返，还多一个失败点；
  ⑤ **每轮把章节追加进对话历史** —— 内容会永久驻留并逐轮叠加（长期反而更贵），
     且会把内部状态写进学生的 Pi 会话 JSONL —— 与 D-032 否掉「画像改追加」的是同一条理由；
  ⑥ **给模型一个写章节的 Tool** —— 章节是学生的显式选择，模型最多能「建议」，写库必须由学生按下去。
- **★ 关键边界（改这块前先看）**：
  - **章节清单只读 `kb.sqlite`**（`kb_repo.chapters_by_grade`，顺序按章号解析，见 P-057），
    **当前章节只写 `learning.db`** 的 `student.current_chapter` 列 —— **两处不许混**
    （与 D-033 的「不要把教材清单存进学生库」同一条纪律）。
  - 章标题上限 **80 字**：`strip()` 后仍超限**或含换行 → 422**（与偏好值同一口径：拒换行、不静默压平）；
    **空串 = 清除**（写 NULL，不需要 kb）。非空标题必须命中**该生当前学段**的章标题集合，否则 422；
    kb 打不开 → 503。`PreferenceKey` / `RagSearchRequest` / `ChatSendRequest` **一个字没动**。
  - **画像块里的章节行**在**固定位置**（紧跟首行标题、在掌握度之前），空章节**整行不出现**；
    它只在**学生改动时**变 → 不违反 D-032（但改这一行时仍要守住「不放时间、不放进度百分比」）。
- **代价 / 风险**：学生改一次章节 = 块变一次 = 丢一次前缀缓存命中 —— 这是**该付的代价**
  （它换来真实的个性化更新，且只发生在学生主动动作时；不像时间戳那样每轮都变）。
  学段变更清空章节意味着学生要重选一次 —— 如实表达「那本书不存在了」，
  优于替他留一个跨学段的幻觉章节。
- **守卫**：契约 / 路由 / 学段清空的行为断言在 `server/tests/test_chapter_selection.py`；
  画像块稳定性（章节行位置、同画像两次渲染逐字相等、**改章节后块必须变**（反向对照）、
  无章节时块与从前逐字相等、块内不含日期 / 时刻 / 10 位以上数字串）在
  `desktop/tests/student-context.test.ts` 的 **G23 组**。
- **服务哪条评分**：教育适配性 20%（需求原文「学生可选择…**或教材**」字面兑现）+
  设计合理性 25%（软偏好与硬过滤的取舍、单一读写落点、与 D-032 缓存纪律自洽）。

## D-039 界面以 `UI/` 原型为唯一表现层，**保留 desktop 的非视觉层**，两处并行接线

- **日期**：2026-09-18
- **决策**：把 `UI/`（另一轮对话产出的 Vue 3 + Element Plus 静态原型）**移植为 `desktop/src/renderer`
  的表现层**，同时**保留** desktop 已有的非视觉层（`api/*`、`stores/*`、`sandbox/*`、`labels.ts`）。
  原型目录在移植完成后**删除**（不再作为独立工程存在）。
- **理由**：
  - 原型是**零接线**的（全部数据来自一个 388 行的 `mocks/index.ts`，没有 fetch / EventSource / IPC），
    但它的**非视觉部分不值钱** —— 值钱的是 desktop 那一侧已经接好的东西：
    6 事件归约（`api/events.ts`）、沙箱（`iframe-host` / `pyodide-runner` / `monaco-setup`）、
    学段与章节的两条独立写通道、以及 548 条回归测试。**丢掉任何一样都等于把已验过的链路重做一遍。**
  - 反过来，desktop 原来的视觉是「先用能用的」，原型在版式与信息层次上明显更好，且带一份冻结的
    `版式契约.md`（字号阶梯 / 间距档 / 零动效）。所以**换皮 + 保引擎**是最省且最不容易错的组合。
- **被否决的方案**：
  - **把原型当作独立前端、跑一个 dev server 与后端联调** —— 用户明确否决（「肯定是要接线进后端一起联动使用，
    就算构建也肯定一起构建不用分开」）。而且那会把「渲染进程只走 IPC 白名单」这条架构约束绕开
    （原型是 HTTP 直连的思路），token 下发与 CORS 那一整类故障会全部回来。
  - **引入 vue-router（原型是 router 驱动的）** —— 见 D-040。
  - **丢弃 desktop 的多标签学习档案页、严格照设计稿** —— 会丢掉错题本 / 章节进度 / 学习地图 /
    历史会话回看 / Markdown 导出这五项**已实现且可演示**的功能。改为**并入**（概览 + 5 个子页）。
- **代价 / 风险**：
  - 原型里有 ~45 个文件依赖 `unplugin-auto-import` 的「API 与 Element Plus 组件都不写 import」约定，
    所以 desktop 必须接受这套构建期行为（新增两个 dev 依赖）。
  - 原型的设计令牌（`--k12-*`）与 desktop 旧令牌不兼容 → `assets/base.css` **整体替换**，
    所有 `var(--bg)` / `var(--text)` 一类旧引用在移植中一次性改掉（**不留过渡期**，留着就是两种视觉混用）。
  - 移植期必须**分批改**：先构建配置 → 再状态层 → 再逐页，每批用 `npm test` + `typecheck` 设关卡。
    一次性大爆炸式替换会让「哪一处坏了」无从定位。
- **服务哪条评分**：用户体验 15%（版式契约 + 学段自适应配色）+ 设计合理性 25%
  （非视觉层的既有约束**一条没丢**：6 事件、沙箱、学段/章节双通道、答案防泄漏）。

## D-040 导航**不引入 vue-router**，`stores/ui.ts` 的 `PAGES` 是唯一真相

- **日期**：2026-09-18
- **决策**：8 个页面的导航由 `stores/ui.ts` 的 `PAGES: Record<PageName, PageMeta>` + `ui.go(page)` 驱动；
  原型的 `vue-router` 用法（`route.meta` 推导侧栏、`router.push`）全部改掉。
- **理由**：
  - Electron **单窗口**应用：没有 URL、没有前进后退、没有深链。引一个路由库是为一个 `ref<string>`
    付一份依赖与一套新概念（这条理由在 desktop 最初的 `stores/ui.ts` 里就写过）。
  - ★ **更重要的是单一真相**：如果同时存在 router 与 store，迟早在
    「侧栏高亮的是这一页、内容区渲染的是那一页」上对不上。
    原型本来就只有**一处**真相（router 的 `meta`），移植时保留这个性质，只是把载体从 router 换成 store。
  - 换掉 router 还顺带保住两处既有资产：`ui-shell.test.ts`（6 条）与
    `verify-ui.mjs` 的 `view-entry` 三步循环断言 —— 它们读的都是 store 的导出。
- **被否决的方案**：**照搬 router**（改动最小但引入双真相 + 两处测试同时失效）；
  **router 与 store 并存**（最坏：两处都要维护，且谁优先没有明文）。
- **代价 / 风险**：`ui.page` 是 `PageName` 联合类型，**新增页面要在三处同时改**
  （`PageName`、`PAGES`、`PAGE_ORDER`）—— TypeScript 会漏掉第一处之外的两处，
  所以 `PAGES` 用 `Record<PageName, PageMeta>` 写：**漏了哪个键 typecheck 当场报**。
- **服务哪条评分**：设计合理性 25%（导航单一真相、约束用类型而不是纪律来守）。

## D-041 窗口固定 1440×900 + **无边框窗口**，标题栏由页面自绘

- **日期**：2026-09-18
- **决策**：Electron 窗口改为 `frame: false` + 固定 1440×900（`minWidth` 1120，与
  `#app` 的 `min-width` 对齐），最小化 / 最大化 / 关闭三个键做进页面（顶栏最右端），
  新增 4 条 IPC 通道（`window:minimize` / `window:toggle-maximize` / `window:close` /
  `window:maximize-changed` 推送）。
- **理由**：
  - **1440 是设计基准**：版式契约（`docs/ui/版式契约.md`）与 `assets/base.css` 的断点
    都按它写；`<1280` 会让侧栏收成 64px 图标条、对话右栏改浮层 —— 响应式是**有意的**，
    但演示与验收要在一屏里看全。原来的 1080×760 恰好落在 `<1280` 那一档，
    于是「图标旁边没有文字」被当成 bug 报了上来（其实那是断点行为）。
  - **无边框**：Windows 原生标题栏是系统灰 + 应用图标 + 菜单，与本设计
    （浅色纸面 + 学段配色）完全不是一套视觉；且它会在顶栏之上再压一行，
    把「对话优先」的纵向空间吃掉一截。
- **被否决的方案**：
  - **`titleBarStyle: 'hidden'` + `titleBarOverlay`**（macOS 的路子）：在 Windows 上会得到
    **系统画的**按钮，与本设计仍然不是一套 —— 等于换了个位置的原生按钮，没有解决问题。
  - **保留原生标题栏、只改窗口大小**：不满足「把最上面的栏砍掉」这条明确要求。
- **代价 / 风险**（都以「少一条就让窗口变得不好用」的强度记在代码注释里）：
  1. **拖拽区**：顶栏那一行必须是 `drag`，其内每个可交互元素必须 `no-drag`，
     否则点击被吞、且**不报错**（见 P-069）；
  2. **最大化状态要推回渲染进程**：双击拖拽区、`Win+↑/↓`、拖到屏幕上边缘、
     系统菜单都会改变它，而渲染进程一个都观察不到 —— 所以有那条推送通道，
     否则按钮图标会一直画错；
  3. **窗口可缩放边框**：Windows 会给无边框窗口留约 7px 的不可见缩放边框，
     所以 `GetWindowRect` 量到的是 1454×909 而内容区是 1440×900 —— **不是 bug**，
     写验收脚本时不要按外框尺寸断言。
- **服务哪条评分**：用户体验 15%（原生栏的灰与设计的浅色纸面互相打架，砍掉后视觉是一套）。

## D-042 数据检视两页从「不进侧栏」改为**进侧栏**（无 router 的必然结果）

- **日期**：2026-09-18
- **决策**：`knowledge`（教材知识库）与 `dependency`（依赖图谱）的 `nav` 由 `false` 改为 `true`，
  放进侧栏「学习数据」分组。
- **理由**：原型把这两页标成 `nav: false`（「开发/数据检视」页），但**原型是 router 驱动的**
  —— 那时 `nav: false` 的语义是「不进侧栏，但可以直接改哈希进去」。
  本项目按 D-040 不装 router，那条「另一条入口」根本不存在，
  于是两页**代码完整、接口接好、但界面上点不到**（实测全仓 grep 只有渲染分支，没有导航）。
  而「教材知识库」里恰好有**导入教材 / 重建索引**两个真功能 —— 做了却进不去等于没做。
- **被否决的方案**：**给它们另加入口**（比如在设置页放两个链接）——
  多一条要维护的跳转路径，而这两页本身对「看数据 / 验收」有用，
  直接进侧栏最省且最不容易忘记。
- **代价 / 风险**：侧栏从 6 项变 8 项。它们放在「学习数据」组**末尾**（`PAGE_ORDER`），
  学生日常路径（对话 / 能力三页 / 学习档案）的顺序一点没动。
- **服务哪条评分**：设计合理性 25%（把「有功能但没入口」这件事在结构上消灭掉）。

## D-043 字号阶梯整体抬升：**正文 14px → 16px**（用眼健康的硬要求）

- **日期**：2026-09-18
- **决策**：把 `--k12-fs-*` 全部 8 档一起抬一档（22→24 / 16→18 / 14→16 / 13→14 /
  12→13 / 11→12 / 15→17），`--k12-lh-body` 1.7→1.75；
  外壳三个尺寸跟着长：侧栏 248→264、顶栏 64→72、阅读栏 820→880。
- **理由**：使用者是 **K12 学生**，会长时间盯着看。14px 的中文在 1440 宽窗口上
  确实偏小 —— 阅读费劲、眼睛容易累。这是**用眼健康**问题，不是审美偏好
  （用户原话：「要考虑学生的视力和长时间使用对眼睛的疲劳 字体太小阅读起来会费劲」）。
- **★ 为什么是「整条阶梯一起抬」而不是只抬正文**：
  只抬正文会让它顶到「次级正文」那一档，档位差被吃掉，
  「标题比正文还小」这类问题会重新出现。抬完之后三条关系仍然成立且更宽松：
  顶栏页面名（17）< 内容区身份行（24）；正文（16）> 任何 meta（13/12）；
  `micro` 仍只给 ≤4 字角标。
- **被否决的方案**：
  - **只抬正文到 16**：见上，会破坏档位差。
  - **加一个「大字号模式」开关**：多一条要维护的路径，且默认字号仍然偏小 ——
    应该把默认值修对，而不是让用户自己去找开关。
- **代价 / 风险**：
  - **容器必须跟着长**（不是字号的错，是容器没跟着长）：侧栏 / 顶栏 / 阅读栏三个尺寸一起改，
    否则会出现「字挤在栏里」「按钮贴着文字边缘」；
  - **写死高度的地方会裁字**：实测抓到 `.cp__model`（22px 固定高装 13px 字）
    与 `.fp__btn`（24px 图标按钮）—— 前者改成由内边距撑开，
    后者抬到 28px（图标按钮的可点区由「手指能不能按到」定，不由视觉定）；
  - **窄栏里的 flex 单行会错位**：实测抓到右栏降级链 —— 档位名折行后
    `align-items: center` 把状态标签飘到两行之间。改成顶对齐 + 圆点自下移，
    并把档位名压到最短。
- **服务哪条评分**：用户体验 15%（可读性是它的地基）+ 教育适配性 20%（低龄学生更需要大字号）。

## D-045 构建联动**由代码强制**：源码指纹 + 装包后校验，取代「记得先跑后端打包」的人为纪律

- **日期**：2026-09-19
- **决策**：把「两条构建链（TS 与 Python）的顺序」从**文档纪律**升级为**构建链的强制检查**：
  1. `server/scripts/build_info.py` = **源码指纹的唯一实现**：对「会进包的文件」按路径排序后做
     sha256（`app/` `scripts/` `packaging/` `knowledge/` `resources/` + `pyproject.toml` `uv.lock`；
     `resources/models/` 的 91MB ONNX **只记大小**；`tests/` `dist/` `build/` `__pycache__` 与
     `resources/kb/`（构建产出）**不参与**）。带 `FINGERPRINT_SCHEMA` 版本号。
  2. `build_server.py`：**打包前**算指纹 → 打包 → 往产物目录写 `build-info.json`；
     自检里新增断言「产物指纹 == 当前源码指纹」；新增 `--if-stale`（新鲜就秒退）。
  3. `desktop/scripts/build-server.mjs`：JS 侧**只调用** Python 取指纹并比对（不自己算哈希），
     挂在 npm 脚本上：`build` 前置 `build:server`；`build:win` / `build:unpack`
     **后置** `check:server:packaged`（校验**装进包里**的那一份）；另有独立的
     `check:server` / `check:server:packaged` 供随时查。
- **理由**：P-072 实测到「安装包里跑着一个几天前的后端」——源码里修好的 bug 在包里还活着、
  新加的端点回 404，而 `npm test`（877 项）与 `typecheck` **全绿**（它们测的是源码）。
  当时只把顺序写进文档，但**文档不能失败**：它没有退出码，换个人/换个上下文照样踩。
  构建系统本身不知道有两份产物 —— `extraResources` 只是「把磁盘上现成的那份拷进去」，
  没有任何一步会问「这份 exe 是不是当前源码打的」。
- **被否决的方案**：
  - **在 `electron.vite.config.ts` 里用 vite 插件钩子去构建 Python**：vite 的钩子粒度是
    「模块图」而不是「产物新鲜度」，且把 PyInstaller 塞进 vite 插件会让
    `npm run dev`（热更新）有莫名其妙的长阻塞；npm 脚本层的顺序编排更直白、更好读。
  - **用 electron-builder 的 `beforePack` 钩子**：时机合适（装包前），但 PyInstaller 要跑几分钟，
    而 electron-builder 的钩子没有「跳过」语义 —— 每次出包都重打一遍 exe，
    在「只改了一行 CSS」时是纯粹的浪费。npm 脚本 + `--if-stale` 能做到「新鲜就秒退」。
  - **JS 侧重写一份哈希逻辑**（不调 Python）：两套算法只要在排序 / 编码 / 换行上有任何差异，
    就会变成「刚打过包却永远判过期」（然后大家开始无视警告）或更糟的
    「过期却判新鲜」（交付事故）。所以 JS 只做**调用与比对**，`G20-4` 守卫断言 JS 侧不得出现 `createHash`。
  - **按 git commit 判新旧**：那样「改了、没提交、直接打包」会被判成**新鲜**
    —— 而那正是最危险的场景（现场改一行 bug 然后出包）。
    所以指纹哈希的是**文件内容**，commit 只作溯源展示。
- **代价 / 风险**：
  - 每次 `npm run build` 都会多一次「算指纹」的开销 —— 实测 **0.34s**（`resources/models/` 只记大小），
    新鲜时**不会**触发重打包，所以这是可接受的常数成本。
  - `tests/` 刻意**不进**指纹：改个测试不该触发几分钟的重打包。否则大家会开始想办法绕过它
    —— 一个逼人绕过的检查等于没有检查。
  - 逃生舱 `K12_SKIP_SERVER_BUILD=1` 保留（CI 里刚单独打过时用），但它会**打印警告**：
    静默跳过正是本机制要消灭的东西。
  - ⚠️ **`resources/kb/` 不进指纹**（它是 `build_kb.py` 的产出，不是源码输入），
    所以「只改了教材没重打包」不会触发 —— 但改教材同时会改 `knowledge/` 下的 Markdown，
    那一条**在**指纹里，兜得住。
- **服务哪条评分**：设计合理性 25%（构建纪律的自动化是「工程完成度」最直接的证据）
  + 可复现性 / 交付可信度（**创新性 15%** 的答辩素材：「把人为纪律换成机器检查」）。
