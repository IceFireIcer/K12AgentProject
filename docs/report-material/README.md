# 报告素材（docs/report-material/）

> **纪律**：每天留 30 分钟，把当天的**截图 / 关键决策 / 踩坑与解决**写进本目录。
> **素材不攒——第 15 天写不出报告。**（出处：`项目执行文档.md` 第 4.1 节执行纪律第 3 条）

## 这个目录干什么用

项目报告与答辩 PPT 的一手素材全从这里出。写代码时顺手记，写报告时直接抄。
不在这里记的东西，到 D15 一定想不起来「当时为什么这么定」「这个坑是怎么爬出来的」。

## 两份文件

| 文件 | 记什么 | 最终去哪 |
| --- | --- | --- |
| `decisions.md` | 技术决策：定了什么、**为什么**、否掉了什么、代价是什么 | 项目报告第 7 章 + **答辩预设问题**（第 16 节那 9 问绝大多数是决策题，答案就在这里） |
| `pitfalls.md` | 踩坑：现象 → 根因 → 解决 → 怎么用进报告 | 报告第 7 章「**难题与解决方案**」（第 16 节指定该章直接取材本文件） |

## 条目格式（两份文件都是「一条目一小节」）

`decisions.md`：标题写「决策一句话」+ 括号补关键限定；字段固定六项、顺序固定：

- **日期** / **决策** / **理由** / **被否决的方案** / **代价 / 风险** / **服务哪条评分**

`pitfalls.md`：标题写「坑的一句话」+ 括号补根因关键词；字段固定五项、顺序固定：

- **现象** / **根因** / **解决** / **防呆**（自动化断言 / 守卫测试 / 脚本自检）/ **报告用法**

「服务哪条评分」只能填评分表的五档：设计合理性 25% / 多模态交互质量 25% / 教育适配性 20% / 用户体验 15% / 创新性 15%。
填不出来的条目，说明这个决策或这个坑不值得写进报告。

## 编号规则

- 编号自 **2026-09-16** 起从 `D-001` / `P-001` **重新开始**（此前编号作废），后续只追加、不重排。
- 新条目一律接在文件末尾，编号 +1；即使中间的死路后来复用了，也不改号、不复用号。
- 条目一旦写下就不要再「美化」：**保留当天的真实判断，包括后来被证明是错的那部分**。
  报告里「我们一度以为 X，实测是 Y」比一份流畅的结论更可信。

## 记录口径

- **决策必须写「被否决的方案 + 否决理由」**。只写结论的决策记录，答辩时一定会被问穿。
- **踩坑必须写根因**（为什么会这样），不要只写「改了这个参数就好了」。根因才是报告第 7 章要的东西。
- 截图等附件一并放本目录，条目里用相对路径引用即可（**工具调用轨迹的源文件例外**：按执行文档 §7.1 落在 `docs/tool-trace.mmd`，其渲染图/截图可放本目录）。
- 本目录只是**叙述**，不是规格。与 `项目执行文档.md` 冲突时，**以执行文档为准**。
